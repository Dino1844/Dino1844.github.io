1. 速度鸿沟：6 个数量级

根本约束

存储层次速度谱

CPU 0.3ns 一个 cycle。磁盘 10ms 一次 I/O。差了 30,000,000 倍。这就像你 1 秒能做完的事 vs 等一整年。I/O 子系统的全部设计都是为了让 CPU 不要等。
$$\begin{aligned}\text{L1 Cache} &\sim 0.5\text{ ns} \quad (1\times)\\\text{L2 Cache} &\sim 4\text{ ns} \quad (8\times)\\\text{RAM} &\sim 100\text{ ns} \quad (200\times)\\\text{SSD} &\sim 100\text{ }\mu\text{s} \quad (200{,}000\times)\\\text{HDD} &\sim 10\text{ ms} \quad (20{,}000{,}000\times)\end{aligned}$$

2. 中断 · 轮询 · DMA

CPU 怎么知道 I/O 完成了？三种方式：

  • 轮询：CPU 反复检查设备状态寄存器——"好了吗？好了吗？"简单但浪费 CPU。适合I/O 极快且频繁的场景（如 10Gbps 网卡——等一个中断的时间数据已经到下一批了）。
  • 中断：设备完成 I/O → 发中断 → CPU 跳到 ISR（中断服务程序）。CPU 在 I/O 期间可以做别的事。适合I/O 慢的场景（磁盘 I/O ~ms 级）。
  • DMA（Direct Memory Access）：CPU 编程 DMA 控制器（"从磁盘读 4KB 放到物理地址 0x12345000"）→ DMA 控制器自己完成数据传输 → 完成后发中断。CPU 只参与"发起"和"收尾"——数据传输由 DMA 包办。
DMA 体现了范式 #6（HW-SW 协同）的极致。硬件（DMA 引擎）做它最擅长的事——按地址批量搬数据（快而蠢）。OS 做它最擅长的事——决定搬去哪、什么时候搬（慢而聪明）。

3. I/O 调度：电梯与它的后代

和 CPU 调度（0002 §7）同一范式——机制是 I/O 请求队列，策略是怎么排序。

I/O 调度器演进

电梯算法（Elevator）：磁头在一个方向扫——合并所有同一柱面的请求，到最远端再回头。简单有效——把随机 I/O 变成顺序 I/O。问题：中间柱面的请求可能等很久（饥饿）。
预期调度（Anticipatory）：完成一个请求后等一小下（几 ms）——如果来了相邻的请求就合并，没来就移走。利用空间局部性——程序经常连续读同一个文件。
CFQ（Completely Fair Queue）：每个进程一个 I/O 队列，按进程公平分配 I/O 带宽。防止一个进程的大量随机 I/O 饿死其他进程。
Deadline：每个请求带 deadline——读请求通常 deadline 更紧（同步操作，有人在等），写请求可以放松（异步——write-back）。
SSD 时代：无 seek 时间——电梯不再有意义。NVMe 的多队列设计让每个 CPU 核有自己的提交队列——无需锁争用。用 noop/mq-deadline/Kyber（基于令牌桶的带宽控制）。

4. RAID：用冗余换可靠性

冗余

RAID · Redundant Array of Independent Disks

RAID 把多块磁盘组合成一块"逻辑盘"——不同 RAID 级别在性能、可靠性、空间效率之间做不同权衡。核心思想：用校验和（parity）代替完整镜像，节省空间。
级别最少盘数空间效率容错读性能写性能
RAID 02100%0 块（坏了全丢）N×N×
RAID 1250%N-1 块N×1×
RAID 43(N-1)/N1 块(N-1)×校验盘瓶颈
RAID 53(N-1)/N1 块N×写放大 4×
RAID 64(N-2)/N2 块N×写放大 6×

RAID 5 写放大与 write hole

RAID 5 的 parity 计算公式：$P = D_0 \oplus D_1 \oplus D_2 \oplus D_3$（异或）。更新 $D_0$：

  1. 读旧 $D_0$ 和旧 $P$
  2. 计算新 $P' = P \oplus D_{0,old} \oplus D_{0,new}$
  3. 写新 $D_0$ 和新 $P'$（两次写 → 4 次 I/O：2 读 + 2 写）

RAID 5 write hole：如果在步骤 3 的两次写之间断电 → $D_0$ 是新值、$P'$ 是旧值 → parity 不一致。之后一个盘坏了 → 用错误的 parity 重建 → 数据损坏。解法：RAID 6（两个独立 parity）或在写前记录 stripe 的意图日志（类似文件系统 journal）。

RAID 5 在现代大容量磁盘上已危险。16TB 盘 + 不可恢复读错误率 $10^{-15}$ → 重建一个盘时读取剩余数据（N-1 × 16TB）遇到一个不可恢复错误的概率 > 50%。如果 rebuild 中又坏一块 → 数据全丢。RAID 6（双冗余）是 2020s 的最低实践。

5. 存储层次全景

把 OS 管的（RAM/SSD/HDD/swap）和硬件管的（L1/L2/L3 cache）拼在一起，就是完整的存储层次。每层是下一层的缓存——数据在层之间移动的规则就是 OS 和硬件各自的策略：

层间数据移动规则

L1↔L2↔L3↔RAM：硬件自动——cache line 64B 为单位，LRU/伪 LRU 替换
RAM↔SSD/HDD：OS 管理——4KB 页为单位，swap/page cache 驱动，clock/LRU 替换
page cache↔文件系统：OS 管理——buffer/page cache，write-back（攒批）或 write-through（立即写）

范式 #2 · 缓存（存储层次版）

从寄存器到磁带，每一层都是下面一层的缓存。每一层都在用"更快但更小的介质"存"更慢但更大的介质"的热数据子集。局部性原理让这个金字塔立得起来——如果访问是均匀随机分布的，各级缓存全是废的。

7. 推导与自测

P1 · 速度鸿沟量化 L1

3GHz CPU 周期 0.33ns。RAM 延迟 100ns，SSD 延迟 100μs，HDD 延迟 10ms。CPU 每周期执行 1 条指令。在等 RAM/SSD/HDD 的一个 I/O 完成期间，CPU 可以执行多少条指令？（假设无超线程/乱序——简单模型）

▸ 解答
RAM: 100ns / 0.33ns ≈ 300 条指令。SSD: 100,000ns / 0.33ns ≈ 300,000 条指令。HDD: 10,000,000ns / 0.33ns ≈ 30,000,000 条指令。
P2 · RAID 重建风险 L2

RAID 5，5 块 10TB 盘（总 40TB 可用）。单盘 URE（不可恢复读错误）率 $10^{-15}$。一块盘坏了，rebuild 需要读其余 4 块。计算 rebuild 中遇到至少一次 URE 的概率。如果用 RAID 6（双冗余），重建中遇到两次 URE 的概率大概多小？

▸ 解答
4 块 × 10TB = 40TB = 40 × 8 × $10^{12}$ bit = $3.2 \times 10^{14}$ bit。URE $10^{-15}$ → 每 $10^{15}$ bit 一个错误。$3.2 \times 10^{14} / 10^{15}$ ≈ 32% 概率遇到至少 1 个 URE 在重建中。
RAID 6：一次 URE 不影响重建（可纠正）。需要两次独立 URE → 概率 ≈ 0.32² ≈ 10%（仍然是不可忽略的）。真正安全需要 RAID 6 + 定期 scrubbing（主动检测并修复静默错误）。
P3 · 中断合并设计 L3

网卡接收数据包（每包 1500B）。10Gbps 链路 → 833,333 pps。如果每包一个中断 → 每秒 833,333 次中断。(a) 估算每次中断的代价（参考 0001 P1）——开销占 CPU 的百分比。(b) 设计中断合并方案——每 N 个包或每 T 微秒发一次中断。tradeoff 是什么？

▸ 解答
(a) 每次中断 ~几百 cycles → ~0.1μs。833K × 0.1μs = ~83ms = 8.3% CPU 在中断处理上。加上中断处理代码本身（分配 sk_buff、拷贝数据……）→ 可能 > 50%。
(b) NAPI（Linux 的新 API）：收到第一个包 → 中断 → 中断处理函数 disable 中断、启动 poll → poll 循环收包直到队列空或 budget 用完 → re-enable 中断。合并后的开销：~1 次中断/每批。代价：延迟——包在网卡队列里等 poll。对吞吐型（下载文件）无所谓，对延迟敏感型（高频交易、在线游戏）可能不可接受。
