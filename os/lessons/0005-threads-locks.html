1. 线程 vs 进程：共享什么、不共享什么

核心

线程 · Thread

一个进程可以有多个线程。线程共享：地址空间（代码+数据+堆）、文件描述符表、信号处理。线程独立拥有：PC（执行到哪）、寄存器、栈（每个线程有自己的栈）、线程 ID。

2. 竞态条件：原子性的幻觉

0001 P3 的 `balance = balance + 100` ——在 x86 上是三条指令：`mov eax, [balance]`; `add eax, 100`; `mov [balance], eax`。如果两个线程交错这三条 → 结果不确定。这不是"编译器的问题"——这是硬件指令级的事实。

临界区（Critical Section）：访问共享数据的代码段——同一时刻最多一个线程在其中。解法 = 互斥（Mutual Exclusion）。互斥的三个要求：正确性（最多一个在临界区）、公平性（有机会进去）、性能（不空耗 CPU）。

3. 锁的硬件基础：从关中断到 CAS

锁实现技术演进

① 关中断（单核·最简单）：进入临界区前 `cli`（关中断），出去后 `sti`（开中断）。在单核上，只要没中断就不会有人抢 CPU → 不会有线程切换 → 临界区自然互斥。缺点：(a) 关中断期间所有 I/O 中断都丢失；(b) 用户态程序不能关中断（特权指令）；(c) 多核上没用——另一个核上的线程不受影响。
② Test-and-Set（硬件原子指令）：`TAS(lock_addr)` 原子地返回旧值、写入 1。如果旧值 0 → 拿到锁；旧值 1 → 锁被占——自旋重试。
③ Compare-and-Swap（CAS）——更强的原子指令：`CAS(addr, expected, new)` → if *addr == expected → *addr = new, return true; else return false。CAS 比 TAS 更通用——它能做的不只是 0/1 flag：无锁栈、无锁队列、原子计数器都靠 CAS。
停下来想一想：锁本身的实现需要原子指令——但谁来保护原子指令？答案：硬件。`LOCK` 前缀（x86）锁住总线或 cache line——在这个原子操作完成前，其他核不能访问同一 cache line。这是范式 #6（HW-SW 协同）的极致——原子指令是硬件给的、锁是软件造的。

4. 自旋锁 → mutex：从忙等到休眠

自旋锁（Spin Lock）：拿不到锁就一直在循环里 CAS——"忙等"。适合临界区极短（几 ns）的场景（内核里常见）。不适合用户态——如果持锁的线程被切走（时间片到），等锁的线程会空转整个时间片。

互斥锁（Mutex）：拿不到锁 → 把自己放入等待队列 → 调 `schedule()` 让出 CPU。持锁线程 unlock 时唤醒等待队列中的一个线程。适合临界区可能较长（μs–ms）的场景。

范式 #6 · HW-SW 协同（锁版）

硬件提供 `LOCK CMPXCHG`（CAS）——一个可以原子地"比较并交换"的指令。软件用它构建自旋锁、mutex、信号量、RCU。硬件不决定临界区多长——那是软件的权力。硬件只管"这个 8-byte 操作不会被打断"。

5. 信号量与生产者-消费者

同步原语

信号量 · Semaphore

一个信号量 = 一个整数 + 一个等待队列 + 两个原子操作：`sem_wait()` ("P"): 如果 count > 0 → count--; 否则 → 睡眠等待。`sem_post()` ("V"): 如果有人在等 → 唤醒一个; 否则 → count++。

二值信号量（count=1）= 互斥锁。但信号量更强大的是计数信号量——控制"最多 N 个线程同时访问资源"。

生产者-消费者问题（Bounded Buffer）：一个或多个生产者线程向有界缓冲区放数据，消费者线程取数据。解：

  • `sem empty(N)` — 缓冲区空位数（初值 N = buffer size）
  • `sem full(0)` — 缓冲区已有数据数（初值 0）
  • `mutex lock` — 保护缓冲区内部数据结构

生产者：`sem_wait(empty); lock(mutex); 放入; unlock(mutex); sem_post(full);`

消费者：`sem_wait(full); lock(mutex); 取出; unlock(mutex); sem_post(empty);`

两个信号量各管一个条件（有空位吗？有数据吗？），互斥锁管缓冲区内部的原子性。三个原语，解一家族问题。

信号量易错。如果生产者顺序写成 `lock(mutex); sem_wait(empty);` → 缓冲区满了 → sem_wait 睡眠 → 持锁睡觉 → 死锁（消费者需要锁才能取数据 → `sem_post(empty)` 但拿不到锁）。这个错误非常常见——因为它看起来"只是顺序不同"。

6. 推导与自测

P1 · CAS 实现自旋锁 L1

用 C 伪代码和 CAS 实现 `spin_lock(lock)` 和 `spin_unlock(lock)`。

▸ 解答
`spin_lock(int *lock) { while (CAS(lock, 0, 1) == false); }` — 原子检查 lock 是否为 0，是 → 设为 1 返回 true（拿到锁）；否 → 返回 false 继续循环。
`spin_unlock(int *lock) { *lock = 0; }` — 释放不需要原子（只有持锁者会写）。
P2 · 生产者-消费者死锁分析 L2

分析：如果 mutex lock 放在 sem_wait(empty) 之前，在 buf 满时会发生什么？画出线程状态。

▸ 解答
生产者获锁 → sem_wait(empty) buf 满 count=0 → 睡眠。消费者需要获锁才能取数据 → 但锁被睡眠的生产者持着 → 死锁。
P3 · Linux futex L3

Linux 的 futex（fast userspace mutex）是 mutex 的高效实现——它在无竞争时不陷入内核。(a) futex 怎么知道有没有竞争？(b) 为什么"无竞争走用户态、有竞争才走内核"能大幅减少系统调用的次数？(c) 这体现了哪个设计范式？

▸ 解答
(a) futex 在用户态用原子 CAS 尝试拿锁。如果 CAS 成功 → 没人竞争 → 直接从用户态返回（零系统调用）。CAS 失败 → 有人持锁 → 调 `futex(FUTEX_WAIT)` 陷入内核睡眠。(b) 大多数 mutex 的持锁时间极短、竞争极罕见——99%+ 的 lock/unlock 可以在用户态完成。(c) 范式 #6（HW-SW 协同）：硬件给 CAS（用户态快速路径），软件在竞争时才用内核机制（休眠/唤醒）。
