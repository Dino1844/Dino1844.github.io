第 3 课我们学了 TCP——它给你一条可靠的字节流管道。但浏览器和服务器在管道里传什么？格式是什么？请求长什么样？响应长什么样？这就是 HTTP（HyperText Transfer Protocol）的职责：定义客户端和服务器之间交换消息的格式和语义。

🎯 本课目标：理解 HTTP 的请求-响应模型、常见方法与状态码的语义、Header 的作用、HTTP/1.1→HTTP/2→HTTP/3 的演进逻辑（队头阻塞→多路复用→QUIC）、以及缓存策略的基本原理。

1. HTTP 的核心模型：请求-响应

HTTP 是无状态的请求-响应协议。客户端发一个请求，服务器返回一个响应。协议本身不记住上一次交互——每个请求都是独立的。

请求 (Request)
响应 (Response)
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Firefox/121.0
Accept: text/html
Accept-Language: zh-CN
Connection: keep-alive

（空行，表示 Header 结束）
（GET 请求没有 Body）
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256
Cache-Control: max-age=3600
Date: Mon, 16 Jun 2026 ...

（空行）
<!DOCTYPE html>
<html>...</html>

关键结构：

  • 起始行——请求是 方法 + URL + 版本，响应是 版本 + 状态码 + 原因短语
  • Header——键值对，描述消息的元数据。以空行结尾
  • Body——实际传输的数据（GET 请求通常没有 Body）
🔗 对接 TCP 知识：上面那些 Header 和 Body 在传输时被 TCP 切成一个一个的段。HTTP 不关心 TCP 怎么分段——它只管"把这些文本发给对面"。这就是分层的威力：HTTP 作者不需要知道 TCP 的拥塞控制算法。

2. 方法 —— 你想让服务器做什么？

方法语义有 Body？安全？幂等？
GET获取资源否是是
POST创建资源 / 提交数据是否否
PUT完整替换资源是否是
PATCH部分修改资源是否否
DELETE删除资源通常否否是
HEAD只获取 Header（不要 Body）否是是
OPTIONS查询服务器支持哪些方法否是是

幂等的意思是：同样的请求发 N 次，结果和第 1 次一样。PUT 是幂等的（每次都用同样的内容覆盖），POST 不是（每次都会创建新资源）。这个区别在工程上很重要：如果请求超时了但不确定服务器有没有处理，幂等的请求可以直接重试，非幂等的需要先检查。

3. 状态码 —— 服务器一句话告诉你结果

范围含义典型例子
1xx信息：收到了，还在处理101 Switching Protocols（WebSocket 升级）
2xx成功200 OK · 201 Created · 204 No Content
3xx重定向：去别的地方找301 Moved Permanently · 302 Found（临时） · 304 Not Modified
4xx客户端错误：你的锅400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 429 Too Many Requests
5xx服务器错误：我的锅500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable · 504 Gateway Timeout
💡 面试常考：301 vs 302 的区别。301 是永久重定向，浏览器会缓存并自动跳转（下次直接去新地址，不发请求到旧地址）。302 是临时重定向，每次都会先问旧地址。搜索引擎看到 301 会把权重转移到新 URL，看到 302 不会。

4. Header —— HTTP 的元数据层

Header 是 HTTP 最灵活的设计。它们承载了消息的上下文信息，使得 HTTP 从简单的文件传输演变成了功能丰富的应用协议：

分类Header 示例作用
内容协商Content-Type, Accept, Accept-Language"我能处理 HTML 和 JSON，你支持哪种？"
缓存控制Cache-Control, ETag, Last-Modified"这个资源 1 小时内不会变，到期前直接用缓存"
认证Authorization, Cookie, Set-Cookie"这是我的身份令牌" / "这是给你的会话 ID"
连接管理Connection, Keep-Alive"这个 TCP 连接用完别关，我还要接着用"
CORSAccess-Control-Allow-Origin"允许来自这些域名的跨域请求"
压缩Content-Encoding, Transfer-Encoding"响应体用 gzip 压缩了" / "分块传输，长度未知"

Cookie 是一个特别值得理解的机制——因为 HTTP 是无状态的，Cookie 用来在客户端存储一小段数据，让服务器能识别"这是同一个用户"。每个请求浏览器自动带上匹配的 Cookie，这就是登录状态能跨请求保持的秘密。

HTTP/1.1 的队头阻塞问题

HTTP/1.1 虽然可以用 Keep-Alive 在同一个 TCP 连接上发多个请求，但请求是串行的——必须先收到上一个响应才能发下一个请求。浏览器为此开了 6 个并行的 TCP 连接来缓解（每个连接各自串行），但这带来了连接开销。

管道化（Pipelining）试图解决——不等上一个响应就发下一个请求。但问题是：响应必须按请求顺序返回。如果第一个请求处理很慢（比如查数据库），后面的响应全部被堵住——这就是 HTTP 层的队头阻塞。

HTTP/2 的多路复用

HTTP/2 在单个 TCP 连接上建立了多个流（Stream）——每个请求-响应对分配一个流 ID，帧在流之间交错传输：

TCP 连接（单条）
  ├─ 流 1: [HEADERS]──[DATA]────────────────────[收完]
  ├─ 流 3: [HEADERS]────[DATA]──[DATA]──[收完]
  └─ 流 5: [HEADERS]────────────[DATA]──[收完]

帧交错到达：1.HDR → 3.HDR → 1.DATA → 5.HDR → 3.DATA → 5.DATA → 3.DATA → 1.END

接收方按流 ID 重新组装。快的请求不再被慢的请求堵住，一个 TCP 连接就能承载所有并发。

但 HTTP/2 仍然跑在 TCP 之上。如果 TCP 层丢了一个段，后续所有段的提交都会被阻塞——尽管它们属于不同的流。这是 TCP 层的队头阻塞，HTTP/2 解决不了。

HTTP/3：抛弃 TCP

HTTP/3 直接基于 QUIC（一种在 UDP 之上的可靠传输协议）。QUIC 把"流"的概念下移到了传输层——每个流独立处理丢包：流 A 丢了包只阻塞流 A，流 B 不受影响。再加上 0-RTT 握手（省掉一次往返）和连接迁移（WiFi 切 4G 不断连），HTTP/3 是真正为现代网络设计的协议。

HTTP/1.1HTTP/2HTTP/3
传输层TCPTCPQUIC (UDP)
并发方式多 TCP 连接单 TCP + 多 Stream单 QUIC + 多 Stream
队头阻塞HTTP 层 ✗TCP 层 ✗无 ✔
握手TCP (1RTT) + TLS (1RTT) = 2RTTTCP + TLS = 2RTTQUIC 内置 TLS 1.3 = 1RTT (复用 0RTT)

6. 缓存 —— 不请求就是最快的请求

HTTP 的缓存机制是 Web 性能的基石。浏览器和 CDN 节点都依赖它来决定「要不要重新请求这个资源」。

强缓存：直接不问服务器

服务器在响应中告诉客户端「这个资源 X 秒内有效」：

Cache-Control: max-age=3600       ← 3600 秒内直接用缓存，不问服务器
Cache-Control: no-cache           ← 可以用缓存，但必须先问服务器确认
Cache-Control: no-store           ← 完全不缓存

协商缓存：问服务器"变了没？"

缓存过期后，浏览器带着上次的指纹去问服务器：

请求 →  If-None-Match: "abc123"        ← "我有版本 abc123 的缓存，你有更新的吗？"
       If-Modified-Since: Mon, 16 Jun  ...

响应 ←  304 Not Modified                ← "没变，用你的缓存吧"（没有 Body，极省带宽）
         或
       ←  200 OK + 新内容 + 新 ETag     ← "有更新，这是新版本"

ETag 是内容的哈希指纹——只要内容变了一个字节，ETag 就不同。这比用时间戳精确得多。

📚 补充：CDN —— 为什么 YouTube 在美国看和中国看一样快

浏览器 → DNS → TCP → TLS → HTTP 这一整条链路，延迟的最大瓶颈是物理距离。光在光纤中的传播速度大约 200,000 km/s，地球周长为 40,000 km——从北京到纽约的光纤延迟下限大约是 200ms（仅光速损耗，不包括路由器处理）。

CDN（Content Delivery Network）的核心思想：把内容提前推到离用户最近的节点。

CDN 如何工作

  1. 内容复制：把静态资源（图片、视频、JS/CSS）同步到全球数百个边缘节点（Edge PoP）
  2. DNS 导向：用户访问 cdn.example.com 时，DNS 根据用户的 IP 地理位置，返回最近的 CDN 节点 IP（基于 GeoDNS / Anycast）
  3. 缓存命中：CDN 节点有缓存就直接返回（几毫秒），缓存未命中再回源站拉取

没有 CDN vs 有 CDN

没有 CDN有 CDN
用户在北京访问美国服务器~200ms RTT~10ms（北京 CDN 节点）
热门视频 100 万人同时看源站被压垮CDN 节点分摊，流量从不回源站
DDoS 攻击源站直接承受CDN 的分布式容量吸收大部分攻击

CDN 和 DNS 的配合

这是 CDN 最巧妙的机制：同一个域名 cdn.example.com，北京的 DNS 返回北京 CDN 节点的 IP，纽约的 DNS 返回纽约 CDN 节点的 IP。这就是为什么 CDN 服务商也是 DNS 服务商——Cloudflare、Akamai、AWS CloudFront 都同时提供 DNS + CDN。

QUIC/HTTP3 在 CDN 中的角色

CDN 是 HTTP/3 的主要推动者。因为 CDN 用户场景是：大量短连接、WiFi↔4G 切换、最后一公里丢包率高。QUIC 的 0-RTT 握手和连接迁移在这些场景下收益巨大。Google 和 Cloudflare 的 CDN 已经全面支持 HTTP/3。
