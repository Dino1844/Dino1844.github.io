1. 管程与条件变量：更结构化的并发

信号量太底层了——P 和 V 可以放在任何地方，编译器和工具链无法帮你检查"是不是每个 P 都有对应的 V"、"P 和 V 的顺序是否正确"。管程（Monitor）把锁和条件封装到一起，编译器/运行时可以保证同一时刻最多一个线程在管程中。

同步原语

管程 · Monitor

一个管程 = 一个互斥锁 + 0 或多个条件变量 + 一组过程（函数）。编译器/运行时保证：同一时刻最多一个线程在管程的某个过程中。锁的 acquire/release 自动发生——程序员不用（也不能）手动操作锁。
历史：C. A. R. Hoare 1974 年提出。Java 的 synchronized 关键字、Python 的 with lock、Go 的 channel 底层都受管程思想影响。

条件变量（Condition Variable）

当线程进入管程但发现"条件不满足"（比如缓冲区空），它不能继续执行。条件变量给了它一个在管程内安全等待的方式：

  • wait(cv, lock)：原子地释放锁 + 把调用线程挂入条件变量的等待队列 + 睡眠。被唤醒时重新获取锁。
  • signal(cv)（或 notify）：唤醒一个在该条件变量上等待的线程（如果有）。
  • broadcast(cv)：唤醒所有等待者。

Mesa vs Hoare 语义

Hoare 语义（理论）Mesa 语义（实际）
signal 行为立即切换上下文给被唤醒者，信号发出者阻塞只是把被唤醒者移到就绪队列，signal 发出者继续执行
被唤醒者如何条件一定满足——可以直接继续条件可能不满足了——必须用 while 重新检查
实现复杂度极高——需要额外的上下文切换简单——把抢占权交给调度器
实际使用几乎无人实现所有现实系统（Java wait()/notify()、pthread_cond_wait、C++ condition_variable）
停下来想一想：Mesa 语义要求用 while(condition) wait(cv) 而非 if(condition) wait(cv)。为什么？
答案：signal 只建议"条件可能变了"——在信号发出者和被唤醒者之间，可能有第三个线程抢先进入管程，消耗了资源，让条件再次不满足。用 if 的话，被唤醒者直接假设条件满足——可能已过时。while 确保再次检查，这是 Mesa 语义的强制要求。

2. 读者-写者问题：饥饿陷阱

读者-写者问题是管程的经典应用：读者只能读，可以并发读；写者独占。用两个条件变量 okToRead 和 okToWrite 协调：

读者-写者的管程方案（伪代码）

读者进入：if (writers > 0 || waitingWriters > 0) → wait(okToRead)。然后 readers++，signal(okToRead)。连锁唤醒：前一个读者唤醒下一个读者，让多个读者同时进入而不干扰写者。
读者离开：readers--。if (readers == 0) → signal(okToWrite)。最后一个读者离开时唤醒一个写者。
写者进入：if (readers > 0 || writers > 0) → wait(okToWrite)。然后 writers++。
写者离开：writers--。if (waitingWriters > 0) → signal(okToWrite) else signal(okToRead)。

但这里有一个饥饿陷阱：如果读者源源不断——读者一进入就 signal(okToRead) 唤醒下一个读者——读者可以"背靠背"地连续进入，写者永远等不到 readers == 0 的时刻。这是写者饥饿（writer starvation）。

解决方案：给写者优先级。当有写者在等时，新读者不能进入——等已有的读者退出后让写者先走。牺牲一点读者延迟，换写者的有界等待。这是"公平性"的经典 tradeoff：无饥饿保证通常以吞吐量为代价。

范式 #5 · 机制/策略分离（读者-写者版）

机制：条件变量 wait/signal + 共享 reader count。提供"读者-写者模式"的基本构件——多个读者并发，写者互斥。策略：读者优先还是写者优先？哪个带饥饿缓解？这些都是可替换的策略，在同一套条件变量机制上实现。Linux 的 rwlock 和 rwsem 就分别提供了不同的读写公平策略。

停下来想一想：如果你设计一个文件缓存系统，读请求是写的 1000 倍。应该用读者优先还是写者优先？
答案：读者优先——写者饥饿的概率极低（排一下队就能得到写锁）。但如果文件系统有日志（journaling），日志写必须尽快完成——那就需要写者优先，让写者不因密集读请求而无限期阻塞。

3. 死锁：四个必要条件的逻辑必然性

灾难

死锁 · Deadlock

四个条件全部满足 → 死锁必然发生。缺一不可——这就是死锁应对的逻辑基础：打破任何一个条件即可预防死锁。

四个必要条件（Coffman 条件，1971）

  1. 互斥：资源不能同时被多个线程使用（锁天然是这个性质）
  2. 持有并等待：线程持有一个资源的同时等待另一个
  3. 不可抢占：不能强行抢走别人持有的资源（持锁不能被夺走）
  4. 循环等待：存在循环链——A 等 B，B 等 C，...，Z 等 A

3.1 死锁检测：资源分配图

资源分配图（Resource Allocation Graph）是可视化死锁的工具。圆形 = 线程，方形 = 资源。从线程到资源的边 = "线程请求该资源"。从资源到线程的边 = "资源已分配给该线程"。有环 → 可能死锁。

3.2 哲学家就餐问题（Dining Philosophers）

五位哲学家围桌而坐，每人左右各有一根筷子。只有同时拿到两根筷子才能吃饭。最直接的解法——每位哲学家先拿左边筷子、再拿右边筷子——会死锁：所有人同时拿起左边的筷子，然后同时等右边的筷子，永远等不到。

解法 1（打破条件 4 循环等待）：给筷子编号，要求所有哲学家先拿较小编号的筷子。哲学家 4（左边 4 号，右边 5 号）先拿 4 号——和以前一样。但哲学家 0（左边 0 号，右边 1 号）先拿 0 号。唯一的改变是哲学家 4（左 4 右 5）：他先拿 4 号（较小），再拿 5 号。如果所有人同时拿较小的——0、1、2、3、4 各拿左边——哲学家 4 左边是 4 号、右边是 5 号——他拿了 4 号后需要 5 号，但 5 号没人抢（5 号不可能被"先拿"因为没有人左右分别是 5 和 0——不存在 5 号是较小的场景）。所以一定有人能拿到两根筷子——环被打破。

哲学家就餐问题的本质：它不是关于"怎么拿筷子"的——它是关于对称性（symmetry）和循环依赖的。所有哲学家执行完全相同的代码 = 所有人在同一时间做完全相同的事 = 齐步走 = 死锁。打破对称性给任意一个哲学家不同的行为（反过来拿、等待随机时间）就能破坏循环等待。

4. 死锁的预防/避免/检测/恢复

死锁有四种应对策略，每种对应不同的前提假设和代价：

四种策略对比

① 预防（Prevention）——在设计层面打破某个 Coffman 条件
打破"互斥"→ 无锁数据结构（§5）。打破"持有并等待"→ 一次性申请所有锁。打破"不可抢占"→ try_lock + 失败释放已持锁。打破"循环等待"→ 强制固定加锁顺序。
代价最小，但对代码结构约束大——有时无法在一次调用中申请所有资源。
② 避免（Avoidance）——运行时判断"这次分配是否安全"
系统跟踪每个线程的最大需求（需提前声明）。银行家算法（下文详述）。
代价：需要先知——知道每个线程的最大资源需求。大多数场景做不到。
③ 检测 + 恢复（Detection + Recovery）——允许死锁发生，发现后解除
定期检查资源分配图是否有环。有环 → 杀一个线程（释放它的所有资源）。
代价：无法回滚 OS 线程的副作用（写了文件、发了网络包）。数据库用得多（事务可回滚）。
④ 忽略——"鸵鸟算法"
假设死锁极其罕见 → 重启机器。Windows/早期 Linux 的实践。
代价：用户数据可能丢失。现代系统至少会做检测（lockdep）。

银行家算法（Banker's Algorithm）的详细推演

Dijkstra 1965 年提出。名字来源于银行家不会把所有现金贷出去——留一部分储备。系统跟踪四个向量：

  • Available：每种资源的剩余量
  • Max：每个线程对每种资源的最大需求（需提前声明）
  • Allocation：每个线程当前持有量
  • Need = Max - Allocation：每个线程还需要多少

算法的核心：在每次分配前，检查"分配后还能找到一条安全序列吗？"安全序列 = 所有线程都能完成的执行顺序（即使它们突然都要最大量）。只有当存在至少一个安全序列时，才允许分配。

停下来想一想：为什么银行家算法实际上很少用？
答案：需要线程提前声明最大资源需求——这在实践中不现实。线程的执行路径取决于输入数据，无法预先知道最大内存/文件/锁的用量。而且线程可能动态创建子线程——执行前谁知道"最大"是多少？STCF 调度（0002 §7.2）也有同样的问题——需要预知执行时间。

5. 无锁编程：CAS 构建栈与 ABA 问题

锁有代价：持锁线程被切走 → 等锁线程全部空转/阻塞 → 优先反转 → 死锁可能。无锁（lock-free）数据结构用 CAS 避免所有这些问题。

5.1 Treiber 栈（无锁栈）

CAS 构建无锁栈

push(node)：do { node->next = top; } while (!CAS(&top, node->next, node));"把新节点的 next 设为当前 top，然后 CAS 尝试把 top 改成新节点——如果这期间 top 被别人改了，重试。"
pop()：do { node = top; if (node==NULL) return NULL; } while (!CAS(&top, node, node->next)); return node;"读 top → 读它的 next → CAS(top, old_top, next)。如果 CAS 失败——重试。"
关键：没有"锁"，没有"临界区"——CAS 失败就 retry。retry 次数 = 竞争度——低竞争时几乎总是一次成功。

5.2 ABA 问题

CAS 有一个致命弱点：它只比较值，不比较"身份"。假设两个线程并发 pop()：

  1. 线程 1 读 top → 节点 A（top=A）。线程 1 读 node->next → B。
  2. 线程 1 被调度走。线程 2 完整 pop A（top→B）。线程 2 再 push A 回去（top→A）。但 A 的 next 已经变了！
  3. 线程 1 的 CAS(&top, A, B) 成功——因为 top 确实等于 A（A 被 push 回来了）。但 A->next 现在指向另一个东西——不是原来的 B。栈的结构被破坏。
ABA 的值等于 A→B→A，CAS 看到"还是 A"，以为没变过。解决方案：用带版本号（tag）的指针——CAS(&top, (A, ver1), (B, ver2)) ——即使地址 A 回来了，版本号不同，CAS 失败。x86-64 上 LOCK CMPXCHG16B 支持 16 字节的 2 字 CAS（指针 + 版本号）。这是下一课更深入的无锁内容的基础。

范式 #3 · 惰性求值（无锁版）

无锁 = 乐观并发控制（optimistic concurrency）——"假设没有冲突，先去做了，如果冲突就重试"。这是惰性求值的并发版：不做冲突预防（锁），冲突发生了才补救（retry）。数据库的 OCC（乐观并发控制）也是同样的思路。

6. RCU：读端零开销的魔法

无锁

RCU · Read-Copy-Update

对于"读极多、写极少"的数据（路由表、文件系统目录缓存、进程列表……），RCU 让读端完全不拿锁、不写共享变量、不需要原子操作——零开销。

三步流程（范式 #3 惰性求值的并发极致）

  1. Copy：写者复制一份数据结构，在副本上做所有修改。原数据不变。
  2. Update：用 rcu_assign_pointer() 原子地更新指向数据结构的全局指针——从旧版切换到新版。这是 O(1) 的操作——一个原子赋值。
  3. Reclaim：等所有正在读旧版本的读者都离开后再释放旧版内存。需要"宽限期"（grace period）。

怎么知道"所有读者都结束了"？

RCU 利用了 OS 调度器的事实：上下文切换点 = 读者的结束点。Linux 内核中，RCU 读者在 rcu_read_lock() 和 rcu_read_unlock() 之间不能睡眠（不能调 schedule()）。所以：

  • 如果每个 CPU 都经历了一次上下文切换——该 CPU 上所有 RCU 读者（如果开始过）必然已经结束
  • synchronize_rcu() 的实现：等所有 CPU 都至少经历一次 quiescent state（上下文切换或 idle 或用户态执行）
  • 现代 RCU 实现（Tree RCU）用内核线程 rcuc 处理回调——不必每次同步等待，可以异步回收
RCU 的优雅：读端在 x86 上 rcu_read_lock / rcu_read_unlock 是空操作（只禁止抢占——但禁止抢占本身不是内存操作）。这意味着读一个 RCU 保护的数据结构——没有任何原子指令、没有锁、没有内存屏障——和普通指针访问一样快。回想 0005 §8 的读写锁：读端需要两次原子操作（获取读锁 + 释放读锁）。RCU 把这两次原子操作降到了零。代价是写端更复杂（copy + synchronize_rcu）。
停下来想一想：RCU 能在用户态用吗？
答案：可以——但无法利用"上下文切换 = quiescent state"这个内核特性。用户态需要自己提供 quiescent state 机制，比如定期调用 rcu_quiescent_state() 或使用用户态调度器协作。Urcu（Userspace RCU）库提供了这个功能，在用户态锁竞争极高的场景（如共享内存数据库）有使用。

8. 习题

P1 · 死锁四条件分析 L1

两个线程各持一个锁等对方另一个锁——经典死锁。逐一确认四个条件是否满足。如果改成 try_lock + 失败就释放已有锁，打破了哪个条件？

▸ 提示
画出资源分配图。每个条件在图中对应什么？
▸ 解答
① 互斥 ✓（锁不能共享）。② 持有并等待 ✓（各持一把等另一把）。③ 不可抢占 ✓（不能夺锁）。④ 循环等待 ✓（A 等 B，B 等 A）。
try_lock + 释放 = 打破条件 3（不可抢占）——主动放弃自己持有的锁，让等待链断开。资源分配图的环被打破。
P2 · 银行家算法推演 L2

系统 12 单位资源。P1（max=10, held=5）、P2（max=4, held=2）、P3（max=9, held=2）。当前分配后剩余 3 单位。问：当前状态安全吗？如果 P2 再申请 1 单位，能分配吗？

▸ 提示
Need = Max - Held。安全序列 = 存在一个顺序，每个进程在获得所需额外资源后都能完成释放。
▸ 解答
当前：剩余 3。P1 need 5（不可满足）、P2 need 2（可满足）→ 先给 P2 完成释放 4 → 剩余 7 → P3 need 7 可满足 → P3 释放 9 → 剩余 16 → P1 need 5 可满足。安全序列 P2→P3→P1 = 安全。
P2 再申请 1 → P2 held=3, need=1, 剩余 2。检查：P2 need 1 可满足 → P2 完成释放 4 → 剩余 6 → P3 need 7 不可满足 → P1 need 5 可满足 → P1 释放 10 → 剩余 16 → P3 need 7 可满足。安全序列 P2→P1→P3 = 安全。可以分配。
P3 · 管程解哲学家就餐 L2

用管程（互斥锁 + 条件变量）实现哲学家就餐问题。每个哲学家的状态可以是 THINKING / HUNGRY / EATING。只允许相邻哲学家都不在 EATING 时，当前哲学家才能开始 EATING。写出 pickup(i) 和 putdown(i) 的伪代码，并说明为什么不会死锁。

▸ 提示
维护 state[5] 数组。pickup(i) 让自己 HUNGRY → 检查左右是否 EATING → 不是则改为 EATING 并 signal 自己。是则 wait。putdown(i) 改为 THINKING → 检查左右邻居——如果可以，signal 它们。
▸ 解答
pickup(i)：lock(mutex); state[i]=HUNGRY; test(i); while(state[i]!=EATING) wait(cond[i], mutex); unlock(mutex)。
putdown(i)：lock(mutex); state[i]=THINKING; test(LEFT); test(RIGHT); unlock(mutex)。
test(i)：if (state[i]==HUNGRY && state[LEFT]!=EATING && state[RIGHT]!=EATING) { state[i]=EATING; signal(cond[i]); }
为什么不死锁：每次 pickup 检查左右是否都在吃——这个检查是在管程锁保护下的。一个哲学家不能"超过自己邻居的状态"。test(i) 的检查防止了"所有人同时拿筷子"的情况。管程锁保证 state 数组的读写原子性。这和 0005 §10 教训相反——这里条件变量在做互斥之外的工作（检查条件），而条件变量的 wait 在管程锁之外阻塞——不会出现"持锁睡眠"。
P4 · CAS 与 ABA 的模拟 L2

无锁栈初始 top→A→B→NULL。线程 1 准备 pop A：读取 top=A，读取→next=B。线程 2 完整 pop A（当前 top→B），再 pop B（top→NULL），再 push A（top→A，但 A→next 不是原来的 B）。假设线程 1 的 CAS(&top, A, B) 在这时执行——它成功还是失败？为什么？栈的最终状态是什么？

▸ 解答
线程 1 的 CAS(&top, A, B) 成功——因为 top 当前确实等于 A（被线程 2 push 回来的那个 A）。top 被设为 B（线程 1 原先读到的 A->next）。
但问题：push 回来的 A 的 next 指向的是另一个东西（假设指向 C），而不是原来的 B。所以 top 被设为 B 后，B 的 next 可能指向 NULL（原本栈只有 A→C→…，但 top 指向了 B，B 不在栈中……）。栈的结构彻底乱了。
P5 · RCU vs 读写锁 L3

比较 RCU 和读写锁（rwlock）在读极多写极少的场景。(a) rwlock 的读端需要什么原子操作？RCU 呢？(b) 在读者有 10000 个、每秒 100 万次读、写者每秒 1 次的场景下，估算 rwlock 和 RCU 的性能差异。(c) 写者较多（每秒 1000 次）时 RCU 有什么问题？

▸ 解答
(a) rwlock 读端：获取读锁（原子递减 reader count）→ 读 → 释放读锁（原子递增）。两次原子操作每次 ~几十 cycle。RCU 读端：rcu_read_lock() + 读 + rcu_read_unlock()——在 x86 上这两个函数是空操作（只禁止抢占——不写任何共享变量）。零原子操作。
(b) rwlock 读者：2×1M×30 cycles = 60M cycles/s；RCU 读者：0。写者 1 次/s 的 synchronize_rcu 等所有 CPU 经历一次 quiescent state——~几到几十 ms——可以接受。
(c) 写者多 → 每次写都要等所有 CPU 进 quiescent state → 延迟高。而且旧版本在 grace period 期间不能释放 → 内存积压。RCU 不适合写密集型。读多写少的"写"也不能太多。（提示：回想 0004 的"抖动"——当回收跟不上分配时，内存会被旧版本撑爆。）
P6 · 设计一个无饥饿的读者-写者锁 L3

使用管程（互斥锁 + 条件变量）设计一个读者-写者锁，保证写者不被饥饿（即有界等待）。提示：需要一个计数器跟踪"有多少读者正在读"，一个标志位"有写者在等待"，以及两个条件变量 okToRead 和 okToWrite。

▸ 提示
关键设计决策：新读者进入前检查是否有写者在等——如果有，读者等待而不是进入；写者进入前检查是否有读者在读——如果有，写者等待；写者离开时，先唤醒写者（如果有），再唤醒读者。
▸ 完整解答
数据结构：int readers=0, writers=0, waitingWriters=0; Condition okToRead, okToWrite; Lock mutex。
readerEnter()：lock(mutex); while(writers > 0 || waitingWriters > 0) wait(okToRead, mutex); readers++; unlock(mutex)。
readerExit()：lock(mutex); readers--; if(readers == 0) signal(okToWrite); unlock(mutex)。
writerEnter()：lock(mutex); waitingWriters++; while(readers > 0 || writers > 0) wait(okToWrite, mutex); waitingWriters--; writers++; unlock(mutex)。
writerExit()：lock(mutex); writers--; if(waitingWriters > 0) signal(okToWrite); else broadcast(okToRead); unlock(mutex)。
为什么无饥饿：写者进入前设 waitingWriters++，新读者看到这个标志就不会进入——等已有读者退出。写者一定能排到所有在它之前、和那些看它标志后不进的读者之前。等待有界。
代价：读者吞吐量下降——即使没有写者竞争，新读者也要先检查 waitingWriters 的值（一次原子读），但相比可能被写者打断的好处，这个代价可接受。
