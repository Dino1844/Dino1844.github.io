1. 虚拟机：在 OS 之下再造 OS

虚拟化

Hypervisor · VMM

OS 在硬件之上造幻象（进程）。Hypervisor 在硬件之上造幻象的幻象——让多个 OS 以为自己独占整台物理机。

Type-1 vs Type-2

Type-1（裸金属）：Hypervisor 直接跑在硬件上（KVM、Xen、VMware ESXi）。Type-2（宿主）：Hypervisor 跑在宿主 OS 上（VirtualBox、VMware Workstation）。

Trap-and-Emulate → 硬件辅助虚拟化

CPU 虚拟化的原始方案：guest OS 跑在 Ring 1（或 Ring 3），它的特权指令（如 `cli`）会 trap 到 Ring 0 的 hypervisor。Hypervisor 模拟这条指令的效果——修改虚拟机的虚拟中断状态而不是物理中断。但 x86 早期不支持——某些特权指令在非 Ring 0 执行时静默失败而非 trap（x86 的虚拟化漏洞）。

硬件辅助虚拟化（Intel VT-x / AMD-V）：CPU 加了 VMX root mode（hypervisor）和 VMX non-root mode（guest）。Guest 的特权指令直接在 non-root 模式下执行——但受 VMCS（VM Control Structure）配置的控制。哪些事件导致 VM Exit（回到 hypervisor）由 hypervisor 编程。

内存虚拟化——嵌套页表：Guest 有自己的页表（GVA → GPA）。Hypervisor 有另一套页表（GPA → HPA）——EPT（Extended Page Table，Intel）/ NPT（Nested Page Table，AMD）。硬件在一次 TLB walk 中同时走两套页表——GVA → GPA → HPA——慢了但不需要 hypervisor 介入。

2. 容器："容器是进程，VM 是机器"

隔离

容器 · Container

容器不是虚拟化——它是"加了围墙的进程"。两个机制：namespaces（限制你能看见什么）+ cgroups（限制你能用多少）。没有 hypervisor，没有嵌套页表，没有额外的内核——所有容器共享宿主内核。
VM容器
隔离层Hypervisor + 嵌套页表Namespace + cgroup
启动时间秒级（boot guest kernel）毫秒级（clone + 设 namespace）
内存开销每个 VM 一个内核（~100MB+）共享内核（容器镜像 ~几 MB+ 应用）
安全隔离强（独立内核 = 攻击面小但非零）弱（共享内核 = 内核漏洞可逃逸）

Namespaces：PID namespace（容器内看到自己的 PID 1）、Mount namespace（自己的文件系统树）、Network namespace（自己的网卡/IP/路由表）、UTS namespace（自己的 hostname）、IPC namespace（自己的信号量/消息队列）、User namespace（容器内 root ≠ 物理 root）、Cgroup namespace（自己的资源限制视图）。

Cgroups（v2）：分层控制——每个 controller（cpu、memory、io、pids……）设使用上限。Memory cgroup 设 `memory.max`——超了就 OOM kill 或不分配。CPU cgroup 设 `cpu.weight`——CFS 按 weight 分配 CPU 给各 cgroup（类似 0002 CFS 的 weight 机制但跨进程组）。

停下来想一想：Docker 镜像的"层"是怎么实现的？答案是 overlayfs——一个 COW 联合文件系统。Base 层（如 ubuntu:22.04）只读，上面叠加多个只读层（每步 RUN），最顶端是可写层。修改文件 → COW 复制到可写层。这和一个文件的完整复制相比，节省了 99% 的空间和传输——范式 #3（惰性求值）从内存 COW（0004）回到了文件系统。

3. 微内核 vs 宏内核

Linux 是宏内核（monolithic kernel）：所有核心服务（调度、内存管理、文件系统、网络栈、驱动）都在一个地址空间里——函数调用就能通信。快但脆——一个驱动崩了整机 panic。

微内核（microkernel）：内核只保留最少的——IPC、地址空间管理、线程调度。文件系统、驱动、网络栈全部是用户态进程——通过 IPC 通信。代表：Minix、L4、seL4。seL4 是整个内核被形式化验证过的（用 Isabelle/HOL 证明了 C 代码实现符合抽象规范——没有缓冲区溢出、没有 NULL 指针解引用）。

微内核的生命线是IPC 性能——如果一次跨进程调用比宏内核的函数调用慢 100×，所有"安全"收益都被性能代价淹没。L4 通过极度优化的 IPC（寄存器传参、避免多余拷贝、scheduling donating——被调用者优先继承调用者的时间片）把 IPC 成本压到 ~100 cycles。

4. OS 安全：内存破坏的攻与防

安全

内存破坏攻防链

从栈溢出到 ROP 到现代防御的演进——每一步防御都是针对上一步攻击的必然回应。

攻击演进

  1. 栈溢出（1988 Morris Worm）：`gets(buf)` 溢出 → 覆盖返回地址 → 跳到 shellcode（栈上的机器码）
  2. ROP（Return-Oriented Programming）：NX bit 让栈不可执行 → 攻击者用 `ret` 链条（gadget），在已有代码里找以 `ret` 结尾的指令片段——跳来跳去拼出攻击语义
  3. return-to-libc：直接跳到 libc 的 `system()`——不需要自己写代码

防御演进

  1. Stack Canary：函数入口在返回地址和局部变量之间放一个随机值。返回前检查——被覆盖 = 异常。绕过：泄露 canary（format string 漏洞读栈）。
  2. NX/DEP（PTE 的 XD bit——0003 §5）：栈页不可执行。绕过：ROP（不执行栈上的代码——用已有的代码）。
  3. ASLR（地址空间布局随机化）：每次启动程序，栈/堆/库的基地址随机化。gadget 地址不可预测。绕过：泄露一个地址 → 算出其他地址。
  4. CFI（控制流完整性）：编译器在每个间接跳转前插入检查——目标地址必须在合法集合里。绕过：更复杂的 gadget——但大幅提高攻击成本。

RowHammer：硬件层的安全问题。反复读(activate+precharge)某一 DRAM 行 → 相邻行的电容泄漏 → bit 翻转。这意味着用户态代码可以在没有访存权限的情况下翻转内核页的 bit——打破所有软件层的防御。修复：DRAM 刷新率提升（性能代价）或 ECC 内存（贵）。RowHammer 提醒我们：OS 的安全金字塔最底层是硬件——硬件层的漏洞无法被任何软件防御完全挡住。

5. Linux 内核数据结构全景

把前 8 课分散讲的数据结构串成一张图——从 `task_struct` 到一切：

task_struct → 整个进程世界的指针

task_struct（每进程一个）—`mm`→ mm_struct（地址空间）—`pgd`→ 四级页表根（PGD 物理地址 → 写入 CR3）—`mmap`→ vm_area_struct 链表（每个 VMA 描述一个已映射区域——代码段/堆/栈/mmap 文件）。
mm_struct—`mmap`→ VMA 链表。`/proc/PID/maps` 就是遍历这链表生成的。0004 缺页处理中，内核检查出错的 VA 是否在任何 VMA 范围内——不在 → SIGSEGV。
task_struct—`files`→ files_struct（打开文件表）—`fdtable`→ file** 数组。`fd=3` → `fdt->fd[3]` → struct file（当前文件位置、访问模式）—`f_inode`→ inode（文件元数据 + 数据块指针）。0007 的 inode 在这里被引用。
task_struct—`tasks`→ 链入全局进程链表（所有 task_struct 串在一起——`ps aux` 遍历这条链表）。—`parent`/`children`→ 进程树（`pstree` 命令的图形）。
task_struct—`sched_entity`→ CFS 的 vruntime + 红黑树节点（0002 §8）。—`stack`→ 指向内核栈（16KB，底部有 `thread_info`）。

遍历一次：`task_struct.mm.pgd → CR3 → 四级页表 → 该进程所有虚拟页的物理映射` 和 `task_struct.files.fdtable.fd[3].f_inode → inode 数据块 → 磁盘`——同一个进程 P 同时持有"内存世界"和"文件世界"的根指针。这就是 OS 的数据结构之美。

6. 一次 read() 的完整代码路径

我们现在有足够的知识去追踪一次 `read(fd, buf, 100)` 从用户态到硬件到返回的完整路径。这是全书知识的综合运用。

read(fd, buf, 100) 的完整代码路径

① 用户态准备：libc `read()` → 设 `rax=SYS_read`(0), `rdi=fd`, `rsi=buf`, `rdx=100` → `syscall`。总开销 ~几十 cycles。
② 硬件陷入内核（0001 §4.1, 0002 §4）：`syscall` → CPU 读 MSR_LSTAR → 跳 `entry_SYSCALL_64` → 硬件自动：切 Ring 0、压栈用户态 RIP/RFLAGS、加载内核栈。~100-200 cycles。
③ 内核系统调用分发：`entry_SYSCALL_64` → 保存所有通用寄存器（SAVE_ALL）→ `do_syscall_64(regs)` → `regs->ax = sys_call_table[__NR_read](regs)` → 调 `ksys_read(fd, buf, 100)`。
④ VFS 层（0007 §3）：`ksys_read` → `fdget(fd)` → `current->files->fdt->fd[fd]` → 得 `struct file *f` → `f->f_op->read`（可能是 `ext4_file_read_iter`）→ `f->f_pos`（读起始位置）。如果 fd 不存在 → 返回 -EBADF。
⑤ 文件系统层（0007 §1–§2）：`ext4_file_read_iter` → 将 (f_pos, 100 bytes) 翻译为 (inode 逻辑块号, 块内偏移) → 查 inode 的多级索引 → 得物理块号。
⑥ Page Cache 检查（范式 #2 缓存）：物理块号 → 查 page cache（address_space->i_pages radix tree）。如果在缓存 → 直接 `copy_to_user(buf, page+offset, 100)` → 跳步 ⑨。缓存命中 = 无磁盘 I/O。这是"快速路径"——大部分 read 走这。
⑦ 块层（0008 §3）：缓存未命中 → 构造 `struct bio`（块 I/O 请求）→ `submit_bio` → 经 I/O 调度器（可能合并相邻请求）→ 入块设备队列。
⑧ 驱动 + DMA（0008 §2）：NVMe 驱动 → 构建 submission queue entry（SQE）→ ring doorbell（写设备寄存器通知有新请求）→ NVMe 控制器从 SQ 取 SQE → DMA 从磁盘读数据到内存物理页 → 完成后写 completion queue entry（CQE）+ 发 MSI-X 中断。CPU 在这期间可以跑别的进程——这是异步 I/O 的基底。
⑨ 中断处理 + 完成：中断 → `nvme_irq` → 读 CQE → 唤醒等待线程（`bio_endio`）→ 数据已在 page cache → `copy_to_user(buf, page+offset, 100)` → 更新 `f_pos += 100`。`copy_to_user` 检查 buf 是否在用户态可写地址——如果用户传了一个内核地址 → 返回 -EFAULT。
⑩ 返回用户态：`sysretq` → 恢复用户态 RIP/RFLAGS → 读到的字节数在 `rax`。总延迟：缓存命中 ~1μs，SSD ~100μs，HDD ~10ms。
这就是操作系统之美。10 步，涉及 0001–0008 的全部核心概念。每一步都是前面机制的具体化。如果你能不看屏幕在脑中走完这 10 步，这个课程就已经达到了它的目标。

8. 推导与自测

P1 · VM vs 容器安全 L2

(a) 攻击者通过内核漏洞拿到了宿主机的 root shell。他能看到容器 A 里的进程的内存吗？容器 B 呢？(b) 如果宿主机跑的是 KVM 虚拟机而非容器，攻击者能从宿主机 root 看到 VM 里的内存吗（无额外漏洞）？(c) 这两种场景揭示了 VM 和容器的什么根本安全差异？

▸ 解答
(a) 宿主机 root → 可以 `nsenter` 进入任意 namespace → 可以看到所有容器的进程、内存、文件。因为容器共享内核——宿主机 root 即是所有 namespace 的 root。(b) KVM 中 guest 的内存在 hypervisor 视角是普通用户态进程的内存——但 EPT/NPT 是独立的页表。宿主机 root 可以读 `/proc/PID/mem` 或 `/dev/mem` 但 guest 的物理内存被映射在 QEMU 进程的虚拟地址空间中——直接读 QEMU 进程内存是可以的（除非额外保护如 AMD SEV 内存加密）。(c) VM 隔离强但非绝对——hypervisor 层的漏洞可打破隔离。容器根本依赖于"内核没有漏洞"这个假设——共享内核意味着一个内核漏洞可以打破所有容器的隔离。
