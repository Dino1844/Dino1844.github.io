Agentic AI 推理的 GPU 气泡：4 种方法 + 大小集群分岔

2026-06-23 · 两轮搜索，精读 10+ 篇论文后提炼

1. 问题：tool call 造成的 GPU 两难

LLM Decode → 生成 tool_call → GPU 空闲 (CPU tool exec 50ms~5s) → Tool Result Prefill → Decode → ... ↑ ↑ ↑ GPU 忙 GPU 气泡 GPU 忙 x 5~100 次 = 严重累积

每个气泡期间，GPU 上的 KV-cache 处于两难：

  • 保留 → 占着显存不做计算 → 其他请求可用显存减少
  • 淘汰 → tool 返回需要重新 prefill → TTFT 增加 + 显存带宽浪费

目前生产引擎（SGLang、vLLM）没有专门针对此场景的机制。经审阅 scheduler 源码确认：GPU 填不满时通用 batching 会塞其他请求，但 KV-cache 的淘汰/保留决策只是 LRU，不知道 "这个 request 等会就回来"。

2. 大 vs 小集群的分岔点

你的集群规模决定了哪个问题更痛：

大集群（几十~几千 GPU）小集群（1~4 GPU）/ 单用户
核心瓶颈KV-cache 显存压力：太多 agent 并发，KV 互相竞争GPU 空转：tool 执行时没有其他请求可填
KV 淘汰错误代价高——淘汰错了，prefill 重新计算的延迟拖慢整个集群低——显存不紧张，几乎不需要淘汰
GPU 空闲时能做什么已经跑满其他请求，无需额外操作没有其他请求——必须创造计算
适合的方法A/B/C（状态管理 + 调度）D（投机计算）

3. 大集群方案：状态管理（方法 A/B/C）

方法之间正交可叠加。

方法 A：Tool-Call 感知的 KV 淘汰决策

核心：把淘汰优先级函数从 LRU 替换为一个知道 "这个 request 等一下要回来" 的函数。
现有：evict_priority = max(now - last_access_time) ← 谁最久没被访问就淘汰谁 方法A：evict_priority = g(agent_state, workflow_structure) ← 谁离下次被访问最远就淘汰谁

不同论文本质上只是 g() 的输入信号不同：

论文信号源怎么算淘汰优先级
Continuumtool call duration 的统计分布TTL = f(reload_cost, queue_delay)；Bernstein 不等式定界；小于 TTL 则保留，过期则淘汰
KVFlowAgent Step Graph（预先知道 agent 调用顺序）steps_to_execution：离下次激活还剩几步，越小越不淘汰
PBKV历史 workflow trace + 当前上下文predicted_reuse_probability：机器学习预测复用概率，只保留高概率的
SAGAAgent Execution Graph（显式声明或 87% 推断）WA-LRU：用 workflow 图优化标准 LRU 的 competitive ratio（1.31× vs 2.84×）
Astraea请求历史状态 + 系统显存压力state × memory_pressure：状态感知的自适应阈值

本质：把 agent workflow 的结构信息编码进 KV 淘汰决策，替代盲目的 LRU。

方法 B：Tool 间隙的主动 KV 搬迁

核心：检测到 tool call → 异步搬运 KV 到便宜存储 → 预测 tool 快回来 → 提前搬回 GPU。
方法A：决定是否淘汰 —— 做决定，不动 方法B：决定搬到哪里、什么时候搬 —— 真的搬数据

不同论文本质上只是搬迁策略的触发条件和搬迁目标不同：

论文触发：GPU→CPU目标 tier触发：CPU→GPU
Tokencake检测到 "function call start" 事件CPU DRAM预测 tool 完成时间，提前启动 H2D
MORIagent 的空闲度排名越过动态分界线GPU HBM ↔ CPU DRAM ↔ SSD 之间动态移动分界排名重新进入"忙"区间时

关键参数：offload_stride（每次搬多少）、prediction_horizon（提前多久预测回传）。

本质：把 tool call 间隙当作免费的数据搬运窗口——不是在 GPU 上空等就是在传数据，选后者。

方法 C：Workflow 级调度（非 Request 级）

核心：调度器看到的不是独立 request，而是整个 agent workflow。同一个 workflow 的多步放入同一 GPU，保持 KV 亲和性。
现有：scheduler 看到 [req1, req2, req3, ...] 一堆独立请求，不知道 req1→req2 属于同一个 agent 方法C：scheduler 看到 [workflow_A: req_a1→req_a2, workflow_B: req_b1→req_b2→req_b3, ...]

论文的区分只在 "workflow 结构怎么来"：

论文workflow 信息源调度策略
SAGAAgent Execution Graph（显式/推断）同 workflow request → 同 GPU（session-affinity batching）+ work-stealing 平衡负载
ThunderAgent用户用 API 声明 LLM Programprogram-aware scheduler 最大化 KV 命中率
Cortex预定义的 stage 划分每个 stage 独立 GPU 资源池，消除跨 stage 干扰
Halo多个 workflow 合并成 Query Plan DAG跨 workflow 找公共子表达式消除 + KV 共享

补充：MARS 在此基础上把 CPU tool execution 也纳入统一 admission control，防止 GPU+CPU 异构资源同时超额申请。

本质：调度粒度从 request → workflow，保持因果依赖链上的 KV 局部性。

4. 小集群方案：投机计算（方法 D）

方法 D：Tool 空闲里的投机计算

核心：没有其他请求可跑 → 空闲时间里提前计算未来可能需要的，观察回来后再决定用不用。
大集群：GPU 空闲 → 其他 request 填上（方法 C） 小集群：GPU 空闲 → 没有其他 request → 投机计算 next step（方法 D）

这个方向和大集群完全不同：不管理状态（KV 放哪），管理计算（GPU 有闲就算什么）。

本质上是对 CPU 分支预测和 speculative decoding 的思想在 agent 层面的应用——预测下一个 tool call 是什么，提前执行。

5. 算子层：CUDA Stream 怎么做数据传输-计算重叠

上三层管策略，这一层管实现

方法 B（主动 KV 搬迁）和方法 D（投机计算）需要在 GPU 上同时跑两件事：数据传输 和 计算。CUDA 的 copy engine 和 SM 是独立硬件，可以并行。

GPU Copy Engine: [KV D2H] .......... [KV H2D] .......... [KV D2H] .......... GPU SM (compute): [decode] [投机计算] [decode] [投机计算] [decode] [投机计算] ... ↑ 两条 hardware pipeline 独立运行 ↑

SGLang 的 Two-Batch Overlap (TBO)

源码 batch_overlap/two_batch_overlap.py 和 operations.py：把一个 batch 拆成两个 sub-batch，用 execute_overlapped_operations 错开 delta 个 stage 交错执行。

Sub-batch A: [stage 1] [stage 2] [stage 3] [stage 4] Sub-batch B: [stage 1] [stage 2] [stage 3] [stage 4] ↑ delta=1，B 比 A 晚一个 stage 开始 A 的 compute 和 B 的数据准备重叠

但对 agent 场景，TBO 是通用优化——它不区分 "这是 tool call 间隙"，只是让任意两个 batch 的计算和数据准备重叠。

KV 搬迁的 Pipeline 重叠

KVDrive（2605.18071）直接解决了这个问题。它把 decode pipeline 拆成三个阶段并流水线化：

Time → Stage 1: [I/O: fetch KV N] [I/O: fetch KV N+1] [I/O: fetch KV N+2] Stage 2: [Transfer N to GPU] [Transfer N+1] [Transfer N+2] Stage 3: [Compute decode N] [Compute decode N+1] [Compute decode N+2] ↑ 三个 stage 流水线，互不阻塞 ↑

对 agent tool calling：tool 返回后需要 prefill 大段 tool result → KVDrive 把 prefill 的 KV fetch 和 transfer 作为前两个 stage，和已有 decode compute 重叠。

HillInfer（2602.18750）针对边缘设备：KV cache 跨 GPU/CPU/SmartSSD 三层，自适应预取 pipeline 重叠计算和数据传输。

PipeMax（2605.02189）：pipeline parallelism 让每张 GPU 一次只跑一个 batch 的 active 部分，其余 KV 卸载到 CPU。协调计算和搬迁的时序来扩大有效 batch size。

Agent 场景的完整 Stream 规划

把 B + D + 算子重叠拼在一起，一个单 GPU 部署的 agent 在 tool 执行期间的完整时间线：

Default Stream (SM): [decode] [投机 plan] [投机 plan] [投机 plan] [合并结果→decode] Copy Engine (DMA): [KV→CPU] [KV←CPU prefetch] CPU (tool): [tool exec..............................] tool returns

没有 CUDA stream 重叠：投机计算和 KV 搬迁依次串行 → 气泡变大。

有 CUDA stream 重叠：KV 搬迁走 copy engine，投机计算走 SM，两者并行 → 零开销。

和 vLLM/SGLang 现状对比：当前引擎不知道 "tool call 开始了"，所以也不会启动 KV 搬迁和投机计算的 stream pipeline——气泡就这么空着。

6. 已被现有引擎覆盖的方法

Stateful Inference（2605.26289）：核心是 "KV-cache 跨 turn persistent + 只 prefill 增量 token"。SGLang RadixAttention 已经做到了前缀复用，这篇文章只是强调 agent 自身多轮之间的连续性——不是一个新方法。

7. 方法关系与叠加

方法 A (淘汰决策) 方法 B (KV 搬迁) 方法 C (workflow 调度) ───────────────────── ───────────────────── ───────────────────── 作用层：KV-cache 管理器 作用层：内存 hierarchy 管理 作用层：调度器 输出： 淘汰/保留 输出： GPU↔CPU 搬迁指令 输出： 哪个 GPU 跑哪个 req 可以叠加： A+B：先用 A 决定保留哪些 KV，再用 B 把保留的搬到 CPU B+C：C 把同 workflow 放同 GPU，B 在 tool 间隙搬迁 A+C：C 保证同 workflow 的 KV 在一台机器上，A 决定在这台机器上淘汰谁

Active-Recall Checkpoint

  1. 方法 A 和 D 的区别是什么？为什么说 A 是"管态"、D 是"管计算"？
  2. 小集群为什么不需要 A/B，但非常需要 D？反过来，大集群为什么 D 的价值有限？
  3. PASTE 的"控制流模式挖掘"和 IdleSpec 的"两种 draft 策略"本质区别是什么？
  4. 如果把 D 的投机 tool call 做错了（预测了错误的 tool，已经执行了），会产生什么副作用？B-PASTE 怎么解决这个问题？

Transfer Task

选一个你关心的 agent 场景（比如 SWE-bench 的 code fix agent），设计一个小集群（1 GPU）方案：

  1. 画出你的 agent 的典型 tool call 序列
  2. 哪些 tool 之间可能存在投机空间？（提示：file_read → search 有依赖吗？test → fix 呢？）
  3. 画投机执行的时间线对比无优化版本
  4. 如果投机预测错了，代价是什么？在你的场景里能接受吗？
