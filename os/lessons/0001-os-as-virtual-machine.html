1. 故事的起点：一个根本矛盾

一台计算机有一块物理 CPU、一块物理内存、一块物理磁盘。但你打开 100 个程序， 每个程序都以为自己独占整台机器——printf("%p", &x) 打印出来的地址 和其他程序的不冲突，while(1) 不会永远霸占 CPU，文件保存在"桌面"上 而不是柱面 372 扇区 18。

把硬件直接暴露给程序，会立刻撞上三堵墙：

硬件裸用的问题

资源问题后果
CPU只有一个/几个核，所有程序都要跑没有调度 → 一个死循环霸占一切；没有抢占 → 一个程序可以永远不让出 CPU
内存物理上只有一块连续空间程序 A 可能读到程序 B 的密码；程序链接的地址可能冲突；碎片让 4G 空闲但装不下一个 2G 程序
磁盘物理上是一堆扇区，数据分布无规则用户需要记住"我的 data 在柱面 57 扇区 1082"；误写一个扇区可以毁掉整个文件系统

OS 的存在就是为了解决这三个问题——它不是"计算机的附加组件"，而是计算机不可用的前提。没有 OS，硬件只是一堆硅。

而解决这三个问题的策略，出奇地统一：

$$\text{OS 的策略} = \text{在硬件之上加一层间接，制造三个"幻象"}$$
OS 不暴露硬件，OS 暴露幻象。 给每个进程一个虚拟 CPU、一片虚拟地址空间、一套虚拟文件系统。 三个幻象各自需要：一个数据结构记录"虚拟 ↔ 物理"的映射，一套规则规定"何时切映射"。 这样想 OS 的话，后面所有课都是一个套路的展开。

2. 三条幻象：OS 制造的三个"谎言"

核心隐喻

操作系统作为虚拟机器

Virtual Machine · Illusionist
本质：OS = 一个把一台物理机映射成 N 台虚拟机的程序。每个进程活在它自己的虚拟机里——有自己的虚拟 CPU（时间片）、虚拟内存（地址空间）、虚拟磁盘（文件系统）。进程永远不会"看见"真实硬件。

三条幻象对应的问题和解法

幻象解决什么问题核心机制展开于
CPU 虚拟化每个进程以为独占 CPU上下文切换 + 调度0002
内存虚拟化每个进程以为独占 0x0 → 0xFFFF…页表 + TLB + 缺页处理0003, 0004
I/O 虚拟化每个进程以为有一棵整洁的文件树inode + 文件描述符 + 块层0007, 0008
→ 0002: CPU 幻象的具体机制 → 0003: 内存幻象的具体机制 → 0007: I/O 幻象的具体机制

2.1 CPU 虚拟化：时分复用制造的幻象

物理上只有 $N$ 个核，但有 $M \gg N$ 个进程想跑。OS 的解法是时分复用—— 为每个进程分配一小段时间片（time slice），时间到了就切走。

切换的频率是多少？以 Linux CFS 为例：

  • 典型时间片：1–20ms（取决于 `sched_latency` 和进程数）
  • 上下文切换开销：~1–10μs（保存/恢复寄存器、切换页表、刷新 TLB 的部分内容）
  • 开销占比：通常 < 0.1%（1μs / 1000μs = 0.1%）——小而可接受的代价

从进程视角，它不知道也不关心自己什么时候被切走——它只看到自己的指令一条条执行。这就是 CPU 幻象。

停下来想一想：如果上下文切换的开销是 10μs、时间片是 1ms，那么 CPU 用于"切换"而非"干活"的比例是多少？如果把时间片缩到 10μs 会怎样？

2.2 内存虚拟化：地址翻译制造的幻象

每个进程的地址都从 0x0 开始（严格说是从 ELF 加载地址开始）， 仿佛整片物理内存都是它的。但实际上：

  • 物理内存是所有进程共享的——OS 把物理页框（frame）分配给各进程的虚拟页
  • 每个进程有自己的页表——虚拟页号 → 物理帧号的映射字典
  • CPU 里的 MMU（Memory Management Unit） 在每次访存时自动查页表翻译地址
  • 进程 A 的 0x7fff0000 和进程 B 的 0x7fff0000 映射到完全不同的物理地址——隔离由此而生
$$\underbrace{\text{虚拟地址}}_{\text{进程看到的}} \;\xrightarrow{\text{MMU + 页表}}\; \underbrace{\text{物理地址}}_{\text{硬件用的}}$$

这个映射不仅隔离进程，还带来了三个超级能力——后面 0003–0004 会深入：

  1. 按需调页（demand paging）：不到用时不给物理帧——可以跑比物理内存大的程序
  2. 写时复制（copy-on-write）：`fork()` 不真的复制——父子共享页直到有人写
  3. 内存映射文件（mmap）：把文件映射到虚拟地址——read/write 退化为指针操作

2.3 I/O 虚拟化：文件抽象制造的幻象

硬盘是柱面/磁头/扇区的几何结构，SSD 是块/页/擦除单元的半导体迷宫。 但程序看到的是 /home/user/report.txt——一棵目录树，每个文件可读可写可定位。

这个幻象的核心机制是层层抽象：

I/O 虚拟化的抽象层次（从高到低）

文件描述符（fd）——进程看到的整数句柄（0 = stdin, 1 = stdout, 2 = stderr） 内核为每个进程维护一个打开文件表 `files_struct`，fd 是数组下标
inode——文件的"身份证"，包含权限/大小/数据块指针，唯独没有文件名 文件名存在目录项（dentry）里——目录本质是"名字→inode号"的映射表
块层（block layer）——把 inode 的块号翻译成设备 I/O 请求 合并相邻请求、排序以减少磁头移动（电梯算法）
设备驱动——把 I/O 请求翻译成硬件寄存器操作 驱动是唯一知道硬件具体协议的代码

这一套抽象让"把 `fd` 改成指向另一个文件"成为一个原子操作（`dup2`），让网络 socket 和普通文件可以统一用 `read`/`write`（Unix 的"一切皆文件"哲学）。

3. 机制/策略分离：OS 设计第一原则

第一原则

机制与策略分离 · Separation of Mechanism and Policy

Mechanism/Policy Split
本质："怎么做"（机制）和"选哪个"（策略）解耦。机制留在内核（因为需要特权指令），策略可以根据场景换——不必改内核代码。

OS 中反复出现的例子

领域机制（内核提供）策略（可换）课次
CPU 调度上下文切换、就绪队列哪个进程得到 CPU、多长时间0002
页替换缺页中断、页表操作换出哪一页（LRU? 时钟?）0004
I/O 调度请求队列、DMA 发起请求的先后顺序0008
文件系统inode 操作、块分配布局策略（ext4? btrfs?）0007
→ 0002: 调度策略可换不改机制 → 0004: clock vs LRU 都是同一个缺页机制上的策略 → 0008: elevator vs deadline 都是同一个请求队列机制

这个原则为什么是"第一"？因为 OS 是长期运行的基础设施——内核一旦写定，上层应用千变万化。 如果每次换个调度算法都要改内核代码，OS 就没法稳定。机制/策略分离让内核提供稳定基元（上下文切换、页表操作、I/O 请求），让策略作为可替换模块存在。

一个经典反例：早期 Unix 的调度器直接把优先级算法硬编码在内核里，后来要换 CFS 时不得不大规模重构。而 Linux 2.6+ 的调度类（scheduling class）设计——`SCHED_NORMAL`（CFS）、`SCHED_FIFO`、`SCHED_RR`、`SCHED_DEADLINE` 等并存——正是机制/策略分离的胜利。

范式 #5 · 机制/策略分离

这一招为什么管用：把"必然的代价"（上下文切换需要修改硬件状态、缺页需要操纵页表——非特权指令不可）和"可变的选择"（谁先跑、谁被换出——无绝对对错）分开。内核付代价，用户做选择。

还在哪里出现：调度（0002）、页替换（0004）、I/O 调度（0008）、安全策略（0009 的 seL4 capability）

4. 保护模型：幻象需要围墙

三条幻象有一个前提：进程不能戳破别人的幻象。进程 A 不能改进程 B 的页表， 不能直接写硬盘绕过文件系统，不能让 CPU 永远不切走。

OS 用硬件支持的两级特权来实现这个隔离：

硬件基础

用户态与内核态 · User Mode vs Kernel Mode

Ring 3 vs Ring 0 · CPL · 特权级
本质：CPU 在某个寄存器里存了当前特权级（x86: CPL，存在 CS 寄存器的低 2 bit）。某些指令（`lgdt`、`lidt`、`hlt`、`in`/`out`、改 CR3……）只在 Ring 0 可用。用户态代码执行这些指令 → CPU 抛异常。

两种态的对比

用户态（Ring 3）内核态（Ring 0）
能访问的内存自己的虚拟地址空间全部物理内存 + 所有进程的页表
能执行的指令普通运算/访存/系统调用特权指令（I/O、MMU 配置、中断控制）
运行什么代码应用程序OS 内核
出错了怎么办进程被杀（segfault）内核 panic（整机重启）

4.1 系统调用：从 Ring 3 进入 Ring 0 的唯一合法入口

用户程序需要 I/O、分配内存、创建进程——这些都要内核帮忙。但用户程序不能随便跳到内核态（否则保护形同虚设）。OS 的设计是：

  • 内核事先在中断描述符表（IDT / Interrupt Descriptor Table）里注册好各系统调用的入口地址
  • 用户程序执行 syscall（x86-64）或 int 0x80（x86 旧版）——触发软件中断
  • CPU 硬件自动：切换到 Ring 0、保存用户态寄存器到内核栈、跳到 IDT 里注册的入口
  • 内核处理完，执行 sysret（或 iret）恢复用户态继续执行

系统调用 ≠ 普通函数调用。普通函数调用只是 `call` 指令（改 RIP + 压栈），几十个 CPU 周期。系统调用涉及 Ring 切换、寄存器全保存、页表切换（可能）、TLB 刷新（可能），代价 100–1000+ 周期。这就是为什么 gettimeofday 这类高频调用在 Linux 上通过 vDSO（虚拟动态共享对象）映射到用户态——避免真的陷入内核。

5. 并发作为根本挑战：幻象的裂缝

三条幻象都假设了某种"原子性"——上下文切换应该对进程透明。 但现实是 OS 本身就是一个并发系统：中断随时到来，多个进程同时在跑（多核）， OS 内核代码本身也可能被中断打断。

这就是 OS 设计和应用程序设计最大的不同：

应用程序假设自己控制一切。OS 内核不能做这个假设。 CPU 在任何时刻都可能触发中断，跳到中断处理程序——而中断处理程序可能修改 正在被当前代码访问的数据结构。并发不是"我选择用多线程"的设计决定——它是物理事实。

5.1 中断：并发的物理根源

一个典型场景：内核正在遍历进程链表（`for (p = procs; p; p = p->next)`），时钟中断来了：

  1. CPU 暂停当前内核代码
  2. 跳到时钟中断处理程序 → 发现当前进程时间片用完了 → 调用 `scheduler()`
  3. `scheduler()` 修改进程链表（把一个进程移到队尾）
  4. 中断返回 → 原来的遍历代码继续跑——但链表已经被改了！`p->next` 可能指向被移除的节点

这就是竞态条件（race condition）的根源。解决方法（锁、信号量、RCU）在 0005–0006 展开。

5.2 并发倒逼的设计决策

正是因为并发是物理事实，OS 设计中有很多看似奇怪的选择其实是为了并发正确性：

  • 为什么 `fork()` 不真的复制全部内存？不只因为慢——复制过程中中断可能改原进程的内存，导致复制版不一致。COW 用只读共享 + 缺页时复制来保证原子性（0004）。
  • 为什么内核栈通常很小（Linux 默认 16KB）？不只是省内存——每进程有自己的内核栈，中断处理复用被中断进程的内核栈。栈小了上下文切换快。
  • 为什么系统调用中一般不能 sleep？持锁时睡眠 = 死锁邀请函。`copy_to_user` 可能因缺页而阻塞——这是内核里少数可以合法睡眠的地方，但它不持锁。
停下来想一想：单核 CPU 上需要锁吗？时钟中断不能打断当前指令，但可以打断两条指令之间。所以单核也需要锁——只是锁的方式不同（关中断就够了，不需要原子指令）。

6. 六大设计范式：OS 的"元技巧"

ML 课程有"推导范式"——配平方、Jensen、Woodbury、拉格朗日对偶。 OS 也有自己的"设计范式"——理解这些范式，你就不是学"100 个机制"而是学"6 个想法在不同场景的 100 次应用"。 本课给出全景，后续每课在 `.meta-box` 中标注"范式 #N"。

范式 #1 · 间接层（Indirection）

一句话："任何计算机科学问题都可以加一个间接层解决——除了间接层太多的问题。"在硬件和程序之间插一层映射，解耦"程序看到的东西"和"物理存在的东西"。

OS 中的体现：虚拟地址（映射到物理帧）、文件描述符（映射到 inode）、inode 号（映射到数据块）、进程 ID（映射到 PCB）、socket（映射到网络连接）。

出现的课：0001（本课）、0003（页表）、0007（inode）、0009（容器的 namespace 隔离）

范式 #2 · 缓存（Caching）

一句话："刚用过的东西很可能马上再用。"在快速介质上存慢速介质的子集，用局部性原理让大多数访问命中缓存。

OS 中的体现：TLB（页表缓存）、buffer cache（磁盘块缓存）、dentry cache（目录项缓存）、inode cache、CPU cache（硬件但 OS 配合——调度时考虑 cache affinity）。

出现的课：0003（TLB）、0007（buffer cache）、0008（存储层次就是缓存层次）

范式 #3 · 惰性求值（Lazy Evaluation）

一句话："不到非做不可就先不做。"推迟工作到真正需要时，用"不做"换取性能。

OS 中的体现：按需调页（不真的分物理帧直到访问）、写时复制（不真的复制直到写入）、惰性分配（`malloc(1GB)` 不真的给物理内存直到用到）、RCU（不真的释放旧版本直到所有读者完成）。

出现的课：0004（COW、demand paging）、0006（RCU）、0007（COW 文件系统）

范式 #4 · 批处理（Batching）

一句话："把小的攒成大的，一次搞定均摊开销。"利用固定开销可以被均摊的性质。

OS 中的体现：I/O 合并（电梯算法把相邻请求合并成一次磁盘操作）、中断合并（网卡攒多个包再中断一次）、组调度（把一组线程一起调度减少切换次数）、写回缓存（攒多个写操作一次刷盘）。

出现的课：0002（组调度）、0008（I/O 合并、中断合并）

范式 #5 · 机制/策略分离（Mechanism/Policy Split）

一句话："怎么做"和"选哪个"解耦。已在 §3 详述。

出现的课：0002（调度）、0004（页替换）、0008（I/O 调度）、0009（seL4 capability 访问控制）

范式 #6 · 硬件-软件协同（HW-SW Co-design）

一句话：硬件提供"又快又蠢"的基元，软件用这些基元构建"慢但聪明"的策略。硬件只做非它不可的事——剩下的留给 OS。

OS 中的体现：MMU 只管页表翻译（硬件不决定换哪页——那是 OS 的策略）、原子指令给 CAS（硬件不决定临界区多长——那是软件的权力）、中断控制器只管分发中断（不决定优先级——那是 OS 的策略）。CPU 给 Ring 0/3、页表结构、中断机制——OS 用它们构建整个幻象世界。

出现的课：0002（中断+上下文切换）、0003（MMU+页表）、0005（CAS+锁）、0010（VMX/SVM 虚拟化扩展）

这六个范式不是彼此独立的——它们在每个 OS 子系统中同时出现。 以页表为例：它是间接层（范式 #1，虚拟→物理），它背后有 TLB（范式 #2，缓存）， 缺页处理是惰性求值（范式 #3），TLB shootdown 是批量（范式 #4）， 页替换算法是机制/策略分离（范式 #5），MMU 硬件和 OS 的配合是 HW-SW 协同（范式 #6）。 六个范式在同一机制上的六重奏——这就是操作系统之美。

7. 自测

Q1 · 三条幻象共同依赖的基础设施是什么？

✓ 正确。三条幻象（CPU/内存/I/O）都是通过间接层实现的：CPU 幻象靠进程状态和调度（间接使用物理 CPU）、内存幻象靠页表（虚拟地址映射到物理地址）、I/O 幻象靠文件描述符和 inode（文件名映射到磁盘块）。间接层是全书第一范式。
✗ 再想想。提示：哪样东西让 CPU 虚拟化、内存虚拟化和 I/O 虚拟化都有了可能？

Q2 · 机制/策略分离的核心价值是什么？

✓ 正确。内核是长期运行的基础设施，不能因策略变化而频繁改动。机制/策略分离让内核提供"怎么做"的稳定基元（上下文切换、页表操作），策略作为可替换模块存在。Linux 的调度类（CFS/RT/DEADLINE 共存）是典范。
✗ 再想想。提示：OS 内核写完了就不能随便改，但调度偏好因人而异。

Q3 · 为什么单核 CPU 也需要锁？

✓ 正确。单核上时钟中断可以在任意两条指令之间到来。如果内核正在修改进程链表而中断处理程序也修改它，就会产生竞态条件。单核的解法是关中断（禁用中断），但这只对单核有效——多核还需要原子指令。
✗ 再想想。提示：中断什么时候可以发生？被打断的代码执行到一半会怎样？

Q4 · 以下哪项不是系统调用？

✓ 正确。`printf` 是 libc 库函数，不是系统调用。它内部会调用 `write`（这才是系统调用），但 `printf` 本身只在用户态运行——做格式化、缓冲等工作。类似地，`malloc` 也不是系统调用——它管理用户态堆，只在不够时调 `brk`/`mmap`。
✗ 再想想。提示：这个函数在格式化字符串——格式化发生在哪一层？

8. 推导/追踪题

P1 · 上下文切换代价估算 L1 基础

假设一次上下文切换需要保存/恢复 40 个通用寄存器（每寄存器 8 字节）、切换页表（写 CR3 寄存器 ~200 cycles）、TLB 部分刷新（~100 cycles 额外开销）。CPU 频率 3 GHz，时间片 2 ms。

（a）计算一次上下文切换需要的总 cycles 数（假设每条寄存器 save/restore 指令 1 cycle，load + store = 2 cycles per register）。

（b）上下文切换开销占 CPU 时间的百分比。

（c）如果缩短时间片到 0.1 ms 以改善响应时间，开销占比变为多少？这意味着什么？

▸ 提示
(a) 寄存器 save（load 从寄存器到内存）+ restore（store 从内存到寄存器）= 2 × 40 = 80 cycles。加上 CR3 写 200 + TLB 100 = 380 cycles。@ 3 GHz, 1 cycle = 1/3 ns。(b) 380 / (2ms 中的 cycles) × 100%。(c) 重新计算并思考：时间片能不能无限缩小？
▸ 完整解答
(a) 寄存器 40 个 × 2（save + restore）= 80 cycles。CR3 写 = 200 cycles。TLB 刷新开销 ≈ 100 cycles。总计 ≈ 380 cycles。@ 3 GHz，380 cycles = 380/3 ns ≈ 127 ns。实际 Linux 上下文切换约 1–5 μs，因为还有 cache 污染、调度算法决策、FPU/向量寄存器保存等额外开销。这里只估了最基础的。
(b) 2ms = 2,000,000 ns = 6,000,000 cycles @ 3 GHz。开销占比 = 380 / 6,000,000 ≈ 0.0063%。几乎为零——这也是为什么 OS 可以安心用时分复用。
(c) 0.1 ms = 100,000 ns = 300,000 cycles。开销占比 = 380 / 300,000 ≈ 0.127%。仍然很小，但趋势明确：时间片越来越小 → 开销比例越来越大 → 系统越来越"忙着切换而非干活"。这就是为什么时间片有个下限（Linux 默认最小粒度约 1ms）。范式 #4（批处理）的体现——时间片太小 = 批太小 = 固定开销不能被均摊。
P2 · 设计一个 FIFO 页替换器 L1 基础

给定物理内存 3 帧（frame），页引用串：1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5。用 FIFO 替换策略，按步骤列出每次访问后的内存状态，统计缺页次数。（此题为 0004 预热）

▸ 提示
维护一个队列。当需要替换时，换出队头（最早进来的）。每步问自己：这页已经在内存里了吗？在 → 命中，不动队列。不在 → 缺页，加入队列队尾，如果满了则弹出队头。
▸ 完整解答
初始：[]（空）
1: [1] ← 缺页（1）
2: [1,2] ← 缺页（2）
3: [1,2,3] ← 缺页（3）
4: [2,3,4] ← 缺页（4）换出 1
1: [3,4,1] ← 缺页（5）换出 2
2: [4,1,2] ← 缺页（6）换出 3
5: [1,2,5] ← 缺页（7）换出 4
1: [1,2,5] ← 命中
2: [1,2,5] ← 命中
3: [2,5,3] ← 缺页（8）换出 1
4: [5,3,4] ← 缺页（9）换出 2
5: [5,3,4] ← 命中
共 9 次缺页。12 次访问中 3 次命中，命中率仅 25%。注意：如果给 4 帧而非 3 帧，FIFO 反而可能有更多缺页——这是著名的 Belady 异常（0004 §3 详讲）。
P3 · 伪代码中的竞态条件 L2 理解

两个线程并发执行以下伪代码（`balance` 初始为 1000）：

Thread A:                          Thread B:
1:  r1 = balance                    1:  r2 = balance
2:  r1 = r1 + 100                   2:  r2 = r2 - 50
3:  balance = r1                    3:  balance = r2

（a）列出至少 3 种不同的最终 `balance` 值以及对应的指令交错顺序。

（b）要使最终值正确（1050），需要怎么约束指令交错顺序？这个约束在真实硬件上能自动满足吗？

（c）如果用 x86 的 `LOCK XADD` 指令替换这三步，能解决吗？代价是什么？

▸ 提示
(a) 两个线程各自有 3 条指令，总共 6 条。但它们是流水线式的——试列出 A 先完整执行、B 先完整执行、A 和 B 在第一条和第二条之间交错的情况。(b) 正确结果要求 A 的读-改-写完整发生在 B 的读-改-写之前或之后——即两个临界区不重叠。(c) LOCK XADD 把"读-改-写"变成一个不可分割的原子操作。
▸ 完整解答
(a) 三种结果：
1050（正确）：A 完整执行（1000→1100），然后 B 完整执行（1100→1050）。或反过来 B 完整执行（1000→950），然后 A 完整执行（950→1050）。两个临界区不重叠。
1100（丢失 B 的 -50）：A1→A2→B1→B2→A3→B3。A 读到 1000 并算好 1100，B 读到 1000 并算好 950。A 先写 1100，然后 B 写 950 覆盖了 A 的写入，但 B 是基于 1000 算的 950——A 的 +100 丢失。最终是 B 的写入赢——但 B 是基于"旧值"1000 算的。
950（丢失 A 的 +100）：B1→B2→B3→A1→A2→A3，或 A1→B1→B2→B3→A2→A3（A 读到 1000 时 B 还没写但 A 写完 B 已覆盖）。最终 A 写 1100 覆盖 B 的 950 但 A 基于旧值 1000。
(b) 正确结果要求 A 的三步完整发生在 B 的三步之前或之后——即 A 的读和 B 的写之间没有交错。真实硬件无法自动满足——中断随时到来，多核上线程真的在同时执行。这正是"临界区"概念的动机（0005）。
(c) `LOCK XADD balance, 100` 能解决——它把读-改-写变成一个不可分割的总线事务。代价：(i) 锁总线或锁 cache line（其他核不能同时访问）；(ii) 只能做简单运算（加法），不能像上面那样做任意复杂操作。更复杂的临界区需要锁（0005 §3-4）。
P4 · 间接层的代价 L2 理解

范式 #1（间接层）是全书最核心的设计模式。但它不是免费的。

（a）举出至少两个"间接层增加了延迟"的具体例子，量化估算增加的延迟量级（大概数量级即可）。

（b）举出至少一个"间接层增加了空间开销"的例子。

（c）为什么 OS 仍然选择加间接层而非直接暴露硬件？——从"灵活性和性能的 tradeoff"角度回答。

▸ 提示
(a) 每次访存都要经过页表翻译——这是间接层。TLB 是缓解但未命中时多花 ~10-100 cycles。(b) 页表本身占内存——一个 4KB 页表可映射 2MB（二级）或 1GB（三级）。(c) 如果每个程序直接用物理地址——那换一个程序就必须重新链接？多程序怎么共存？
▸ 完整解答
(a) 两个增加延迟的例子：
① 页表翻译。每次访存都要先查页表。TLB 命中 → ~0.5-1 cycle 额外延迟（TLB 和 L1 cache 并行访问）。TLB 未命中 → 需要走页表（PMH/page miss handler）：二级页表 ~10 cycles，四级页表 ~40-100 cycles。极端情况（缺页）→ 磁盘 I/O ~10ms。TLB 命中率通常 > 99.9%，所以平均额外延迟很小（~1-2 cycles），但未命中路径很贵。如果没有虚拟内存（所有地址都是物理地址），每次访存就是 0 cycle 翻译开销——但丧失了隔离和所有内存虚拟化能力。
② 文件系统路径解析。`open("/a/b/c/d/file")` 内核需要逐级查找：读 inode of "/" → 在目录块里找 "a" 的 inode 号 → 读 a 的 inode → 找 "b" 的 inode 号 → ... 每一步都可能触发磁盘 I/O。无缓存时是 ~5 × 10ms = 50ms。dentry cache 把常用目录项缓存在内存里——大部分 `open` 不需要任何磁盘 I/O。如果没有目录树（所有文件用扇区号访问），用户需要记住每个文件的物理位置。
(b) 空间开销：页表本身占内存。每个进程有自己的四级页表：PGD（1页=4KB）→ PUD（1页=4KB）→ PMD（1页=4KB）→ PTE（每 2MB 区域需要 1 页 PTE）。一个 128TB 虚拟地址空间的进程完整页表需要 ~256GB……但实际通过"惰性分配"和"大页"只需几百 KB 到几十 MB。
(c) OS 选择间接层而非直接暴露的原因：直接暴露物理硬件 = 没有隔离（A 能读写 B 的内存）、没有灵活性（换一个文件系统需要改所有程序）、没有可移植性（程序绑定到特定硬件配置）。间接层的延迟和空间代价可以通过缓存（范式 #2）和惰性求值（范式 #3）来缓解——大部分时间你感受不到。但间接层带来的隔离和灵活性是物理硬件不可能给的。OS 的设计哲学不是"消除间接层的代价"，而是"让代价小到不可感知，换来不可替代的能力"。
P5 · 机制/策略分离的反例分析 L3 进阶

考虑 Linux 的 OOM Killer（Out-Of-Memory Killer）——当系统内存耗尽时，内核选择一个进程杀掉以回收内存。

（a）分析当前 OOM Killer 的设计：机制是什么？策略是什么？它们分离了吗？

（b）如果让你严格遵守机制/策略分离原则重新设计 OOM Killer，你会怎么拆分？用户态需要什么信息来做决策？

（c）这个案例揭示了机制/策略分离的什么局限？什么情况下把策略放在内核里反而更好？

▸ 提示
(a) Linux OOM Killer 的策略是用启发式打分（`oom_badness()`）选择受害者——策略在内核里。(b) 内核可以提供"哪些进程用了多少内存"的信息和"请杀掉 PID X"的接口，让用户态守护进程做决策。(c) 但是——如果系统内存已经没了，用户态守护进程自己也可能被换出或无法分配内存来运行。这时候谁来杀？
▸ 完整解答
(a) 当前的机制/策略混合：机制——内核检测到内存分配失败后进入 OOM 路径（`out_of_memory()`），遍历进程打分（`oom_badness()`），发送 SIGKILL。策略——打分函数 `oom_badness()` 的逻辑：看 RSS、看 swap 使用、看 `oom_score_adj`（用户可调）、优先杀子进程多的、`CAP_SYS_ADMIN` 的进程打折扣……策略硬编码在内核里。而且打分逻辑的版本间变化很大——这正是策略不该在内核里的信号。
(b) 严格分离的设计：机制（内核提供）：(i) 触发条件——内存分配失败时暂停分配者，不杀任何进程；(ii) 信息接口——`/proc/oom/candidates` 列出所有进程及其内存统计；(iii) 操作接口——`/proc/oom/kill` 接受 PID，内核杀掉该进程。策略（用户态守护进程 oomd）：读候选列表 → 按自己策略打分 → 选最低分的杀。这样不同的工作负载可以用完全不同的 OOM 策略而不改内核。
(c) 这个案例揭示的局限：当系统已内存耗尽——用户态守护进程需要分配内存来运行（读 /proc 需要分配 buffer、做决策需要栈空间），但这正是问题所在：没有内存了。而且如果守护进程被换出——换入需要内存。如果 OOM 由死锁引起且守护进程被牵连——它永远无法做出决策。这是 emergency path 悖论：当系统在最坏情况下，机制/策略分离的"用户态做策略"恰恰不可用。

所以 OOM Killer 的策略确实部分留在内核里——不是违反原则，而是紧急情况下你不能信任用户态。类似的例子还有内核 panic 处理——不能依赖用户态。机制/策略分离是指导原则而非教条，紧急路径是合法的例外。
P6 · 设计一个微缩 OS L3 进阶

本课建立了 OS 的六大范式。现在把它们用到极致：

设计一个极简 OS，它只跑一种程序——每秒从传感器读一个数，和上一个数比较，如果差值大于阈值就报警。这个 OS 必须提供：(i) 虚拟 CPU（让程序以为独占 CPU），(ii) 虚拟内存（保护内核不被程序破坏），(iii) 虚拟 I/O（程序通过文件接口读写传感器数据）。

（a）用六大范式逐一分析：这个极简 OS 中哪些范式必须实现？哪些可以省略？

（b）画出程序发起一次 `read(sensor_fd)` 到数据返回的完整代码路径——从用户态到内核态再到硬件再返回。

（c）如果这个 OS 要支持两个程序同时跑（一个读传感器、一个写日志），你需要增加哪些机制？哪些范式从"可选"变成"必须"？

▸ 提示
(a) 范式 #1（间接层）是三条幻象的基础——必须。范式 #2（缓存）：只有一个程序，缓存可能不需要。范式 #5（机制/策略分离）：只有一个程序 = 只有一个调度策略（"总是跑它"），不需要分离。(b) 类比本课 §4.1 的系统调用追踪，但简化——没有 VFS 层，直接读传感器。(c) 两个程序 = 需要调度、需要内存隔离（两个地址空间）、需要 I/O 互斥（传感器是共享资源）。
▸ 完整解答
(a) 范式分析：
范式 #1（间接层）——必须。虚拟 CPU：进程状态结构（PCB）记录"程序当前执行到哪"，时钟中断到来时保存上下文。虚拟内存：至少一个简单的页表（或者基址-界限寄存器），让程序不能写内核内存。虚拟 I/O：文件描述符映射到传感器设备。
范式 #2（缓存）——可省略。单程序场景，缓存不会提升性能（没有竞争），反而增加复杂度。但如果传感器读数很慢且程序可能多次读同一数据块，一个简单的 buffer cache 可以避免重复硬件读取。
范式 #3（惰性求值）——可省略大部分。单程序不需要 COW。但按需调页可能有用——如果程序代码很大（不用一次全加载到内存）。
范式 #4（批处理）——可省略。没有多个 I/O 请求可以合并。
范式 #5（机制/策略分离）——可省略。只有一个程序 = 调度策略"总是跑它"，不需要替换。但把上下文切换机制和"下一个跑谁"分开的代码结构仍然有利于后面扩展。
范式 #6（HW-SW 协同）——必须。需要时钟硬件发中断（实现 CPU 虚拟化）、需要 MMU 或至少 MPU（内存保护单元——ARM Cortex-M 的轻量版）、需要中断控制器区分传感器中断和时钟中断。
(b) read(sensor_fd) 的代码路径：
用户态：`read(3, buf, 8)` → libc → `syscall` → 硬件切换 Ring、压栈、跳 `trap_handler`
内核 `trap_handler`：保存寄存器 → 查系统调用表 [`SYS_read`] → `sys_read(fd=3, buf, 8)`
`sys_read`：从 `current->files[3]` 找到 `file` 结构 → `file->f_op->read`（传感器驱动）
传感器驱动：写传感器 I/O 端口（触发 ADC 转换）→ 忙等待或睡眠等中断 → 传感器中断返回数据 → 驱动把数据 `copy_to_user(buf)`
返回：`sys_read` 返回实际字节数 → `trap_handler` 恢复寄存器 → `sysret` → 用户态继续
(c) 支持两个程序需要增加的：
调度器（0002 的内容）——范式 #5 从可选变必须。需要决定谁跑、跑多久。最简单的：RR（轮流，各跑一个时间片）。需要两个 PCB。
两个独立的页表（0003）——范式 #1 扩展到第二个程序。上下文切换时必须切换页表（写 CR3），这让切换代价显著增加。
I/O 互斥（0005）——当一个传感器被两个程序共享时的新问题。读传感器的程序不能被打断（否则读数不一致）——需要一个锁。这是并发从"不存在"变为"核心问题"的时刻。
范式 #2（缓存）从可选变推荐：两个程序可能竞争传感器——缓存最近一次读数避免重复硬件访问。
总结：一个单程序 OS ≈ 硬件裸跑加一点点保护。多程序 OS 才是"真正的 OS"——六大范式全部从可选升级为必须。第二条路径（并发 0005-0006）此时从"理论上的挑战"变为"实际的必须品"。
