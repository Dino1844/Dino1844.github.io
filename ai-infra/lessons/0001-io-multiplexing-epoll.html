IO 多路复用与 epoll

为什么 epoll 比 select 快 — 推理 server 高并发的底座

这一节是 Phase 0 工程地基的第一块。它不是"AI"内容,但 vLLM 的 async engine、NCCL 通信、所有高并发推理 server 全建在这层之上。面试问"你 vLLM 里 ZMQ/TensorPipe 怎么用的",答不上来多半就是这层空。

1. 进程与 fd — 心智模型对齐

一个进程是内核眼里一组被隔离的资源:

进程 = { 地址空间 (代码/数据/堆/栈), ← 独享, 别人看不到 打开的文件描述符表 (fd table), ← 重点 一个或多个线程, PID, 权限, cwd ... }

Linux 的核心设计原则:一切皆文件。打开真文件、开 socket、开 pipe、开 /dev/null——内核都给你一个非负整数,叫文件描述符 (fd)。之后 read/write/close 全用这个整数。

fd 0 = stdin, 1 = stdout, 2 = stderr (默认开着) fd 3+ = 你 open/socket/pipe 出来的
面试常问"进程 vs 线程":进程切换要换地址空间(贵),线程切换只换栈和寄存器(便宜)。这就是为什么 vLLM 跨进程 tensor parallel 通信贵、同进程多线程便宜。

2. socket — 一种特殊的 fd

socket 是一个 fd,但两头连着网络或本机。TCP server 标准流程:

socket()  → 拿到 listen_fd
bind()    → 绑到 (ip, port)
listen()  → 标记"我是 server"
accept()  → 阻塞等连接, 返回新 fd = conn_fd
              ↑ 这个 fd 才用来 read/write 数据

关键坑:一个 server 同时有 N 个客户端,就有 1 个 listen_fd + N 个 conn_fd。你要同时盯这 N+1 个 fd:哪个来数据读哪个,哪个新连进来就 accept。
问题来了:怎么用一两个线程同时盯一堆 fd?

3. IO 多路复用 — 本节核心

3.1 最笨:一个线程一个连接

每个 conn_fd 开一个线程,各自阻塞 read()。1 万连接 = 1 万线程,内存爆 + 上下文切换爆。这就是早期 C10k 问题。

3.2 select — 第一个多路复用

int select(int nfds, fd_set *readfds, ...);
// 把要盯的 fd 塞进 bitmap, 阻塞到任一就绪, 返回。
// 然后你遍历 bitmap 看是哪个。

三个致命问题(面试必问):

  1. fd 数量有上限:典型 1024 (FD_SETSIZE),改要重编内核。
  2. 每次调用全量拷 fd 集合从用户态到内核态。N 大时贵。
  3. 返回后线性遍历找 ready fd,O(N)。

3.3 poll — 修了上限,没修本质

struct pollfd { int fd; short events; short revents; };
int poll(struct pollfd *fds, nfds_t nfds, int timeout);

用数组代替 bitmap,fd 数量没上限了。但问题 2、3 还在:仍全量拷、仍线性遍历。poll 也没解决 C10k。

3.4 epoll — Linux 的答案

epoll 把"盯哪些 fd"拆成两步:

int epfd = epoll_create1(0);               // 内核里建一个实例 (红黑树)

epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);    // 增量! 只在加/删时调
epoll_ctl(epfd, EPOLL_CTL_DEL, fd, ...);

epoll_wait(epfd, events, maxevents, -1);    // 阻塞, 只返回就绪的 fd
                  ↑ 不遍历全部, 只把就绪的拷出来
select / pollepoll
拷贝每次调用全量拷 fd 集合epoll_ctl 增量注册, 只在加删时调
找 ready fd线性遍历全部 O(N)只返回就绪的 O(就绪数)
fd 上限select 1024无
深层原因:epoll 在内核里给每个注册 fd 挂了回调。fd 上有数据到达,内核直接把它加进 ready list,不轮询。所以 epoll 是 O(1) 注册 + O(就绪数) 返回,与总 fd 数无关。

3.5 水平触发 vs 边沿触发(面试加分)

  • LT(水平触发,默认):fd 里只要还有未读数据,epoll_wait 就一直返回它。读不干净下次还提醒。安全,不易漏数据。
  • ET(边沿触发):只在状态从无到有变化那一次返回,之后哪怕还有数据也不提醒。性能更好(系统调用少),但必须循环 read 到 EAGAIN,否则数据卡住。nginx、Redis 用 ET。
本节 gate:能用自己的话讲清epoll 比 select 快的三个原因(增量注册 / 只返回就绪 / 无上限),并能解释 ET 模式下为什么必须循环 read 到 EAGAIN。下一节(0002)会用 Python selectors + C 裸 epoll 把这套机制写出来。

概念检查

Q1. 一个 server 有 1 万空闲连接,没数据在传。select 和 epoll 的 CPU 占用差别在哪?

Q2. 为什么说"select 是 O(N),epoll 是 O(就绪数)"?N 是什么?

Q3. ET 模式下你 read 一次读了 1024 字节,但对方发了 8KB。会发生什么?怎么避免?

答案(先自己想再展开)

Q1:空闲时都阻塞,几乎都没 CPU。差别在有事件时:select 要把 1 万 fd 全拷进内核 + 返回后线性扫 1 万个找是哪个;epoll 只返回那 1 个就绪的。空闲时都闲,有事件时 select 开销随连接数线性涨,epoll 不涨。

Q2:N = 注册的 fd 总数。select 返回后必须遍历所有 N 个 fd 检查 FD_ISSET;epoll_wait 直接把就绪的填进 events 数组,数量 = 就绪数,跟 N 无关。

Q3:ET 只在"从无到有"通知一次。读 1024 字节后缓冲区还有 7KB,但 epoll 不再通知 → 数据卡住,连接看起来 hang。避免:ET 下必须循环 read 直到返回 EAGAIN/EWOULDBLOCK,且 fd 设成非阻塞。
