1. 线程 vs 进程：共享什么、不共享什么

核心

线程 · Thread

线程是进程内的执行流。一个进程可以有多个线程，它们共享进程的"静态资源"（地址空间、文件描述符表、信号处理表、当前工作目录），但各自独立拥有"动态状态"（PC、寄存器、栈、栈指针、线程局部存储、信号掩码）。
图 1.1 · 同一进程的多线程：上方共享资源是一份，下方每线程独立自己的执行状态。栈必须独立——否则函数调用互相覆盖返回地址立刻崩溃。线程栈之间留 guard page（未映射），溢出踩到 → SIGSEGV 而非悄悄破坏邻居。
停下来想一想：线程切换比进程切换便宜，便宜在哪一步？
答案：进程切换要写 CR3（换页表根）→ TLB 全刷 → 后续访存全部 TLB miss 重新 walk 页表。线程切换不写 CR3，TLB 保留，cache 也大概率还有效（同一地址空间）。省下的不是"少存几个寄存器"——寄存器都要存——省下的是 TLB/cache 的冷启动代价。这就是 0002 §3 讲的"上下文切换真正的代价是 cache 污染"。

2. 线程的创建：clone() 与 pthread 的内核路径

用户态调 pthread_create，背后 glibc 的 NPTL 最终调一个系统调用——clone()。理解 clone 是理解"线程和进程在内核里其实是同一种东西"的钥匙。

统一

clone() · 进程和线程的同源

Linux 内核里没有"进程"和"线程"两种对象——只有 task_struct。fork() 和 pthread_create() 都调 clone()，区别只在传给 clone 的 flags：共享哪些资源。
图 2.1 · fork 与 pthread_create 走同一条 clone 路径，差别仅在 flags。内核不区分"进程对象"和"线程对象"——都是 task_struct，差别在它们共享了多少资源。

创建路径的四步：(1) glibc 用 mmap 分配线程栈 + guard page，设好 TLS 基址，然后调 clone；(2) 内核 copy_process 根据 flags 决定复制还是共享——CLONE_VM 不设就 COW 复制页表，设了就父子指向同一个 mm_struct；(3) copy_thread 把子线程的内核栈伪造好，设其返回点指向 ret_from_fork，这样它第一次被调度时就能回到用户态跑 fn(arg)；(4) wake_up_new_task 把新 task_struct 入 CFS 红黑树，等下次调度获得 CPU。

pid 命名陷阱。Linux 内核里 task_struct.pid 实际是"线程 ID"，task_struct.tgid 才是用户态看到的"进程 ID"。getpid() 返回 tgid，gettid() 返回 pid。主线程的 pid == tgid。这个命名是历史包袱，看内核代码时要时刻警惕。

3. 竞态条件：原子性的幻觉（指令级剖析）

0001 P3 的 balance = balance + 100 看起来是一条语句，但在 x86 上是三条机器指令：把 balance 从内存读进寄存器、在寄存器里加 100、把结果写回内存。这三条指令之间，任何时刻都可能发生线程切换（中断 → 调度）。两个线程各执行一次，关键看"读"和"写"之间是否插入了另一个线程的完整序列。

图 3.1 · "丢失更新"的本质：读和写之间插入了别人的读，导致两次加法都基于同一个旧值。

停下来想一想：如果 balance 是 int，两个线程各加 1 一百万次，最终值最坏是多少？
答案：最好 2,000,000（几乎不穿插）。最坏 2——所有线程都先读完 0，然后依次写 1、覆盖 1、覆盖 1……只要"读"全部发生在任何"写"之前。实际最坏值取决于穿插模式，但任何小于 2,000,000 的值都可能出现。这就是为什么"测试通过"毫无意义——竞态 bug 是概率性的，跑一万次可能只错一次。

3.1 竞态的四个必要条件

竞态发生需要四个条件同时满足，打断任何一个就消除竞态：

  1. 共享：两个线程访问同一变量
  2. 可变：至少一个是写
  3. 交错：访问不是原子的，中间能切换
  4. 无同步：没有锁/原子操作保护

解法对应四种思路：不共享（线程局部存储）、不可变（只读共享）、不交错（原子指令/锁）、加同步（本课主题）。本课聚焦后两种。

5. 锁的硬件基础：从关中断到 CAS 到 FAA

软件层面的锁最终都要落到硬件给的原子指令上——软件本身没有"原子地做两件事"的能力。原子指令的演进，每一种都是上一种的"还不够"：

原子指令演进链

① 关中断（单核·最简单）：进临界区前 cli，出去后 sti。单核上只要没中断就不会调度 → 临界区自然互斥。缺点：关中断期间 I/O 中断都丢失；用户态不能执行特权指令；多核上没用——另一核的线程不受本核 cli 影响。
② Test-and-Set (TAS)：原子地"返回旧值，写入 1"。用来造自旋锁：返回 1（被占）就继续转，返回 0（空闲，已写成 1）就拿到锁。
③ Compare-and-Swap (CAS) —— 更通用：原子地"若当前值 == 期望值 则写成新值并返回成功，否则返回失败"。CAS 比 TAS 通用——TAS 只能玩 0/1 flag，CAS 能做无锁栈、无锁队列、任意原子更新。x86 上是 LOCK CMPXCHG。
④ Fetch-and-Add (FAA)：原子地"返回旧值，写入 旧值+n"。用来做 ticket 自旋锁和原子计数器。
⑤ LL/SC（Load-Linked / Store-Conditional）：RISC 风格（ARM/MIPS/RISC-V）。LL 普通读，SC"若该地址自上次 LL 没被写过则写并成功，否则失败"。比 CAS 更基础，能构建双字 CAS。
停下来想一想：锁本身的实现需要原子指令——但谁来保护原子指令的原子性？
答案：硬件。LOCK 前缀在多核时锁住缓存行（通过 MESI 协议获取该 cache line 的独占权）——在这个原子操作完成前，其他核不能修改同一 cache line。早期实现锁总线——慢得多。现代 CPU 用 cache line lock，只影响该行。这是范式 #6（HW-SW 协同）的极致：原子指令是硬件给的、锁是软件造的、锁的语义是软件定的。

范式 #6 · HW-SW 协同（锁版）

硬件提供 LOCK CMPXCHG——一个原子地"比较并交换"的指令，只保证这一个 8-byte 操作不被打断。软件用它构建自旋锁、mutex、信号量、RCU、无锁栈。硬件不决定临界区多长、保护什么——那是软件的权力。分工：硬件给又快又蠢的原子砖，软件砌又慢但聪明的锁。

CAS 的"弱"在于它只比较值，不比较"身份"。如果值从 A → B → A，CAS 会以为"没变过"——这就是 ABA 问题，是 0006 无锁编程的核心难点。这里先埋下。

6. 自旋锁的演进：TAS → Ticket → MCS

自旋锁是最简单的锁，但"简单"的实现有性能陷阱。三种自旋锁，每一种都是上一种的"在竞争时不够好"。

图 6.1 · 三种自旋锁的等待方式。TAS：所有人挤在同一个字上抢，unlock 时 cache line 雪崩失效。Ticket：取号排队解决公平，但仍在共享字上等。MCS：每人等在自己的本地变量上，unlock 只唤醒链表下一个——只动一个 cache line。
自旋锁的使用准则：临界区必须极短（几 ns 到几 μs），且持锁期间不睡眠（不能调任何可能睡眠的函数）。原因：自旋时不让 CPU，如果持锁者被调度走，等锁者会空转整个时间片。内核里中断处理程序用的锁都是自旋锁，因为中断里不能睡眠。

7. 自旋锁 → mutex：从忙等到休眠

自旋锁在临界区长或可能睡眠时是灾难。mutex 解决"持锁者被切走"的问题——拿不到锁就让出 CPU 睡觉，持锁者释放时唤醒。

原语

Mutex · 互斥锁

拿不到锁 → 把自己挂入等待队列 → 调 schedule() 让出 CPU（睡眠）。持锁者 unlock 时唤醒等待队列中的一个线程。代价：两次上下文切换（切出 + 切回），但持锁期间不空耗 CPU。
图 7.1 · Mutex 的完整工作流。快路径：CAS 抢到锁直接返回。慢路径：CAS 失败 → 入等待队列 → 睡眠。unlock 唤醒队首，把锁"传递"给它（state 不归零，避免新来的插队）。

停下来想一想：临界区多长时该用自旋锁、多长时该用 mutex？
答案：临界区时间 T_cs 与一次上下文切换时间 T_ctx（约 1-5 μs）比较。T_cs < T_ctx → 自旋锁更优（睡眠+唤醒比直接转完还贵）。T_cs > T_ctx → mutex 更优（让出 CPU 给别人干活）。边界在 μs 量级——所以内核中断处理用自旋，用户态几乎都用 mutex。

8. 读写锁与 per-CPU 变量

8.1 读写锁（rwlock）

很多共享数据是读多写少——比如内核的进程列表、路由表。读不修改数据，多个读者同时读完全安全。用普通 mutex 会让读者互相串行——浪费。读写锁区分读模式和写模式：多个读者可同时持有读锁；写锁独占——有写者时不能有任何读者或其他写者；有读者时不能加写锁。

读写锁的饥饿陷阱。如果读者源源不断，写者永远等不到所有读者退出——写者饥饿。解决：写者到来时设"有写者在等"flag，新读者看到 flag 就不进入——让已有读者慢慢退出，写者进去。这牺牲一点读者吞吐换写者公平。Linux 的 rwsem 就处理了这个问题。

8.2 per-CPU 变量（免锁计数）

如果每个 CPU 只访问自己的计数器，就根本不需要锁。Linux 的 DEFINE_PER_CPU 给每个 CPU 分配一份副本。更新时关本核抢占 + 访问本核副本——无跨核同步。读时遍历所有核求和。这是用空间换同步——N 个核 N 份计数器。网络包计数、中断计数、vm_stat 都用这招。

图 8.1 · per-CPU 变量：写无锁（各写各的），读求和。范式 #6 的另一面——硬件给"每核独立 cache"，软件用它造免锁计数。

9. 信号量：计数同步原语

同步原语

Semaphore · 信号量

一个信号量 = 一个整数 count + 一个等待队列 + 两个原子操作。P (wait)：若有名额则占一个，否则睡眠。V (post)：释放一个名额，若有等待者则唤醒一个。Dijkstra 1965 提出。
图 9.1 · 信号量是"名额池"。P 申请名额（满则睡），V 释放名额（有等待者则唤醒）。二值即锁，计数即并发限制。
信号量与 mutex 不完全等价。二值信号量看起来像 mutex，但有区别：mutex 有"所有权"——只有持锁者才能 unlock（调试时能定位谁忘放锁）。信号量没有所有权——任何线程都能 V。所以用信号量当 mutex 是反模式，会丢失调试信息。

10. 生产者-消费者：完整代码与死锁陷阱

生产者-消费者问题（Bounded Buffer）：生产者向有界缓冲区放数据，消费者取数据。要解决三个约束：缓冲区满时生产者等、空时消费者等、缓冲区本身的结构修改要互斥。用三个原语各管一件事：empty 信号量管"有空位吗"、full 信号量管"有数据吗"、mutex 管缓冲区内部结构的原子性。

图 10.1 · 生产者-消费者的完整结构。empty/full 各管一个条件，mutex 管缓冲区原子性。顺序写反是经典死锁。
死锁陷阱：顺序写反。如果生产者先 lock(mutex) 再 P(empty)——缓冲区满时：生产者拿到 mutex → P(empty) 因满而睡眠 → 持着 mutex 睡觉。消费者需要 mutex 才能取数据 → 拿不到 mutex → 永远不能 V(empty) → 死锁。这个错误极常见——因为代码"看起来只是顺序不同"，但语义天差地别。规则：先等条件（P），再拿互斥（mutex）。
停下来想一想：如果只有一个生产者一个消费者，mutex 还需要吗？
答案：不需要。单生产单消费时，in 只有生产者写、out 只有消费者写，两者各读对方的索引但不修改——不会竞态。empty 和 full 两个信号量已足够。但多生产或多消费时，多个生产者同时改 in → 需要 mutex。这是"无锁"的边界——竞态条件是否真存在决定了锁是否真需要。

11. futex：用户态快速路径 + 内核态慢路径

传统的 mutex 每次 lock/unlock 都陷入内核——即使无竞争也要两次系统调用（~几百 ns 每次）。但大多数 mutex 的实际使用几乎无竞争——99%+ 的 lock/unlock 是同一个线程在跑，根本没人抢。为这 99% 的情况付系统调用代价，太亏。Linux 的 futex（fast userspace mutex） 解决这个。

实战

Futex · 快速用户态互斥

无竞争时在用户态用原子指令完成（零系统调用）；有竞争时才陷入内核睡眠/唤醒。把"快路径"做到极致，"慢路径"只在必要时走。
图 11.1 · futex 的双路径。无竞争时纯用户态 CAS，零系统调用；有竞争才陷入内核。三态 0/1/2 让"无等待者的 unlock"也走快路径（1→0 不需 FUTEX_WAKE）。

范式 #6 + #3 · futex 的双重范式

futex 是范式 #6（HW-SW 协同）的教科书案例：硬件给 CAS（用户态快速路径），软件在竞争时才用内核机制（休眠/唤醒）。同时也是范式 #3（惰性求值）：内核对象（等待队列）不到真有人等待时才创建——无竞争时完全没有内核态开销。glibc 的 pthread_mutex 底层就是 futex。

12. 内存序与屏障：并发的最后一道暗坑

这是并发里最反直觉、最容易写错的部分。即使你用了原子指令，编译器和 CPU 仍然会重排你的访存指令——单线程下重排不影响结果，但多线程下会破坏你精心设计的同步。重排来源：编译器看到无依赖的访存可交换顺序；CPU 乱序执行 + 写缓冲 + cache 不一致——x86 是强序（TSO，只可能 store-load 重排），ARM/POWER 是弱序（几乎任意重排）。

图 12.1 · 内存序的本质：给原子操作加约束，禁止某些重排。release-store 保证之前的写先可见；acquire-load 保证之后的读不提前。配对使用即正确发布。
这是真坑。很多"在 x86 上跑得好好的"代码移植到 ARM 就出 bug——因为 x86 的强序掩盖了代码的内存序错误。Linux 内核的 smp_store_release / smp_load_acquire、C11 的 memory_order_*、Rust 的 Ordering::Acquire/Release 都是为这个。写无锁代码不懂内存序 = 写 bug。
停下来想一想：为什么 x86 的 LOCK CMPXCHG（CAS）自带全序语义，而普通 mov 不自带？
答案：LOCK 前缀不仅锁 cache line，还隐含全内存屏障——它之前的所有 store 必须先对其他核可见，才能执行这个 CAS，CAS 之后的读也不能提前。普通 mov 在 x86 上只保证 TSO（store 顺序、load 顺序，但 store→load 可重排），不保证全序。所以用 CAS 做同步天然安全，用普通 mov 做 flag 就要小心。

14. 习题

P1 · CAS 实现自旋锁 L1

用文字描述如何用 CAS 实现 spin_lock 和 spin_unlock。说明 unlock 为什么不需要 CAS。

▸ 解答
spin_lock：循环 CAS(lock, 0, 1) 直到成功——原子检查 lock 是否为 0，是则设为 1 返回成功（拿到锁），否则返回失败继续循环。
spin_unlock：直接写 lock=0。只有持锁者会写 lock=0，没有竞争；其他线程在读 lock 判断是否为 0，普通 store 对它们可见（x86 TSO 保证 store 顺序可见）。若要严格跨平台，用 release 序的原子 store。
P2 · 竞态值枚举 L2

两个线程各执行 x = x + 1 一次，x 初值 0，x = x + 1 编译为 load→add→store 三指令。列出所有可能的最终 x 值，并各给一个产生该值的交错。

▸ 解答
可能值：1 或 2。
x=2：T1 全做完 (load0→add→store1) → T2 全做完 (load1→add→store2)。串行。
x=1：T1 load(0) → T2 load(0) → T1 add→store(1) → T2 add→store(1)。T2 的 load 抢在 T1 的 store 前，两人都从 0 加，都写 1，丢失一次更新。
不可能得到 0（至少一次 store 会成功）或 3（只有两次 add）。推广：N 个线程各加 1 一次，结果范围 [1, N]。各加 1 共 M 次，结果范围 [1, M]——最坏是所有 load 先于所有 store。
P3 · 生产者-消费者死锁分析 L2

若 mutex 放在 sem_wait(empty) 之前，缓冲区满时描述所有线程的状态，证明死锁。

▸ 解答
状态：生产者 P 持有 mutex，正在 sem_wait(empty) 上睡眠（empty=0）。消费者 C 阻塞在 mutex_lock 上（等 P 释放 mutex）。
死锁条件：C 要释放 empty（V(empty)）才能唤醒 P，但 C 需要 mutex 才能进入临界区取数据 → V(empty)，而 mutex 被 P 持着 → C 永远拿不到 mutex → empty 永远不被 post → P 永远睡。循环等待，死锁。
修复：调换顺序，先 sem_wait(empty) 再 mutex_lock。sem_wait 在 mutex 之外睡眠，不持 mutex，消费者能拿 mutex 取数据并 V(empty) 唤醒生产者。
P4 · Ticket 锁公平性 L2

证明 ticket spinlock 满足"有限等待"（无饥饿），并解释它相对 TAS 锁在公平性上的改进。

▸ 解答
证明：每个线程调 lock 时通过 FAA 取到一个唯一递增的 ticket 号 my。owner 从 0 单调递增，每次 unlock +1。线程 my 会在 owner 等于 my 时获得锁——它前面只有 my - owner 个线程，这个数只减不增（每次 unlock 减 1）。所以最多等 my - owner 次 unlock 就轮到——等待有界。
TAS 锁：unlock 写 locked=0 后，所有等待者同时去 TAS 抢——谁抢到随机，可能某核一直抢不到（饥饿）。ticket 锁按取号顺序服务，严格 FIFO，消除饥饿。
P5 · futex 双路径 L3

(a) futex 怎么知道有没有竞争？(b) 为什么"无竞争走用户态、有竞争才走内核"能大幅减少系统调用次数？(c) fut 字的三个值 0/1/2 各代表什么状态？为什么需要区分 1 和 2？

▸ 解答
(a) 用户态先 CAS 尝试 0→1。成功 → 无竞争 → 直接返回（零系统调用）。失败 → 有竞争 → 调 futex(FUTEX_WAIT) 陷入内核睡眠。
(b) 大多数 mutex 持锁时间极短、竞争极罕见——99%+ 的 lock/unlock 无竞争，在用户态完成。只有真正冲突时才付系统调用代价。把昂贵路径推到罕见情况 = 范式 #3（惰性求值）。
(c) 0=空闲；1=被占但无等待者；2=被占且有等待者在内核睡。区分 1 和 2 的原因：unlock 时若 fut==1，直接减到 0 即可，不需要唤醒（没人在等）——省一次 FUTEX_WAKE 系统调用。若 fut==2，减到 0 后必须 FUTEX_WAKE 唤醒一个等待者。如果不区分（只用 0/1），unlock 每次都要调 FUTEX_WAKE 检查有没有等待者——又回到每次系统调用的老路。三态设计让"无等待者时的 unlock"也走快路径。
P6 · 内存序发布 bug L3

线程 1：data = 42; ready = 1;（普通 store）。线程 2：if (ready) print(data);（普通 load）。在 ARM 上观察到线程 2 打印出 0。解释原因，并给出用 release/acquire 修复的方案。

▸ 解答
原因：ARM 是弱序内存模型，编译器/CPU 可把线程 1 的两个 store 重排为先 ready=1 后 data=42（单线程下无依赖，重排合法）。线程 2 看到 ready=1 时 data 可能还是 0。
修复：线程 1 用 store(ready, 1, release)——保证 data 的 store 先于 ready 的 store 对其他核可见；线程 2 用 load(ready, acquire)——保证 ready 的 load 之后的 data 读不会重排到 ready 之前。配对使用，线程 2 看到 ready==1 则 data 必为 42。
x86 上这个 bug 不会出现——x86 的 TSO 保证 store-store 不重排，普通 store 自带 release 语义。但写可移植代码不能依赖 x86 的强序，必须显式标注内存序。
