1. 管程与条件变量

同步原语

管程 · Monitor

一个管程 = 一个互斥锁 + 0 或多个条件变量 + 一组过程。编译器/运行时保证：同一时刻最多一个线程在管程的某个过程中。管程把锁的 acquire/release 隐藏起来——程序员只写"条件不满足就 wait"，不用管锁。

条件变量（Condition Variable）

wait()：原子地释放锁 + 让当前线程睡眠。signal()：唤醒一个在 wait 的线程。

Mesa 语义（Java/Pthread）：signal 只建议"条件可能变了"，被唤醒者必须重新检查条件（while 而非 if）。Hoare 语义（理论）：signal 立即把 CPU 让给被唤醒者——唤醒者不用重检查。后者理论上更优雅但实现极难——所有实际系统都用 Mesa。

读者-写者问题用管程：读者可以同时读（共享锁），写者独占。条件变量 `okToRead` 和 `okToWrite` 协调等待者。这个问题的"饥饿"变体揭示了调度公平是并发原语之上的额外要求——锁本身不保证"先等的先进"。

2. 死锁：四个必要条件的逻辑必然性

灾难

死锁 · Deadlock

四个条件全部满足 → 死锁必然发生。缺一不可——这就是死锁应对的逻辑基础：打破任何一个条件即可预防死锁。

四个必要条件

  1. 互斥：资源不能同时被多个线程使用
  2. 持有并等待：持有一个资源的同时等待另一个
  3. 不可抢占：不能强行抢走别人持有的资源
  4. 循环等待：A 等 B，B 等 C，...，Z 等 A——资源分配图中有环
打破任何一个条件就可以预防死锁。打破条件 1（互斥）→ 无锁数据结构（CAS 造的无锁栈不持锁——没有"互斥"这回事）。打破条件 2（持有并等待）→ 一次性申请所有需要的锁。打破条件 3（不可抢占）→ 拿不到锁就释放已持锁（`try_lock` + 回退）。打破条件 4（循环等待）→ 按固定顺序加锁（所有代码先锁 A 再锁 B——永远不会形成环）。

3. 银行家算法与死锁应对

银行家算法（Banker's Algorithm）——死锁避免（avoidance，有别于预防 prevention）：系统跟踪每个线程的"最大资源需求"和"当前持有"，在每次分配前判断"分完后还存在一个安全序列（所有线程都能完成）吗？"如果不存在 → 不让分——即使资源空闲。

实际上很少用——因为需要提前知道最大需求（和 STCF 调度一样不现实）。更实用的做法是预防 + 检测恢复（周期性检查资源分配图是否有环 → 有环就杀一个线程释放资源）。

停下来想一想：数据库系统经常检测到死锁后回滚一个事务——为什么 OS 很少用检测恢复？因为数据库事务可以回滚（undo log），OS 线程很难"回滚"——它已经做了副作用（写了 pipe、发了网络包、改了共享内存）。

4. 无锁编程：CAS 构建栈

锁有代价：持锁线程被切走 → 等锁线程全部空转/阻塞 → 优先反转 → 死锁可能。无锁（lock-free）数据结构用 CAS 避免所有这些问题。

CAS 构建无锁栈（Treiber Stack）

push(node)：do { node->next = top; } while (!CAS(&top, node->next, node));"把新节点的 next 设为当前 top，然后 CAS 尝试把 top 改成新节点——如果这期间 top 被别人改了，重试。"
pop()：do { node = top; if (node==NULL) return NULL; next = node->next; } while (!CAS(&top, node, next)); return node;"读 top → 读它的 next → CAS(top, old_top, next)。如果 CAS 失败——重试。"
关键：没有"锁"，没有"临界区"——CAS 失败就 retry。retry 次数 = 竞争度——低竞争时几乎总是一次成功。

范式 #3 · 惰性求值（无锁版）

无锁 = 乐观并发控制（optimistic concurrency）——"假设没有冲突，先去做了，如果冲突就重试"。这是惰性求值的并发版：不做冲突预防（锁），冲突发生了才补救（retry）。数据库的 OCC（乐观并发控制）也是同样的思路。

5. RCU：读端零开销的魔法

无锁

RCU · Read-Copy-Update

对于"读极多、写极少"的数据（路由表、文件系统目录缓存……），RCU 让读端完全不拿锁、不写共享变量、不需要原子操作——零开销。

三步流程

  1. Copy：写者复制数据结构，在副本上修改
  2. Update：原子指针 `rcu_assign_pointer` 把全局指针从旧版切到新版
  3. Reclaim：等所有已存在的读者都结束后（通过 `synchronize_rcu` 或宽限期回调），释放旧版内存

怎么知道"所有读者都结束了"？RCU 利用了 OS 的一个事实：上下文切换点 = 读者的结束点。Linux 内核中，读者在 RCU 读临界区中不能睡眠（不能调 `schedule()`）。所以：只要每个 CPU 都经历了一次上下文切换，该 CPU 上所有 RCU 读者都已结束。`synchronize_rcu` = 等所有 CPU 都经历过一次 quiescent state（通常是上下文切换）。

RCU 是惰性求值（范式 #3）在并发中的终极应用。写者不改原数据——它造一份新的，然后"切指针"这个 O(1) 原子操作完成更新。旧数据的回收推迟到"确定没人看了"——可能是几 ms 到几秒后。这期间新旧版本同时存在——空间换并发。

6. 推导与自测

P1 · 死锁四条件分析 L1

两个线程各持一个锁等对方另一个锁——经典死锁。逐一确认四个条件是否满足。如果改成 `try_lock` + 失败就释放已有锁，打破了哪个条件？

▸ 解答
① 互斥 ✓（锁不能共享）。② 持有并等待 ✓（各持一把等另一把）。③ 不可抢占 ✓（不能夺锁）。④ 循环等待 ✓（A 等 B，B 等 A）。`try_lock` + 释放 = 打破条件 3（不可抢占）——主动放弃自己持有的锁，让等待链断开。
P2 · 银行家算法推演 L2

系统 12 单位资源。P1（max=10, held=5）、P2（max=4, held=2）、P3（max=9, held=2）。当前分配后剩余 3 单位。问：当前状态安全吗？如果 P2 再申请 1 单位，能分配吗？

▸ 解答
当前：剩余 3。P1 need 5（不可满足）、P2 need 2（可满足）→ 先给 P2 完成释放 4 → 剩余 7 → P3 need 7 可满足 → P3 释放 9 → 剩余 16 → P1 need 5 可满足。安全序列 P2→P3→P1 = 安全。
P2 再申请 1 → P2 held=3, need=1, 剩余 2。检查：P2 need 1 可满足 → P2 完成释放 4 → 剩余 6 → P3 need 7 不可满足 → P1 need 5 可满足 → P1 释放 10 → 剩余 16 → P3 need 7 可满足。安全序列 P2→P1→P3 = 安全。可以分配。
P3 · RCU vs 读写锁 L3

比较 RCU 和读写锁（rwlock）在读极多写极少的场景。(a) rwlock 的读端需要什么原子操作？RCU 呢？(b) 在读者有 10000 个、每秒 100 万次读、写者每秒 1 次的场景下，估算 rwlock 和 RCU 的性能差异。(c) 写者较多（每秒 1000 次）时 RCU 有什么问题？

▸ 解答
(a) rwlock 读端：获取读锁（原子递减 reader count）→ 读 → 释放读锁（原子递增）。两次原子操作每次 ~几十 cycle。RCU 读端：`rcu_read_lock()` + 读 + `rcu_read_unlock()`——在 x86 上这两个函数是空操作（只禁止抢占——不写任何共享变量）。零原子操作。(b) rwlock 读者：2×1M×30 cycles = 60M cycles/s；RCU 读者：0。写者 1 次/s 的 `synchronize_rcu` 等所有 CPU 经历一次 quiescent state——~几到几十 ms——可以接受。(c) 写者多 → 每次写都要等所有 CPU 进 quiescent state → 延迟高。而且旧版本在 grace period 期间不能释放 → 内存积压。RCU 不适合写密集型。
