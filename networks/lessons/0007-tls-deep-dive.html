传输层   TCP
网络层   IP

TLS（Transport Layer Security）坐在 TCP 之上、HTTP 之下。当 HTTP 跑在 TLS 之上时，就变成了 HTTPS。TLS 提供三个保证：机密性（中间人看不到内容）、完整性（内容没被篡改）、身份认证（对方确实是它声称的那个）。

🎯 本课目标：理解非对称加密与对称加密的分工、TLS 握手的完整流程、证书链的验证机制、TLS 1.3 相对于 1.2 的改进。

1. 两种加密的分工

非对称加密 (RSA/ECDH)对称加密 (AES/ChaCha20)
密钥公钥 + 私钥（两个不同密钥）一个共享密钥（双方相同）
速度慢（比对称慢 100–1000 倍）快
在 TLS 中的角色握手阶段：验证身份 + 安全地协商出对称密钥数据传输阶段：用协商好的密钥加密所有流量

TLS 的设计哲学：用慢的非对称加密做一次性的密钥协商，然后用快的对称加密做大量的数据传输。两全其美。

2. TLS 1.2 握手 —— 经典的两轮往返

服务器
ClientHello支持的密码套件 + 随机数 C

ServerHello选定的密码套件 + 随机数 S

开始对称加密传输 HTTP 数据

对称密钥如何生成？客户端生成一个 Pre-Master Secret，用服务器公钥加密发送。双方用「随机数 C + 随机数 S + Pre-Master Secret」通过 PRF 推导出最终的对称密钥。这保证了即使攻击者能监听握手消息（随机数是明文），也无法算出对称密钥（因为 Pre-Master Secret 被公钥加密了）。

3. 证书与证书链 —— "你真的是 example.com 吗？"

中间人攻击的经典场景：攻击者在你和服务器之间，用自己的公钥替换服务器的。为了防这个，TLS 引入了证书（Certificate）和 CA（Certificate Authority）。

证书是一个由 CA 签名的文件，包含了域名和该域名的公钥。浏览器内置了约 150 个根 CA 的证书，这些是信任的锚点：

根 CA（浏览器信任列表，如 DigiCert、Let's Encrypt）
  ↓ 签名
中间 CA（根 CA 委派，日常签发）
  ↓ 签名
服务器证书（example.com + 公钥）

浏览器验证时从下往上逐级检查：服务器证书的签名是否来自中间 CA → 中间 CA 的签名是否来自根 CA → 根 CA 是否在信任列表中。任何一级不通过，浏览器显示安全警告。

4. TLS 1.3 —— 更快、更安全

TLS 1.2TLS 1.3 (2018)
握手往返2-RTT（两次往返）1-RTT（会话恢复 0-RTT）
密钥交换RSA 或 ECDHE仅 ECDHE（前向安全）
支持的密码套件几十种（含不安全旧算法）仅 5 种（全是 AEAD 加密）
加密时机握手后半段才加密ServerHello 之后全部加密
0-RTT不支持支持（之前连接过的客户端可以直接发加密数据）

TLS 1.3 的最大改进：把 2-RTT 缩减为 1-RTT，并且删除了所有已知不安全的密码套件。它不给你配置错误的机会——能用的全是安全的。

🔑 前向安全（Forward Secrecy）：即使服务器的私钥未来某天泄露了，过去的会话也无法被解密。因为每次会话的对称密钥是临时生成的（ECDHE），用完就丢。RSA 密钥交换没有前向安全——拿到私钥就能解密所有历史流量。
