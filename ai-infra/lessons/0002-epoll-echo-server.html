IO 多路复用与 epoll：从 select 到手写 echo server

读完这一页，你会知道为什么需要 epoll、它内部怎么工作、跟 select 差在哪里——然后亲手写出来。

0. 回顾：0001 的 server 为什么一次只能处理一个连接

上一课的 echo server 长这样：

while True:
    conn, addr = sock.accept()     # 阻塞：没新连接就等
    data = conn.recv(4096)         # 阻塞：没数据就等
    conn.sendall(data)
    conn.close()

问题在于：recv() 是阻塞的。当你在跟客户端 A 等数据的时候，客户端 B 已经完成了三次握手、在内核 backlog 里排队了——但你的程序根本不知道 B 的存在，因为你还卡在 recv() 那里。

时间线： server: accept(A) ──── recv(A) ──── send(A) ──── close(A) ──── accept(B) ... ↑ ↑ B 已经到 backlog 了 终于轮到 B 但 server 不知道 等了一整个 A 的时间

直觉反应：给每个连接开一个线程不就行了？

1. 第一反应：多线程 —— 为什么不够

while True:
    conn, addr = sock.accept()
    threading.Thread(target=handle, args=(conn,)).start()

一个连接一个线程，看起来很自然。问题是：

问题为什么严重
线程开销 每个线程至少占 1-8 MB 栈空间 + 内核调度开销。1 万个连接 = 1 万个线程 = 几十 GB 内存，光栈就撑爆了。
上下文切换 CPU 在 1 万个线程之间来回切换，大部分时间花在"换人"而不是"干活"。
大部分线程在等 一个 LLM 推理 server 可能有 1000 个并发连接，但同一毫秒内只有几个连接真正有数据要处理。其他 990+ 个线程全在阻塞等 IO，白占资源。
一个餐厅有 100 张桌子。多线程方案 = 每张桌子配一个服务员，专门盯这一桌。问题是大部分桌子这时候没在点菜——客人在吃饭、在聊天——但服务员就站那等着。100 个服务员，工资谁付？

更好的方案：一个服务员盯所有桌子，哪桌举手了就去哪桌。这就是 IO 多路复用。
C10k 问题：2000 年前后，业界发现"用线程模型扛 1 万个并发连接"在当时的硬件上根本不可行。这催生了 IO 多路复用技术：用一个线程管理成千上万个 fd。nginx、Redis、Node.js、vLLM 的 event loop 全都是这个模型。

2. IO 多路复用：一个线程盯多个 fd

核心思想很简单：你不主动去 recv() 某个特定的连接（因为不知道谁有数据），而是告诉内核：

"我这里有 N 个 fd，你帮我盯着，谁有数据了（或 listen fd 有新连接了），叫我一声。"

然后你的程序阻塞在一个统一的"等"操作上，而不是阻塞在某个具体的 recv() 上。内核叫你的时候，会告诉你哪些 fd 就绪了，你只处理这些。

你的程序 内核 ───────── ────── "帮我盯这 100 个 fd" ──→ 记录到内核数据结构 │ 阻塞等待（睡觉）... │ 内核在后台监控所有 fd │ ... fd 37 有数据了！ │ ... listen fd 有新连接了！ │ ←── "醒醒！fd 37 和 listen fd 就绪了" 只处理 fd 37 和 listen fd 其他 98 个 fd 根本不看 处理完了，继续等... ──→ 继续监控

这个"帮我盯着 + 叫我"的机制，经历了三次迭代：select → poll → epoll。每一代都在解决上一代的性能瓶颈。

3. select：最朴素的实现

它怎么工作

select 是 1983 年在 BSD Unix 里引入的。它的接口设计非常直白：

# Python 伪代码（帮你理解概念，不是真 API）
ready_to_read, _, _ = select.select(
    [fd3, fd4, fd5, listen_fd],   # "帮我盯这些 fd 的可读事件"
    [],                            # "帮我盯这些 fd 的可写事件"（暂不管）
    [],                            # "帮我盯这些 fd 的异常"（暂不管）
    timeout=None                   # 没有就绪就永远等
)

调用后，你的程序阻塞。内核逐个检查你传进来的 fd 列表，发现有就绪的就返回。返回后你拿到一个"就绪 fd 列表"。

内核内部在干什么

select 的内核实现很朴素——用 fd_set 位图：

fd_set（一个固定长度的位数组，通常 1024 bit）： bit 位置: 0 1 2 3 4 5 6 7 ... 1023 ─ ─ ─ ─ ─ ─ ─ ─ ─ 1 1 1 0 1 1 0 0 ... 0 ↑ ↑ ↑ ↑ ↑ stdin stdout stderr fd4 fd5 (fd3=1, fd4=1, fd5=1)

每次调 select()，内核做三件事：

  1. 拷贝：把你传进来的 fd 列表从用户空间拷到内核空间
  2. 遍历：从头到尾扫一遍 fd_set（1024 个 bit），对每个设了 1 的 fd 检查"有没有数据"
  3. 修改：把没有数据的 fd 对应 bit 清零，整个 fd_set 拷回用户空间

三个致命缺陷

缺陷说明后果
O(N) 遍历 每次调用都要扫全部 1024 个 bit，不管有几个就绪 fd 越多越慢，即使只有 1 个活跃
重复拷贝 每次调用都要把 fd_set 从用户空间拷到内核、再拷回来 1024 bit = 128 字节，每次系统调用都拷贝，高频调用时开销大
1024 上限 fd_set 固定大小，默认最多盯 1024 个 fd 超过 1024 个连接？不行。要改内核宏重新编译。
select 就像老师点名：每次上课，老师从 1 号叫到 1024 号，每个名字都喊一遍"张三在吗？李四在吗？王五在吗？"，即使全班只有 3 个人举手。班里人越多，点名越慢——哪怕真正有事的人只有几个。

4. poll：链表替代位图，但本质没变

poll（1986 年，System V Unix）把 fd_set 位图换成了一个动态数组（struct pollfd 的数组）：

struct pollfd {
    int fd;         // 要盯的 fd
    short events;   // 我关心什么事件（可读？可写？）
    short revents;  // 内核填回来的：实际发生了什么事件
};

好处：没有 1024 上限了，想盯多少个 fd 都行。

坏处：O(N) 遍历和重复拷贝的问题完全没解决。每次调用还是要把整个数组拷进内核、从头扫到尾、再拷回来。

面试时不要说 "poll 比 select 快很多"。poll 只是去掉了 fd 数量上限，性能瓶颈（O(N) 遍历 + 拷贝）完全一样。真正快的是 epoll。

5. epoll：内核替你记住"谁在盯谁"

epoll 是 2002 年 Linux 2.6 引入的。它的设计哲学是：把"盯 fd"这件事交给内核持久化保存，不要每次都从头来。

核心设计：三个 syscall 分离

select/poll 只有一个 syscall，"盯 + 等" 全塞在一起。epoll 把它拆成三步：

syscall做什么调用频率
epoll_create() 在内核建一个 epoll 实例（一个"监控中心"） 程序启动时调一次
epoll_ctl() 往监控中心注册 / 修改 / 删除 fd 新连接来时调一次，连接断开时调一次
epoll_wait() 阻塞等事件，返回只有就绪的 fd 事件循环里反复调
select = 每次上课都从头点名。
epoll = 老师在开学时拿到一份花名册（epoll_ctl 注册），之后只喊举手的同学（epoll_wait 只返回就绪的）。新同学来了？加到花名册上。退课了？划掉。花名册一直保留，不用每次重建。

epoll 内部数据结构

这是面试高频题。epoll 实例在内核里维护两个东西：

epoll 实例（内核中） ┌─────────────────────────────────────────────────┐ │ │ │ 1. 红黑树 (rbtree) │ │ 存所有被监控的 fd + 关心的事件 │ │ 插入/删除/查找 = O(log N) │ │ │ │ ┌──┐ │ │ / \ │ │ fd3 fd7 │ │ / \ / \ │ │ fd4 fd5 fd8 fd12 ← 所有注册过的 fd │ │ │ │ 2. 就绪链表 (ready list / doubly-linked list) │ │ 只存有事件的 fd │ │ │ │ fd5 → fd12 → NULL ← epoll_wait 只返回这些 │ │ │ └─────────────────────────────────────────────────┘

关键机制：

  1. 你调 epoll_ctl(ADD, fd5) → fd5 插入红黑树
  2. 内核在后台监控红黑树里所有 fd。当 fd5 的 socket 缓冲区来了数据，内核的网卡中断处理程序把 fd5 挂到就绪链表上
  3. 你调 epoll_wait() → 内核只看就绪链表，把上面的 fd 填到你给的数组里返回

这就是 epoll 为什么是 O(就绪数)：10000 个连接里只有 3 个活跃？epoll_wait 只返回这 3 个，不碰其他 9997 个。

面试问 "epoll 为什么比 select 快"，标准答案三条：
1. 注册持久化：fd 注册一次，不用每次调用都拷贝
2. O(就绪数)：只返回活跃的 fd，不遍历全部
3. 无 fd 数量限制：红黑树动态分配，上限是系统内存

追问 "epoll 内部用什么数据结构"，答：红黑树（存注册的 fd）+ 双向链表（存就绪的 fd）。

三个 syscall 逐个看

第一步：epoll_create — 建监控中心

int epfd = epoll_create1(0);   // 返回一个 fd，代表这个 epoll 实例本身
// epfd 也是一个文件描述符！用完要 close(epfd)

epoll_create1(0) 在内核分配一个 epoll 实例，返回一个 fd 让你引用它。这个 fd 不是 socket、不是文件——它代表的是内核里的那个红黑树 + 就绪链表。

第二步：epoll_ctl — 注册 / 修改 / 删除

struct epoll_event ev;
ev.events  = EPOLLIN;       // 关心"可读"事件
ev.data.fd = listen_fd;     // 把这个 fd 存进去，返回时能拿回来

epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
//              ^^^^^^^^^^^^^
//              ADD = 新增    MOD = 修改    DEL = 删除

关键：ev.data 是一个 union，可以存一个 fd 整数，也可以存一个指针。epoll_wait 返回时会原样还给你。这样你不用自己维护"这个就绪的 fd 是哪个连接"的映射。

第三步：epoll_wait — 等事件

struct epoll_event events[64];     // 你提供的输出缓冲区
int n = epoll_wait(epfd, events, 64, -1);
//                            ^^  ^^
//                       最多返回几个  超时(-1=永远等)

// 返回后，events[0] .. events[n-1] 就是就绪的事件
for (int i = 0; i < n; i++) {
    int fd = events[i].data.fd;     // 你注册时存的 fd
    uint32_t revents = events[i].events;  // EPOLLIN / EPOLLOUT / ...
    // 处理这个 fd ...
}
epoll_wait 的第二个参数 events 是你分配的数组，内核往里填。第三个参数是数组大小（最多填多少）。返回值 n 是实际就绪数。如果 n == 64（等于你的上限），说明可能还有就绪事件没返回完——下次 epoll_wait 会继续给你，不会丢。

6. LT vs ET：两种触发模式

注册 fd 时，你可以在 ev.events 上加一个标志位 EPOLLET：

ev.events = EPOLLIN;             // Level Triggered（水平触发，默认）
ev.events = EPOLLIN | EPOLLET;   // Edge Triggered（边沿触发）

区别非常大：

Level Triggered (LT)Edge Triggered (ET)
触发条件 缓冲区有数据就通知（状态） 缓冲区从空变非空时通知一次（变化）
重复通知 如果你没读完，下次 epoll_wait 还会返回这个 fd 只通知一次，没读完的数据不会再次通知
read 策略 读一次就行，没读完下次还会叫你 必须循环读到 EAGAIN，否则数据卡住
必须非阻塞？ 建议但非必须 必须（循环读要靠 EAGAIN 判断读完）
性能 略低（可能重复唤醒） 略高（减少无效唤醒）
你邮箱里有 3 封未读邮件。

LT = 每次你问"有没有邮件"，邮递员都说"有！3 封！"。你读走 1 封，下次问"还有 2 封！"。一直到你全读完。

ET = 只有新邮件到达那一刻，邮递员叫你一次"来邮件了！"。如果你去取了 1 封但没取完，剩下的邮递员不会再叫你——你得自己记着去取。
ET 模式下忘记循环读到 EAGAIN = 数据永久卡在内核缓冲区，客户端以为你收了但你程序不知道。这是 epoll 最常见的 bug。面试问 "ET 有什么坑" 就是在问这个。

初学建议：先用 LT（默认），稳了再切 ET。生产环境（nginx、Redis）通常用 ET 减少无效唤醒。

7. 把概念串起来：一个完整的 epoll server 事件循环

现在把所有概念拼成一个完整的流程图：

程序启动 │ ├─ socket() → listen_fd ├─ bind() + listen() ├─ epfd = epoll_create1(0) ← 建监控中心 ├─ epoll_ctl(epfd, ADD, listen_fd) ← 注册 listen fd │ ▼ ┌─────────────── 事件循环 ──────────────────┐ │ │ │ n = epoll_wait(epfd, events, 64, -1) │ ← 阻塞等事件 │ │ │ │ ├─ events[i].fd == listen_fd ? │ │ │ ├─ YES: conn = accept(listen_fd) │ ← 取新连接 │ │ │ set_nonblock(conn) │ │ │ │ epoll_ctl(epfd, ADD, conn) │ ← 注册到监控 │ │ │ │ │ │ └─ NO: conn 有数据 │ │ │ data = recv(conn) │ │ │ ├─ data 为空: 对端关闭 │ │ │ │ epoll_ctl(DEL, conn) │ ← 从监控移除 │ │ │ close(conn) │ │ │ └─ 有数据: 处理 + sendall │ │ │ │ │ └─ 继续循环... │ └────────────────────────────────────────────┘
这个模式就是Reactor 模式——单线程 + 事件循环 + IO 多路复用。nginx、Redis、Node.js、vLLM 的 AsyncLLMEngine 底层都是这个形状。区别只是"处理"那一步做的事不同：nginx 反代、Redis 执行命令、vLLM 调度推理。

9. 概念检查（确认你跟上了再写代码）

Q1. 1000 个连接，只有 2 个活跃。select 每次调用要看多少个 fd？epoll_wait 每次返回多少个？
Q2. epoll_ctl 的 ev.data.fd 字段为什么存在？如果 epoll 没有这个字段，你的程序要怎么知道"就绪的 fd 7 对应哪个客户端"？
Q3. ET 模式下，你 read(fd, buf, 1024) 读了 1024 字节，但客户端实际发了 3000 字节。剩下 1976 字节会怎样？LT 模式下呢？
点击展开答案（先自己答再看）

A1：select 每次要看全部 1000 个 fd（O(N)），即使只有 2 个有数据。epoll_wait 只返回 2 个（O(就绪数)）。这就是 epoll 在高并发场景下的核心优势。

A2：ev.data 让你在注册时"存一个标记"，epoll_wait 返回时"原样拿回"。如果没有它，你需要自己维护一个 fd → connection_info 的字典。有这个字段就省了这一步——你可以直接把连接对象的指针（C）或对象本身（Python selectors 的 data=conn）存进去。

A3：ET 模式下，剩下 1976 字节卡在内核缓冲区。因为 epoll 只在"空→非空"时通知一次，缓冲区里还有数据不算"新事件"，下次 epoll_wait 不会返回这个 fd。你必须循环 read 直到返回 EAGAIN 才安全。LT 模式下，因为缓冲区还有数据（"有数据"这个状态持续），下次 epoll_wait 还会返回这个 fd，你可以继续读，不会丢数据。

10. 实践：手写 epoll echo server

概念搞清楚了，现在兑现成代码。两版骨架已放到 exercises/0002-epoll-echo/:

  • echo_server_py.py — Python selectors 版,先做这个
  • echo_server_c.c — C 裸 epoll 版,面试白板级

为什么先 Python 再 C

Python selectors 把 epoll 包了一层,不用管 struct epoll_event、不用管 fd 整数,10 分钟能跑通——先建立"多路复用 server 长什么样"的整体形状。然后 C 版把同一形状裸写一遍,fd 就是个 int,这才是面试要你白板写的。

Python 版 — 要填的 5 处

accept 出 conn 后,要告诉 epoll"以后帮我盯这个 fd 的可读事件"。

sel.register(conn, selectors.EVENT_READ, data=conn)

关键:data=conn 是你塞给 epoll 的私货（就是上面讲的 ev.data）。等会 sel.select() 返回时,它会原样还给你(key.data),这样你不用自己维护 fd→conn 的映射。

conn.sendall(data)

教学版用 sendall 省事。生产环境 socket buffer 满了 send 会 partial write,要监听 EVENT_WRITE + 缓冲未发完的数据——这是另一节课,先不管。

sel.register(sock, selectors.EVENT_READ, data=sock)

和 TODO 1 一样,只是这次 fd 是 listen socket。data 塞 sock 本身,待会用 key.fileobj is sock 区分"这是新连接"还是"这是数据"。

events = sel.select(timeout=None)

阻塞到任一 fd 就绪,返回 [(key, mask), ...]。只有就绪的,不遍历全部——这就是上面讲的"O(就绪数)"。

if key.fileobj is sock:
    accept_conn(sel, callback)
else:
    service_conn(sel, callback)

listen fd 可读 = 有新连接 → accept。conn fd 可读 = 有数据 → recv。同一个线程,同一个循环,靠 key.fileobj 分流。这就是"单线程扛多连接"的全部秘密。

跑起来验证

python3 echo_server_py.py
# 终端 2:
nc 127.0.0.1 9000
hello        # 应回显 hello
# 终端 3 (同时):
nc 127.0.0.1 9000
world        # 也回显 world, 互不影响

两个 nc 同时连、同时 echo = 多路复用成功。

C 版 — 同样的形状,裸写

填 5 处 TODO,对应 Python 的 5 步,只是没了抽象:

  1. epoll_create1(0) — 建 epoll 实例（监控中心）
  2. epoll_ctl(epfd, EPOLL_CTL_ADD, lfd, &ev) — 注册 listen fd 到红黑树
  3. epoll_wait(epfd, events, MAX_EVENTS, -1) — 从就绪链表取事件
  4. fd==lfd 分支:accept + set_nonblock + epoll_ctl ADD
  5. else 分支:read → >0 write 回去 / ==0 关连接 / <0 看 errno
gcc -O2 -Wall echo_server_c.c -o echo_server_c
./echo_server_c
C 版几个会卡你的点:struct epoll_event 的 .events 是位掩码(EPOLLIN | EPOLLET),.data.fd 是个 union,你存 fd 进去,返回时 events[i].data.fd 取回。LT 模式下 read 一次就行;切 ET 要循环 read 到 EAGAIN。

11. 代码级概念检查

Q4. Python 版里,如果不传 data=conn,sel.select() 返回时你怎么知道是哪个连接?

Q5. C 版 epoll_wait 的第二个参数 events 数组和 MAX_EVENTS 各是什么角色?数组开太大有坏处吗?

Q6. 为什么 accept 出来的 conn_fd 也要 set_nonblock?LT 模式下不设会死吗?

答案(先想再展开)

Q4：key.fileobj 仍能拿到 fd/socket 对象(Python 自动维护),所以不传 data 也能用 key.fileobj 区分。但生产代码里一个 fd 上可能挂多种状态(待发缓冲、peer addr 等),data 让你把这些一起塞进去,省掉自己维护 dict。这就是 ev.data 的设计意图。

Q5：events 是你提供的输出缓冲,epoll_wait 把就绪事件填进去;MAX_EVENTS 是告诉它"最多填这么多"。返回值 n = 实际就绪数。数组开太大只是浪费一点栈/堆,没别的坏处;开太小会一次拿不完(下次 epoll_wait 还会返回剩下的,不会丢)。

Q6：非阻塞是为了 recv/read 没数据时返回 EAGAIN 而不是阻塞整个事件循环——一个慢连接把全 server 卡死。LT 模式下不设非阻塞也能跑(读到没数据时阻塞一下再返回),但会拖累其他连接;ET 模式下必须非阻塞,否则循环 read 到没数据时会阻塞死。所以无论如何都设。
