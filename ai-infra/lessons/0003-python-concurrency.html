Python 并发：threading / GIL / multiprocessing / asyncio

Python 的并发为什么这么麻烦？读完这一页你会彻底搞清 GIL 是什么、为什么不是所有并发都需要多线程、以及 asyncio 在 vLLM 里怎么用。

0. 为什么 AI Infra 面试会考 Python 并发

所有主流推理引擎的核心组件都是 Python 写的——而它们必须同时处理大量请求：

  • vLLM 的 AsyncLLMEngine 用 asyncio event loop 管理请求的生命周期
  • SGLang 用 asyncio + multiprocessing 做推理 worker 池
  • 数据加载（DataLoader）用 multiprocessing 预取数据
  • 训练中用单独的进程做 checkpoint 保存 / 日志写入

面试可能直接问："Python GIL 怎么影响推理引擎？为什么 vLLM 用 asyncio 而不是多线程作请求调度？"

回答这些问题的前提，就是搞清楚 Python 的四种并发武器：threading · multiprocessing · asyncio · Queue。

1. threading — 轻量但有个大坑

线程（thread）是操作系统调度的最小单位。同一进程里的线程共享内存地址空间——这意味着它们可以读写同一个变量（方便但也危险）。

开线程很简单

import threading, time

def worker(n):
    for i in range(3):
        print(f"worker {n}: step {i}")
        time.sleep(0.1)

threads = []
for i in range(3):
    t = threading.Thread(target=worker, args=(i,))
    t.start()
    threads.append(t)
for t in threads:
    t.join()
print("all done")

几个要点：

  • .start() → 告诉 OS 启动这个线程。线程立即开始跑 worker()。
  • .join() → 主线程阻塞在这里，等这个线程结束才继续往下走。
  • 线程间共享变量需要 threading.Lock 保护——否则两个线程同时写同一个列表会出错（data race）。
类比：主线程是"店长"，.start() 是给员工分配任务，.join() 是等员工干完再下班。员工之间共用同一个货架（共享内存）——如果两个人同时往同一格放东西，东西就乱套了（data race），需要一把锁（Lock），一次只让一个人碰货架。

但 Python 的线程有一个致命限制——GIL。

2. GIL — 为什么 Python 线程不能并行做 CPU 计算

GIL 是什么

GIL = Global Interpreter Lock（全局解释器锁）。CPython（标准 Python）的实现中，整个解释器在执行 Python 字节码时，只允许同时只有一个线程持有这把锁。

时间轴 → 线程 A: ██████████░░░░░░░░░░██████████████████ 线程 B: ░░░░░██████████████░░░░░░░░░░████████ ^ ^ A 持有 GIL A 释放 GIL，B 拿到

这意味着：两个 Python 线程不能同时在两个 CPU 核上跑 Python 代码。它们只是在"快速轮流"（时间片轮转），不是真正的并行。

那 threading 有什么用？

答案是——IO 密集型任务有用，CPU 密集型没用。

任务类型举例GIL 影响
IO 密集型网络请求、文件读写、数据库查询线程等 IO 时会主动释放 GIL，其他线程可以跑
CPU 密集型矩阵乘法、解析数据、字符串处理线程一直占着 GIL 不放，其他线程干等——等于单核
混合型先读数据、再计算、再写结果计算部分串行，IO 部分可以 overlap

关键机制：Python 的执行器在 IO 操作（read()、write()、send()、time.sleep()）之前会释放 GIL，因为 IO 等待不涉及 Python 对象操作。这跟 Lesson 0002 的 epoll 很像——等 IO 时不占 CPU，把 CPU 让给别人。

面试必问："Python 开 10 个线程做矩阵乘法，比 1 个线程快吗？"
答案：不快，甚至更慢（因为 GIL 切换开销）。矩阵乘法是 CPU 密集的 NumPy 操作。但注意：NumPy 和一些 C 扩展（如 PyTorch）的内部计算会释放 GIL，它们调用 C/Fortran 库时不受 GIL 限制。所以 PyTorch 的 tensor 运算可以多线程加速，但 Python 层的控制逻辑不行。

3. multiprocessing — 真并行，但代价大

如果 threading 因为 GIL 不能并行跑 CPU 计算，那怎么办？答案：不开线程，开进程。

每个进程有自己独立的内存空间、自己独立的 Python 解释器、自己独立的 GIL。N 个进程可以真正跑在 N 个 CPU 核上。

from multiprocessing import Process

def worker(n):
    # 每个进程有自己的 GIL → 真并行
    result = sum(i * i for i in range(10_000_000))
    print(f"process {n}: done")

if __name__ == "__main__":
    procs = []
    for i in range(4):
        p = Process(target=worker, args=(i,))
        p.start()
        procs.append(p)
    for p in procs:
        p.join()

进程 vs 线程：权衡

threadingmultiprocessing
内存共享（省内存，但容易 data race）独立（每个进程拷贝一遍，内存开销大）
启动速度快（ms 级）慢（需要 fork/exec 整个解释器，百 ms 级）
通信直接读写共享变量（需 Lock）需要 IPC 机制（Queue / Pipe / shared memory）
GIL受 GIL 限制不受 GIL 限制（真并行）
适用IO 密集型、调用 C 扩展CPU 密集型、隔离任务
类比：threading = 几个店员共用同一本账本（共享内存），需要轮流用（GIL），但传话快（共享变量）。multiprocessing = 几家分店各自独立记账（独立进程），可以同时算（真并行），但互相传话需要打电话/送文件（IPC）。

进程间通信：Queue

最常用的 IPC 方式：一个进程往 Queue 放数据，另一个取。底层用 pipe + pickle 序列化。

from multiprocessing import Process, Queue

def producer(q):
    for i in range(10):
        q.put(i)         # 放进队列
    q.put(None)          # 哨兵：告诉 consumer 结束了

def consumer(q):
    while True:
        item = q.get()   # 阻塞等数据
        if item is None:  # 哨兵检测
            break
        print(f"got {item}")

if __name__ == "__main__":
    q = Queue()
    p1 = Process(target=producer, args=(q,))
    p2 = Process(target=consumer, args=(q,))
    p1.start(); p2.start()
    p1.join(); p2.join()

这就是生产者-消费者模式——AI Infra 里随处可见：

  • 数据加载进程（producer）→ 训练进程（consumer）
  • 日志写入进程（consumer）← 推理进程（producer）
  • 请求分发进程（producer）→ GPU worker 进程（consumer）

4. asyncio — 单线程里的协作式并发

如果只是等 IO，连线程的开销都嫌大怎么办？Python 的 asyncio 提供了一个单线程内协作式多任务的方案。

核心概念

概念是什么
async def定义一个"协程函数"。调用它不会立即执行，而是返回一个 coroutine object。
await交还控制权。"这个操作可能要等，你先去干别的，等操作完了再回来叫我。"
event loop一个调度器，管理所有协程的切换。阻塞时切走，就绪时切回。
asyncio.run()创建一个 event loop，把协程丢进去跑，跑完收尾。
import asyncio

async def fetch_data(url):
    print(f"fetching {url}...")
    await asyncio.sleep(1)  # 模拟网络请求
    print(f"done {url}")
    return f"data from {url}"

async def main():
    # 并发发起 3 个请求
    tasks = [
        asyncio.create_task(fetch_data("url1")),
        asyncio.create_task(fetch_data("url2")),
        asyncio.create_task(fetch_data("url3")),
    ]
    results = await asyncio.gather(*tasks)
    print(results)

asyncio.run(main())

执行过程（关键！）

线程 1 (唯一线程): 时间 → █═fetch═1═sleep═░░░═done1═█═fetch═2═sleep═░░░═done2═█═... █═fetch═3═sleep═░░═done3═══█ ^^^^^ ^^^^ await 切走 1 秒后回来 三个请求总共耗时 ~1 秒，不是 3 秒

关键认知：整个程序只有一个线程，一个 GIL。asyncio 的并发不是"同时做"，而是"不等时切走，好了再回来"。但这对于 IO 密集场景来说效果和并发一样——因为等待 IO 不消耗 CPU。

asyncio vs threading：
threading：OS 内核决定什么时候切换（抢占式），切换开销大（涉及内核态）。
asyncio：Python 代码在 await 处主动让出（协作式），切换在用户态完成，开销小得多。

结论：IO 密集且连接数多 → asyncio（数万连接都没有问题，epoll 底层支持）。
CPU 密集或需要真并行 → multiprocessing。

5. 四种并发武器怎么选

场景选哪个原因
大量网络请求（HTTP 推理请求、API 调用）asyncio单线程 + epoll 底层，数万连接无压力。GIL 不影响（等网络 IO 时释放）。
CPU 计算（tokenize、detokenize、后处理）multiprocessing需要真并行。GIL 下 threading 等于单核。
GPU 计算 + CPU 控制混合asyncio + multiprocessingasyncio 管请求调度（IO），multiprocessing 管 GPU worker 池（计算）。
vLLM 就是这样。
简单的定时任务、轻量后台threading启动快，够用。但要小心 data race。
进程间数据传递Queuemultiprocessing.Queue 是标准方式。底层 pipe，自动处理锁和序列化。

6. 在 AI Infra 里的实战

vLLM 的架构（简化）

┌─────────────────────────────────────────┐ │ 主进程 (asyncio event loop) │ │ asyncio HTTP server (aiohttp) │ │ ├─ 接收推理请求 │ │ └─ 通过 Queue 发给 GPU worker │ ├─────────────────────────────────────────┤ │ GPU Worker 进程 (multiprocessing) │ │ while True: │ │ request = queue.get() │ │ result = model.forward(request) ← 跑在 GPU │ │ queue_out.put(result) │ └─────────────────────────────────────────┘

为什么这么设计？

  • 主进程用 asyncio：同时处理成千上万的 HTTP 连接，不阻塞。如果有请求在等 GPU 计算结果，asyncio 可以先去接其他请求。
  • GPU Worker 用独立进程：PyTorch 模型跑在 GPU 上时释放 GIL，但为了隔离显存和避免 GIL 干扰控制流，单独开进程更安全。每个进程绑定一块 GPU。
  • Queue 做桥梁：主进程放请求，worker 取；worker 放结果，主进程取。

SGLang 的多 worker 模式

类似设计：一个 router 进程（asyncio）接收请求，分发到多个推理 worker 进程（multiprocessing），每个 worker 管理自己的 GPU。

数据加载的 Pipeline

训练时常见模式：

  • 2-4 个 prefetch 进程（producer）：从磁盘读数据，预处理，放进 multiprocessing.Queue
  • 1 个训练进程（consumer）：从 Queue 取已经预处理好的 batch，直接送 GPU
  • 效果：磁盘 IO 和 GPU 计算重叠——气泡（bubble）缩小了

7. 概念检查

Q1. 线程 A 在执行 time.sleep(1) 时，线程 B 能跑吗？为什么？
Q2. 为什么 asyncio 能在单线程里实现"同时"处理几百个连接？这和 threading 的区别是什么？
Q3. 推理引擎里，为什么用 multiprocessing 而不是 threading 来做 GPU 推理 worker？
Q4. 下面这段代码的结果是什么？（考察 GIL 对 CPU 计算的影响）
import threading, time

def count():
    for i in range(50_000_000):
        pass

t1 = threading.Thread(target=count)
t2 = threading.Thread(target=count)
start = time.time()
t1.start(); t2.start()
t1.join(); t2.join()
print(time.time() - start)
# 和串行的比：更快？更慢？差不多？
点击展开答案（先自己答再看）

A1：能。sleep() 是 IO 操作，Python 执行器在进入 IO 前释放 GIL，线程 B 可以拿到 GIL 运行。这是 GIL 的关键行为——IO 操作不占 GIL。

A2：asyncio 单线程里不是"同时做"，而是"不等待"——协程在 await 处主动让出控制权，event loop 切到另一个就绪的协程。区别：threading 是 OS 在任意时刻抢占切换（不可预测，开销大）；asyncio 是代码在 await 处主动让出（可预测，开销小）。asyncio 底层用 epoll 监视 fd——跟 Lesson 0002 一样。

A3：两个原因。(1) GPU 显存隔离——每个进程有自己的 CUDA context，一个进程崩了不影响其他 worker。(2) GIL——model.forward() 虽然释放 GIL，但 Python 层的调度逻辑、response 组装等 CPU 操作受 GIL 限制，用独立进程可以真并行。

A4：和串行差不多，甚至略慢。因为 count() 是纯 CPU 密集的 Python 代码，不释放 GIL。两个线程轮流持有 GIL，每个时刻只有一个人跑——实际效果和单线程一样，加上线程切换开销反而更慢。把 threading 换成 multiprocessing.Process 才会真正变快（约 2 倍）。

8. 实践：手写多进程数据 Pipeline

下面是一个 skeleton：实现 "producer 进程读数据 → worker 进程处理 → consumer 进程写结果" 的三阶段 pipeline。填上 TODO 跑通。

# data_pipeline.py — 多进程数据 pipeline skeleton
from multiprocessing import Process, Queue

def load_data(in_q: Queue, out_q: Queue):
    """从 in_q 拿原始数据, 处理后放入 out_q"""
    while True:
        item = in_q.get()
        if item is None:   # 哨兵
            out_q.put(None)
            break
        # TODO: 对 item 做某种处理（比如 item * 2）
        # out_q.put(...)

def write_result(out_q: Queue):
    """从 out_q 拿处理后的数据, 打印"""
    while True:
        item = out_q.get()
        if item is None:
            break
        print(f"result: {item}")

if __name__ == "__main__":
    in_q = Queue()
    out_q = Queue()

    # 放 10 个原始数据
    for i in range(10):
        in_q.put(i)

    loader = Process(target=load_data, args=(in_q, out_q))
    writer = Process(target=write_result, args=(out_q,))
    loader.start()
    writer.start()

    # 等 loader 结束
    loader.join()
    # 给 writer 发哨兵
    in_q.put(None)  # 这里有问题——loader 已经结束了！想想怎么改
    writer.join()
✏️ 任务
  1. 填上 load_data 的 TODO（把 item 翻倍）
  2. 发现上面 in_q.put(None) 的 bug 了吗？loader 已经 join 了，再往 in_q 放哨兵没用。正确的做法是：load_data 收到 None 后放 None 到 out_q，writer 收到 None 后退出。不需要主线程再放哨兵。
