从 socket() 到 accept()：一个 TCP Server 是怎么建起来的

不需要 C 基础。会用 Python 就能看懂。读完这一页，你就知道 vLLM 推理 server 底层的 "listen socket + conn socket" 模型是什么。

0. 首先回答：你打开文件、读文件的时候，电脑内部到底发生了什么？

因为答案直接决定了 socket 是什么。

假设你在 Python 里写：

f = open("hello.txt", "r")
content = f.read()
f.close()

这三行代码背后，操作系统（Linux 内核）做了一个关键设计：它不给你这个文件本身，只给你一个号码牌。

你的程序 Linux 内核 ───────── ───────── ┌─────────────────────┐ f = open("hello.txt") ──→ │ 找到 hello.txt │ ←── │ 分配第 3 号牌子给你 │ 返回 3 └─────────────────────┘ f.read() ──→ "帮我读 3 号牌子对应的那个文件" ←── 把文件内容拷给你 f.close() ──→ "我还 3 号牌子, 不读了"

这个号码牌就是 文件描述符 (file descriptor)，简称 fd。它是一个非负整数。

Linux 的核心设计哲学就是一句话：一切皆文件。你要操作什么东西（真文件、网络连接、管道、设备），内核就给你派一个 fd，之后所有读/写/关操作都用这个整数。

fd 0 = 键盘输入 (stdin) ← 程序一启动就开着 fd 1 = 屏幕输出 (stdout) fd 2 = 错误输出 (stderr) fd 3 = 你自己 open() 的第一个东西 fd 4 = 你自己 open() 的第二个东西 ...
去银行取号。柜员不直接管你叫"张三"，她叫"第 37 号"。这个 37 号就是 fd——一个简短的数字，用来唯一代表你（文件/连接/设备）。之后你每一次被叫到（read/write），都是喊这个号。

记住这个模型之后，socket 就很好理解了。

1. socket() — 建一个通信用的"空壳"

我们现在想写一个 server 程序，监听网络上的请求。第一步：socket()。

import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)

逐字拆解

代码含义
socket.socket(...) 请操作系统（内核）给我建一个通信用的"空壳"，并返还一个 fd 让我能引用它。
AF_INET 地址家族 = AF_INET，意思是"我用 IPv4 地址"。比如 127.0.0.1 就是一个 IPv4 地址。
另一种常见的是 AF_UNIX——同机器上两个进程之间通信，不需要走网卡，用 unix domain socket 更快。
SOCK_STREAM 用 TCP 协议。TCP 的特点是：可靠（确保送达）、有序（先发的先到）、字节流（不帮你分消息边界）。
另一种是 SOCK_DGRAM = UDP，不可靠但快。

调用后，内核返回一个整数——这就是 sock 对应的 fd。此刻这个 socket 还没有地址，还没有绑定端口，只是内核里一个"新建的通信端点"。

为什么 vLLM 里你常听到 "TensorPipe / ZMQ / NCCL / shared memory" 这些词？因为 tensor parallel 通信时： 同机两个 GPU 之间不需要走 TCP 协议栈（太慢），用 AF_UNIX（unix domain socket）甚至直接共享内存； 跨机通信 才走 TCP + NCCL 的 RDMA 通道。你后面 Phase 4 会学 NCCL 为什么能绕过内核直接写远程 GPU 显存。
socket.socket() 返回的是一个 Python 对象（有方法有属性），不只一个整数。但本质上这个 Python 对象里面包了一个 C 级别的 fd 整数。你可以用 sock.fileno() 直接拿到这个整数。

2. bind() — 给这个空壳贴上地址

sock.bind(("127.0.0.1", 9000))

socket() 建了一个空壳，谁都可以往它发数据——但"谁"是谁？网络上的数据包到达主机后，内核看什么字段来决定发给哪个 socket？

看 (IP 地址, 端口号) 这个二元组。bind() 就是告诉内核：以后发到 127.0.0.1:9000 的数据包，请交给这个 socket。

socket() = 你租了一间毛坯房。
bind() = 你在门口挂上门牌 "长宁路 100 号，9000 室"。之后所有寄到 "长宁路 100 号 9000 室" 的信件（数据包），邮局（内核）都知道应该往这间房投。
参数含义
"127.0.0.1"只接受发给本机的连接。如果你想让局域网内其他机器也能连，绑 "0.0.0.0"（监听所有网卡）。
9000端口号。0-1023 是系统保留端口（比如 80 是 HTTP），大于 1024 的可以随便选。

3. listen() — 打开"迎客模式"

sock.listen(128)

此前，这个 socket 只是一个有地址的通信端点，还不能接客户端。调了 listen() 之后，有两件事改变：

  1. 这个 socket 被标记为 "server socket"。只有 listen socket 才能调 accept()。
  2. 内核开始维护一个"已完成握手队列"（backlog）。参数 128 就是这个队列的长度上限。
listen() = 你把毛坯房装修成了营业厅，开了叫号系统。128 = 你最多让 128 个客户在等候区排队，满 128 之后新来的客户，内核替你给人家回复 "我现在满了，等会再试"。

关键认知：listen 之后，内核就已经开始在后台帮你接 TCP 三次握手了。你的程序甚至还没调 accept()，内核就已经替你发了 SYN+ACK。这样当你的程序终于调 accept() 时，很可能连接已经建好，只是放在内核队列里等你来拿。

128 这个 backlog 值在面试里可能问到。实际上内核会把它放大（Linux 上默认乘 1.5），但太多 pending 连接意味着你的 server 处理速度赶不上需求——要么扩进程，要么优化 accept 速度。

4. accept() — 从等候区叫下一个客户

这是你之前最搞不清的一步。现在我把它内部机制说清楚。

conn, addr = sock.accept()

accept() 不是建立连接，连接早被内核建好了。它做的事情非常简单：

内核的 "已完成队列" （backlog） ┌─────────────────────────────────┐ │ [client A: fd=12 ready] │ ← 内核已经帮这个客户端完成了三次握手 │ [client B: fd=14 ready] │ │ [client C: fd=17 ready] │ └─────────────────────────────────┘ ↓ accept() — 你的程序喊 "下一个" ↓ 返回 conn (fd=12), addr (客户端的 ip:port) fd=12 从队列中移除

逐行看：accept 到底发生了什么

Python 代码: conn, addr = sock.accept() — 逐行含义
●
你的程序调用 sock.accept() — 这是一次系统调用 (syscall)，控制权从你的程序交给 Linux 内核。
●
内核检查 sock 对应的 listen backlog 队列。
●
队列为空？ 默认行为是 阻塞——你的程序暂停在这行，什么事都不干，等有客户连进来。如果 socket 设置了非阻塞模式 (setblocking(False))，则立刻返回一个错误 EAGAIN（"现在没人，你先干别的"）。
●
队列有连接？ 内核从队首摘一个连接，给它分配一个新的 fd 整数（比如 fd=12），并把客户端的 IP 和端口号也记下来。
●
返回给你的程序：conn = 一个新的 Python socket 对象（封装了 fd=12），addr = ("127.0.0.1", 54321)。
最关键的误会：很多人以为 accept() 返回的 conn 就是原来的 sock，只是"激活了一下"。不对。listen socket (sock) 和 accept 返回的 connector socket (conn) 是两个完全不同的 fd，代表两个完全不同的东西：

sock (listen fd)：只做一件事——"有没有新客户来了？" 你不往它里面读数据，你从它身上取连接。
conn (connector fd)：只做一件事——跟一个具体客户收发数据。你往它里面 read/write。

为什么不能复用 listen fd？

因为一个 server 要同时服务 100 个客户端。每个客户端有自己的发送速率、自己的传输状态、自己的序列号。如果用同一个 fd 操作所有客户端，你发出一句话 "Hello client 27"，内核怎么知道发给 100 个客户端里的哪一个？

所以设计成：一个连接 = 一个 fd。同时有 100 个客户端 = 1 个 listen_fd + 100 个 conn_fd = 你的进程里开着 101 个 fd。

你的 server 进程 (fd 表) ┌─────────────────────────────────┐ │ fd 0 = stdin │ │ fd 1 = stdout │ │ fd 2 = stderr │ │ fd 3 = sock (listen socket) │ ← 只 accept, 不 read 数据 │ fd 4 = connA (客户端 A) │ ← 可以 recv/send │ fd 5 = connB (客户端 B) │ │ fd 6 = connC (客户端 C) │ │ ... │ └─────────────────────────────────┘

5. 四步串联在一起：一个完整的、可跑的 TCP Echo Server

下面这 25 行代码就是上面 4 步的串联。它做的事情：收到什么就回什么（echo）。

import socket

# 1. 建一个空壳
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)  # 让端口可重用

# 2. 贴上地址
sock.bind(("127.0.0.1", 9000))

# 3. 开迎客模式
sock.listen(128)
print("server listening on 127.0.0.1:9000")

while True:
    # 4. 从等候区叫下一个客户
    conn, addr = sock.accept()
    print(f"new connection from {addr}")

    # 5. 跟这个客户收发数据
    data = conn.recv(4096)       # 从 conn_fd 里读
    conn.sendall(data)           # 原样写回去
    conn.close()                 # 还回这个 fd
    print(f"closed {addr}")
这个 server 有一个致命缺陷：while 循环一次只能处理一个连接。它在跟 A 收发数据时，B 哪怕已经在 backlog 里排到队了，也必须等 A 的 conn.close() 之后再下一轮 accept()。这就是下一课要解决的问题——如何同时处理多个客户端（io 多路复用）。

6. 概念检查（确认你跟上了再往下走）

Q1. 下面这个描述哪里错了？ "一个 server 只有一个 socket，客户端连进来后 accept 直接把这个 socket 变成可以通信的状态。"
Q2. 同时有 5 个客户端连接，你的进程里共有几个 socket/fd？分别是什么？
Q3. listen(128) 的参数 128 控制什么？设成 5 和设成 1000 的区别是什么？
点击展开答案（先自己答再看）

A1：错了。listen socket 不会"变成"conn socket。accept 是创建一个全新的 fd：listen socket 仍然存在（继续接新连接），新 fd 负责跟这个客户通信。它们是两个不同的 fd。

A2：6 个。1 个 listen socket（接新连接）+ 5 个 connector socket（跟各自的客户端通信）。

A3：控制内核 backlog 队列的长度（完成握手但尚未被 accept 取走的连接数上限）。设 5 的话，第 6 个同时在握手的客户端会被内核拒绝；设 1000 则缓冲更大，但内存占用更多。关键是：backlog 太长意味着你的 accept 速度跟不上连接速度——根本解决办法不是调大 backlog，而是加快 accept 或加进程。

8. 这篇文章跟 AI Infra 面试有什么关系

  1. vLLM 的 AsyncLLMEngine 底层就是用一个 event loop 管理一堆 socket fd（HTTP/gRPC 请求、TP 通信）。你如果在简历上写"熟悉 vLLM 源码"，面试官问你 "vLLM 怎么同时处理推理请求和 health check"，本质就是考这套多 fd 管理。
  2. NCCL 通信 里每个 rank 之间的通信通道就是 socket + 内存映射。理解 fd 这个抽象之后，你再看 NCCL 源码才知道它怎么复用同一个 fd 来做 ring all-reduce。
  3. 系统设计题 "设计一个 LLM 推理平台"——你至少需要画清楚：负载均衡→推理 server（如何并发？）→ GPU 间通信（走什么协议？）。答案全是从今天这课开始的。
