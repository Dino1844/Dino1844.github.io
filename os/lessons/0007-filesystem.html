1. inode：文件的"身份证"

核心

inode · Index Node

inode 包含关于一个文件的一切——除了文件名和文件内容。权限（rwx）、所有者（uid/gid）、大小、时间戳（atime/mtime/ctime）、数据块指针数组——都在 inode 里。文件名不在 inode 里——它存在目录项里。

为什么文件名不存 inode

因为一个文件可以有多个名字（硬链接）。`ln file file2` → file 和 file2 指向同一个 inode——inode 里的 link count 从 1 变成 2。`rm file` → link count 降到 1（文件还在）。`rm file2` → 0 → 文件真正删除（inode 和数据块全部释放）。硬链接让"文件名只是一个指向 inode 的指针"变得具体。

范式 #1（间接层）：inode 号是文件名到数据块的间接层

2. 多级索引：小文件快、大文件支持

inode 里的数据块指针数组大小固定（ext4: 15 个指针，60 字节）。15 个指针怎么指向几百 GB 的文件？多级索引：

  • 前 12 个：直接指针——直接指向数据块。4KB/块 × 12 = 48KB（~大多数文件）
  • 第 13 个：间接指针——指向一个装满指针的块（1024 个指针 × 4KB = 4MB）
  • 第 14 个：双间接——指向的块里每个指针指向一个间接块（1024² × 4KB ≈ 4GB）
  • 第 15 个：三间接——1024³ × 4KB ≈ 4TB

效果：小文件（<48KB）→ 前 12 个直接指针就够了——一次磁盘访问（inode 本身）。大文件才触达间接块。这是常见情况优化——大多数文件是小文件（代码、配置、.txt），少数大文件（视频、数据库）付出间接块的开销。范式 #2（缓存）进一步加持：inode 本身在 inode cache 中，热文件的直接指针几乎不需要磁盘 I/O。

3. 目录 = 名字到 inode 号的映射

目录也是文件——它的"数据"是一个表：(name, inode_number) 对。`ls -i` 显示 inode 号。`open("/dir/file")` 的内核流程：读 "/" 的 inode（inode 2——root inode）→ 在数据块里找 "dir" → 得到 inode 号 → 读 dir 的 inode → 在数据块里找 "file" → 得到 file 的 inode → 返回 file 的 inode。每一步都可能触发磁盘 I/O——dentry cache（目录项缓存）把常用路径缓存在内存里，让大部分 `open` 不需要磁盘 I/O。

4. FFS：为磁盘几何优化的文件系统

FFS（Fast File System）的核心思想：把相关的数据放在磁盘上相近的位置——减少磁头移动（seek）。

  • 柱面组（cylinder group）：磁盘分成多个柱面组，每个组有自己的 inode 区和数据块区
  • 目录放一起：同一目录下的文件 inode 在同一个柱面组——`ls -l` 不需要跨组 seek
  • 大文件跨组：避免一个大文件吃光一个柱面组的空间，把别的文件挤到别的组强制 seek

SSD 时代 FFS 的 seek 优化不再重要（无机械结构），但数据局部性仍然重要——同一目录的文件更可能一起被读取（空间局部性 → read-ahead 更有效）。

5. 崩溃一致性：写一半断电怎么办

核心问题

崩溃一致性 · Crash Consistency

文件系统的很多操作需要更新多个磁盘块（inode bitmap、inode、数据 bitmap、数据块——四个位置）。如果在四个更新之间断电 → 磁盘上的数据结构不一致。

经典问题：创建一个文件。需要：(1) 在 inode bitmap 标记 inode 已用；(2) 初始化 inode；(3) 在数据 bitmap 标记数据块已用；(4) 把 (name, inode#) 写入目录。如果顺序是 1→2→4→3，在 4 和 3 之间断电 → 目录指向 inode，inode 看起来 OK（bitmap 标记了），但 inode 指向的数据块 bitmap 说"这个块是空的"——这之后如果另一个分配把这个块给了别的文件 → 两个文件指向同一数据块（数据损坏）。

fsck（文件系统检查）

在挂载（mount）文件系统时扫描所有 inode 和 bitmap——修复不一致。例如：inode 标记已用但 bitmap 说未用 → 把 bitmap 改回来。数据块 bitmap 标记已用但没有任何 inode 指向它 → 释放。
问题：fsck 需要扫描整个文件系统——对 TB 级磁盘可能需要几分钟到几十分钟。不可接受。

6. 日志与 COW：两种解法

6.1 日志（Journaling）——ext3/ext4 的答案

日志的三步

① 写日志（journal write）：把要改的所有块的旧内容+新内容写到日志区（磁盘上预留的连续区域——顺序写、快！）
② 提交日志（journal commit）：写一个 commit 记录——"以上日志内容已完整"
③ 检查点（checkpoint）：把日志里的新内容写到文件系统的实际位置（随机写）
恢复：重启后检查日志——有 commit 的 → 重放（replay）；没有 commit 的 → 丢弃（没影响原始数据）

ext4 的 data=ordered 模式（默认）：元数据写日志，数据直接写原位置——但在元数据提交前数据必须先到位。"元数据永远不会指向未写入的数据"——最严重的崩溃一致性错误（上面的"两个文件指同一块"）被消除了。

范式 #4 · 批处理（日志版）

日志把多次随机写（改 bitmap + inode + 目录）合并成一次顺序写（日志追加）。顺序写比随机写快 ~10×（HDD 无 seek，SSD 无 4KB 随机写开销）。然后 checkpointer 在空闲时把日志批量写回原位置。批处理让"最重要的操作"（日志提交 = 顺序写）成为瓶颈路径上最快的操作。

6.2 COW（Copy-on-Write）——ZFS/Btrfs 的答案

和内存 COW（0004 §5）同一哲学——从不原地覆写：

  1. 要改一个块 → 把新内容写到一个新的空闲块
  2. 更新指向它的上一层块 → 也写到新块 → 递归到根
  3. 最后原子地切换根指针（uberblock）

效果：崩溃后 → 旧树完全无损（因为根指针还是旧的）。新的 uberblock 有校验和——不完整的新树直接被忽略。而且旧树天然是 snapshot——时间和空间开销几乎为零。

日志 vs COW 是两种哲学：日志 = "坏了能修好"（事后恢复），COW = "永远不会坏"（事前防止）。日志的瓶颈在 checkpoint（随机写回到原位置），COW 的瓶颈在碎片化（树永远在长——inode 和数据块不在一起了）。没有银弹。

8. 推导与自测

P1 · inode 指针覆盖范围 L1

4KB 块、4 字节指针。计算直接（12 个）、单间接、双间接、三间接各能覆盖的最大文件大小。

▸ 解答
直接：12 × 4KB = 48KB。单间接：1024 × 4KB = 4MB。双间接：1024² × 4KB = 4GB。三间接：1024³ × 4KB = 4TB。合计 ≈ 4TB + 4GB + 4MB + 48KB。
P2 · 崩溃场景分析 L2

(a) 删除一个文件的磁盘更新包括哪些块？(b) 如果先删目录项再释放 inode，中间断电 → 有什么问题？(c) 如果先释放 inode 再删目录项呢？

▸ 解答
(a) 更新目录数据块（移除 name→inode 条目）、更新 inode bitmap（标记释放）、(可选) 更新数据 bitmap（释放数据块）、(可选) 更新 inode（link count--，如果为 0 才真正释放）。
(b) 目录项先删 → 目录里没有文件了 → 但 inode 还标记为使用中 → 空间泄漏（inode 和数据块被标记占用但无文件指向它——永远无法再被使用）。
(c) inode 先释放 → 新文件可能被分配到这个 inode → 但目录项还指向这个 inode → 旧路径指向新文件（安全灾难）。
