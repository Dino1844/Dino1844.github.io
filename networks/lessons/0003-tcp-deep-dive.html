第 4 课告诉我们：IP 层只做「尽力而为」的转发——包可能丢了、可能重复了、可能后发先至。这就是 TCP 存在的全部意义：在不可靠的 IP 层之上，给应用程序一个"数据绝对不会出问题"的幻觉。

🎯 本课目标：理解 TCP 如何在不可靠的 IP 之上，实现「不丢、不乱、不重复」的可靠字节流传输。含三次握手、序列号/ACK、滑动窗口流量控制、拥塞控制（慢启动/拥塞避免/快速恢复）、四次挥手与 TIME_WAIT。TCP 是面试最高频的考点，值得投入最多时间。

1. TCP 要解决哪四个问题？

IP 层给了你一个「不可靠的包投递服务」。TCP 要在上面造出：

问题IP 层的问题TCP 的解法机制
丢包路由器缓冲区溢出，包被丢弃可靠传输ACK + 超时重传
乱序不同包可能走不同路径有序交付序列号重排
重复重传可能导致重复包去重序列号去重
流量/拥塞发太快会压垮接收方或网络流量控制 + 拥塞控制滑动窗口 + 拥塞窗口

这四个问题，序列号（Sequence Number）是解决前三个的基础。拥塞控制是 TCP 最精巧的部分——也是最常被问到的。

2. 三次握手 —— 为什么要三次？

TCP 是面向连接的：传输数据之前，双方必须先建立连接。这个过程叫三次握手：

客户端（主动打开）
服务器（被动监听）
SYN, seq=x "我想和你建立连接，我的初始序列号是 x"
SYN-SENT  ·                          SYN-RCVD
SYN+ACK, seq=y, ack=x+1 "好的，我的初始序列号是 y，我收到了你的 x"
ACK, ack=y+1 "我收到了你的确认"
ESTABLISHED  ·                       ESTABLISHED

为什么不是两次？

核心原因：防止旧的、延迟的 SYN 包导致错误建立连接。

想象一个场景：客户端发了一个 SYN，但它因为网络拥塞在半路上滞留了很久。客户端以为丢了，重发了一个 SYN，这次正常完成了通信。如果只用两次握手（客户端发 SYN → 服务器回 SYN-ACK 就算连接建立），当那个旧的、迟到的 SYN终于到达服务器时，服务器会单方面认为连接建立了——但客户端根本不知道这事，白白占用服务器资源。

三次握手让双方都确认了对方的收发能力：

  • 客户端通过收到 SYN-ACK 确认：我发的 SYN 服务器收到了，服务器也能发
  • 服务器通过收到 ACK 确认：我发的 SYN-ACK 客户端收到了
🔑 另一个关键作用：同步初始序列号。三次握手不仅建立连接，还交换了双方的初始序列号（ISN）。序列号不是从 0 开始——而是从随机值开始，这是为了安全（防止序列号预测攻击）和防止与旧连接的包混淆。

3. 序列号与 ACK —— 可靠传输的基石

TCP 把数据看作一个字节流。每个字节有一个编号——序列号。确认号的意思是：「我已经收到了前 N 个字节，下一个期待第 N+1 号字节。」

这不同于「第几个包」的思维模型。TCP 的 ACK 是累计确认：ACK 1000 的意思是「0–999 号字节全部收到」。如果收到了 1000–1999 但中间缺了 500–999，ACK 依然是 500——不会跳过未收到的部分。

主机 A seq=1, 100 bytes → 主机 B B 收到字节 1–100
seq=101, 100 bytes → B 收到字节 101–200
seq=201, 100 bytes → B 收到字节 201–300
ack=301 ← "前 300 字节收到了，下一个期待 301"

如果 B 只收到了 seq=1 和 seq=201（丢了 seq=101 那个包），B 的 ACK 仍然是 101。这就会触发 A 重传 seq=101。

⚠️ 常见误区：ACK 号不等于 seq+1。ACK 号 = seq + 收到的字节数。如果 seq=100 且发了 200 字节，正确的 ACK 是 300。

4. 滑动窗口 —— 我不要你发太快

发送方不能无限制发送。接收方有一个接收缓冲区，如果满了还要硬塞，数据就丢了。TCP 用滑动窗口做流量控制——接收方在 ACK 中告诉发送方「我的窗口还有多大」。

5. 拥塞控制 —— TCP 最精妙的设计

流量控制管的是「接收方会不会被淹死」。拥塞控制管的是「网络管道本身会不会被堵死」。

发送方维护一个拥塞窗口（cwnd）——它猜测网络目前能承受多少「在飞」的数据。实际发送量 = min(接收方窗口, 拥塞窗口)。

慢启动（Slow Start）

TCP 连接刚建立时，它不知道网络能承受多少流量。不能一上来就灌满。慢启动的策略是从 1 个 MSS 开始，指数增长：每收到一个 ACK，cwnd + 1。结果是每个 RTT 翻一倍。

12345 6789× 1011121314
慢启动（指数） 拥塞避免（线性） 快速恢复 丢包 (×)

虽然是"指数"增长，但起点很低（1 MSS），所以叫"慢启动"——慢在起点，快在增速。

拥塞避免（Congestion Avoidance）

cwnd 不能永远指数增长。到达慢启动阈值（ssthresh）后，进入拥塞避免阶段——每 RTT 只加 1 MSS（线性增长），谨慎试探瓶颈。

💡 为什么三个重复 ACK 就算轻微拥塞？一个重复 ACK 可能只是包乱序了。两个也可能是。但连续三个重复 ACK 几乎不可能只是因为乱序——后面一定有个包丢了。此时不必等 RTO 超时（几百毫秒），直接重传 + 减半 cwnd。这就是"快速"二字的含义。

6. 四次挥手 —— TIME_WAIT 之谜

TCP 是全双工的：数据可以向两个方向独立流动。断开连接需要双方各自关闭自己的发送方向，所以是四次：

主动关闭方
被动关闭方
FIN, seq=u "我说完了，不再发数据了"
ACK, ack=u+1 "知道了"
半关闭：客户端→服务器方向已关闭，服务器可能还有数据要发
FIN, seq=v "我也说完了"
ACK, ack=v+1 "知道了"
TIME_WAIT (等 2MSL)                 CLOSED

为什么有 TIME_WAIT？必须等 2MSL？

主动关闭方发出最后一个 ACK 后，进入 TIME_WAIT 状态，等待 2MSL（Maximum Segment Lifetime，约 60 秒）：

  1. 防止最后一个 ACK 丢失。如果 ACK 丢了，被动方会重发 FIN。TIME_WAIT 让主动方还能回复 ACK
  2. 让旧连接的残余包在网络上消亡。等 2MSL 确保这个连接的所有包都过期了，新连接不会混淆
⚠️ 面试高频：服务端如果看到大量 TIME_WAIT 连接，通常是短连接太多或 keep-alive 没开。大量 TIME_WAIT 会耗尽端口号。

7. TCP vs UDP —— 什么场景不用 TCP？

TCPUDP
连接面向连接（三次握手）无连接（直接发）
可靠性保证送达、有序、不重复不保证任何事
速度握手 + ACK 有开销零开销
头部大小20–60 字节固定 8 字节
流量/拥塞控制有无（应用层自己管）
适用场景Web 浏览、文件传输、邮件视频通话、DNS、在线游戏、IoT

选择 UDP 的场景有几个共同点：容忍丢包但不容忍延迟（视频/游戏）、需要广播/组播、或者想在应用层自己管可靠性（如 QUIC/HTTP3）。

📚 补充：可靠传输的算法基础 —— TCP 为什么这样设计

TCP 的可靠传输不是凭空发明的。在它之前，学术界已经研究了三种经典的可靠传输算法，TCP 融合了它们的优点。理解这些基础算法，TCP 的序列号、ACK、滑动窗口就不再是"记忆"而是"推导"。

Stop-and-Wait（停等协议）

发一个包 → 等 ACK → 收到 ACK 再发下一个。如果超时，重发同一个包。

发送方：发 P0 ──→ 等... ←── ACK0 → 发 P1 ──→ 等... X 丢了！ 超时！→ 发 P1 ──→ ←── ACK1

问题：利用率极低。假设 RTT=30ms，带宽=1Gbps，包大小=1KB。Stop-and-Wait 的实际吞吐量 = 1KB/30ms ≈ 267Kbps——只用到了 1Gbps 的 0.026%。大量时间花在"等 ACK"上。

💡 管道化（Pipelining）：解决利用率低的方法很简单——不等 ACK 回复，连续发多个包。这就是 Go-Back-N 和 Selective Repeat 的思路。

Go-Back-N（回退 N 步）

发送方维护一个大小为 N 的窗口，可以连续发窗口内的所有包，不等 ACK。但接收方只接受按序到达的包——乱序的包直接丢弃。如果包 k 丢了，发送方超时后必须从包 k 开始重传所有后续包（即使后面的包已经成功到达）。

窗口大小 N=4
发送方：发 P0 → P1 → P2 → P3 （全部在飞）
接收方：← ACK0 ← ACK1 P2 丢了！ 收到 P3 → 丢弃 P3 → 重复 ACK1
发送方：超时！ 重传 P2 → P3 → P4 → P5 （回退到 P2，全部重发）

问题：重传浪费。P3 明明已经到了，因为乱序被丢弃，还需要重传。当丢包率高时，Go-Back-N 退化到接近 Stop-and-Wait。

Selective Repeat（选择重传）

和 Go-Back-N 一样用窗口，但关键区别是：接收方缓存乱序的包。只有真正丢失的包才重传——不乱丢已经收到的。

发送方：发 P0 → P1 → P2 → P3
接收方：← ACK0 ← ACK1 P2 丢了 → 缓存 P3 → 发 SACK(0-1, 3)
发送方：收到 SACK → 只重传 P2
接收方：P2 到了 → 拼上 P3 → 一次性交付 P0 P1 P2 P3

TCP 是怎么融合的？

TCP 机制来自哪个算法改进
累计 ACK（ACK N 表示 N-1 以前全收到）Go-Back-N 风格—
只有丢包才重传（不重传已收到的）Selective Repeat 风格通过 SACK 选项支持选择性确认
单一定时器（一个窗口只设一个超时计时器）Go-Back-N 风格简化实现
快速重传（3 个重复 ACK 触发重传）TCP 独创不等超时，提前发现丢包

TCP 在实践上是 Go-Back-N 和 Selective Repeat 的混合体：默认用累计 ACK（Go-Back-N 的简单性），但加上 SACK（Selective Repeat 的效率），再叠加快速重传优化。这就是为什么它既简单、又高效。
