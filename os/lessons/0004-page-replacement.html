1. 缺页中断：Present bit = 0 的全部分支

MMU 在页表 walk 中发现某个 PTE 的 P=0 → 硬件触发缺页异常（page fault，#PF，x86 中断 14）。CPU 把引发缺页的虚拟地址存入 CR2 寄存器，然后跳到 OS 的缺页处理程序。

缺页处理程序的分支（Linux do_page_fault）

① 读 CR2 → 出错的虚拟地址。
② 检查地址合法性：如果地址在进程的 VMA（vm_area_struct）范围外 → SIGSEGV（真正的 segfault）。VMA 是进程通过 mmap/brk 向内核"申请"过的区域——没申请的地址访问就是非法的。
③ 检查权限：如果 VMA 是只读的但访问是写 → SIGSEGV（写保护页）。如果 VMA 不可执行但访问是指令取指 → SIGSEGV（NX violation）。
④ 合法的缺页——分配物理帧：
　• 真正的缺页（major fault）：页在 swap 里 → 从 swap 读回来（~ms 级延迟）
　• COW 缺页：页是 COW 的 → 复制一份（§5）
　• 按需调页（minor fault）：页还没分配过 → 分配新帧填零（~μs 级）
　• 文件映射页：页对应 mmap 的文件 → 从 page cache 读（~μs 到 ~ms）
⑤ 更新页表：把新分配的 PFN 写入 PTE，P=1，设置 R/W/U/D/A 等 bit → iret 返回 → CPU 重新执行引起缺页的指令。
关键洞察："合法缺页"是 OS 的正常操作路径。按需调页、COW、swap 全部靠缺页驱动——这不是"出错"，是"惰性机制被触发"。缺页是内存管理中最高频的内核路径之一。

2. 按需调页：不到用时不给帧

一个进程启动时，内核不为代码段和零初始化数据段（BSS）真的分配物理帧——只建 VMA，页表里 PTE 全部 P=0。进程第一次执行到代码或访问数据 → 缺页 → 内核才分配帧。这节省了大量物理内存——一个加载了 100MB 库但只用其中 1MB 函数的进程，只花 1MB 物理内存。

范式 #3 · 惰性求值（按需调页版）

核心思想：推迟物理帧的分配，直到真正需要时。not-yet-accessed = not-yet-allocated。不仅省内存，还让启动变快——进程创建时只需建 VMA + 页表壳子，不触碰物理帧。

还在哪里出现：COW（§5）、惰性 slab 分配、RCU（0006）、容器镜像的 overlayfs（0009）

3. 页替换算法：从 Belady 到时钟

物理内存满了，新缺页需要分配新帧。必须选一个已经在内存里的页换出去。选哪个？

核心问题

页替换 · Page Replacement

目标：最小化未来缺页次数。最优解（Belady's OPT）：换出"未来最长时间不会被访问"的页。这是完美的——但需要预知未来访问模式。它提供的是一个无法达到的上界。

算法演进

算法策略问题
FIFO换最早进来的Belady 异常——更多帧可能导致更多缺页
LRU换最久未用的完美模拟过去 = 缺页少——但每次访问都要更新排序，硬件不支持。纯软件实现 O(1) 需要大量硬件支持
时钟（Clock）循环扫描，给第二次机会LRU 的近似——用 A bit 判断"最近用过没有"，足够好且可实现

Belady 异常：给更多的帧，反而更多缺页

FIFO 独有的反直觉行为。页引用串 1,2,3,4,1,2,5,1,2,3,4,5：3 帧 → 9 次缺页；4 帧 → 10 次缺页。根本原因：FIFO 不关心页的"未来"，换出的页可能是马上要用的。LRU 和 Clock 没有这个异常——它们用"过去"近似"未来"，这种近似保证了栈性质（stack property）：N+1 帧的页集合一定包含 N 帧的页集合。

时钟算法（Clock / Second Chance）

帧围成环，手（指针）在环上转。当需要换出：

  1. 如果当前帧的 A bit = 0 → 换出它
  2. 如果 A bit = 1 → 清 A bit 为 0，手移到下一帧（给"第二次机会"）

效果：最近被访问过的页（A=1）会被跳过——近似 LRU，但不需要每次访问都更新排序。增强版时钟（考虑 D bit 避免换出脏页）：A=0,D=0 最佳、A=0,D=1 次之、A=1,D=0 再次之、A=1,D=1 最差。

范式 #5 · 机制/策略分离（页替换版）

机制：缺页中断 → 找空帧（或换出）→ 更新页表和 TLB。

策略：选哪一页换出。FIFO、LRU、Clock 是不同的策略，但它们共用同一套缺页/页表更新/磁盘 I/O 的机制。

Linux 实际：用了双链表 LRU 近似——active list + inactive list。页在被访问时在 active 和 inactive 之间移动，换出总是从 inactive 链表尾部选。比纯 Clock 更精细但原理相同。

4. 抖动与工作集

抖动（thrashing）：所有活跃进程的工作集之和 > 物理内存时，系统进入死亡漩涡——进程缺页 → 换出一页 → 被换出的那页恰好是另一个进程马上要用的 → 另一个进程也缺页 → 再换出 → 那个被换出的又是刚才那个进程要用的……CPU 在缺页处理（磁盘 I/O）上花的时间远超实际运行时间。

工作集（Working Set）：进程在最近 Δ 时间内访问过的页的集合。它是进程真正需要的内存量——如果分配给进程的帧数少于工作集，该进程会频繁缺页（抖动）。Denning 的工作集模型：OS 应该跟踪每个进程的工作集，只调度"工作集之和 ≤ 物理内存"的进程组合。

$$W(t, \Delta) = \{\text{page } p \mid p \text{ was accessed in } [t-\Delta, t]\}$$
抖动时你加 CPU 没用——换更快的 CPU 只让你更快地缺页。唯一的解法：加内存（物理扩容）或杀进程（OOM Killer——见 0001 P5 的讨论）或 swap out 整个进程（现代 Linux 很少用）。

5. 写时复制：fork 不真的复制

0002 §5 提到 `fork()` 不深拷贝页表——而是 COW（Copy-On-Write）：

COW 的完整流程

① fork 时：子进程复制父进程的页表，但所有页（父子进程的页）的 PTE 被标记为只读（R/W=0）。父子共享同一物理帧。页被标为 COW。
② 同时读：父子都能读（读不需要 R/W=1）→ 不需要复制 → 无额外缺页。大部分页在被写之前一直共享。
③ 写入触发：父或子写某共享页 → MMU 检查 R/W=0 → 缺页异常 → OS 检测到"这是 COW 页被写了" → 分配新物理帧 → 复制原帧内容 → 更新写入者页表的 PTE（R/W=1，指向新帧）→ 另一个进程的 PTE 保持只读（仍指原帧）。
④ exec 时：子进程 exec → 全新的地址空间 → 子进程的页表被全换 → 所有 COW 标记消失——子进程不会再去碰父进程的页 → 整个 COW 过程没有发生过一次真正的复制。
COW 是惰性求值（范式 #3）在内存管理中最漂亮的应用。"万一不需要呢？"——`fork+exec` 模式里子进程几乎从不写父进程的数据。COW 利用了缺页异常机制（写完才裂）和 MMU 的 R/W 保护，让 fork 从 O(内存大小) 变成 O(页表大小)——快了几个数量级。

6. 交换 + mmap：完整图景

现在可以画出完整的虚拟内存图景——每个虚拟页处于五种可能状态之一：

状态PTE P bit数据在哪访问行为
未分配0（也无 swap 位置）不存在→ segfault（不在 VMA 内）或 缺页分配填零帧
已分配·在内存1物理帧→ TLB 命中或走页表 → 正常访问
已分配·在 swap0（swap 位置存在）swap 分区/文件→ major page fault → 从 swap 读回物理帧
mmap 文件页0 或 1文件在磁盘→ 缺页 → 从 page cache 读（或磁盘 I/O → 放入 page cache）
COW 共享页1（R/W=0）物理帧（共享）读 → 正常；写 → COW 缺页 → 复制

mmap 的优雅：mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_PRIVATE, fd, 0) 把文件映射到虚拟地址——以后 `*(int*)addr` 就是读文件、`*(int*)addr = x` 就是写文件。内核在背后做缺页驱动的文件 I/O——和 swap 共用了同一套缺页 + page cache 机制。

停下来想一想：`MAP_PRIVATE` 的 mmap 写文件映射的页时，是写文件还是触发 COW？MAP_PRIVATE → COW 复制，写入不会回写文件（"私有"）。MAP_SHARED → 写入直接改原文件的内容（多个进程可以共享同一文件映射做 IPC）。

7. 推导与自测

P1 · Belady 异常验证 L1

页引用串 1,2,3,4,1,2,5,1,2,3,4,5。帧数 3 → FIFO 缺页 9 次。帧数 4 → 验证缺页次数（应得 10 次——Belady 异常）。

▸ 解答
3 帧 FIFO：1缺 2缺 3缺 → [123], 4缺换1 → [234], 1缺换2 → [341], 2缺换3 → [412], 5缺换4 → [125], 1命中, 2命中, 3缺换1 → [253], 4缺换2 → [534], 5命中。共 9 次。
4 帧 FIFO：1缺 2缺 3缺 4缺 → [1234], 1命中, 2命中, 5缺换1 → [2345], 1缺换2 → [3451], 2缺换3 → [4512], 3缺换4 → [5123], 4缺换5 → [1234], 5缺换1 → [2345]。共 10 次。
P2 · COW 节省了多少 L2

进程 P（占 200MB 物理内存）调用 fork()。(a) 无 COW 时，fork 需要多少物理内存？(b) 有 COW 时，fork 后立即需要多少额外物理内存？(c) 子进程随后 exec 了 /bin/ls（2MB），又实际需要多少额外物理内存？

▸ 解答
(a) 无 COW：200MB（子进程完整复制）。(b) 有 COW：~0 MB（共享——页表额外开销 ~几 MB）。(c) exec 后：子进程换新地址空间 → COW 共享消失。子进程实际用 ~2MB（ls）。父进程的 200MB 不变。总共额外 ≈ 2MB 而非 200MB——节省了 ~100×。
P3 · 抖动诊断 L3

你的服务器突然变慢，`top` 显示 CPU 的 %iowait 很高、但 CPU 使用率低。`vmstat 1` 显示每秒几千次缺页（`si`/`so` 列数字很大）。(a) 最可能是什么问题？(b) 你会怎么验证和解决？(c) 为什么 `kill -9` 某些进程后系统变快了？

▸ 解答
(a) 抖动——高缺页率 + 高 I/O wait + 低 CPU util = CPU 在等磁盘（缺页处理），不是在做有用功。
(b) 验证：`ps aux --sort=-%mem` 看谁占内存最多。`top` 看 RES（实际用物理内存）。如果所有大进程的 RES 之和 > 物理内存 → 确认抖动。解决：加内存、减少进程数、或使用 cgroup 限制内存（让 OOM killer 主动干预而非被动抖动）。
(c) 杀掉一些进程 → 它们占的物理帧释放 → 剩余的"活跃进程工作集之和"变小 → 可能重新 fit 进物理内存 → 缺页率骤降 → 系统恢复。这就是 OOM Killer 的"主动版"——它在系统进入抖动前就杀了进程。
