1. 为什么虚拟化内存

实际上只有一个物理内存（一堆 byte-addressable cell），但 OS 让每个进程以为自己有一整片连续的虚拟地址空间。为什么费这个劲？

理由没有虚拟化会怎样
保护进程 A 可以读写进程 B 的内存——读走密码、写坏数据
简化编程模型每个程序需要知道自己的物理地址范围。链接器和加载器必须协商物理地址布局——换一个程序就要重新链接
透明扩展不支持 swap——物理内存用完就真的完了；不支持 mmap——不能把文件映射到内存
虚拟内存不是"让内存变多"的魔术，而是"让每个进程有独立地址空间"的隔离墙。swap、mmap、COW 这些"超能力"都是隔离墙建好后才获得的附加馈赠。

2. 基址-界限：最简单的虚拟化

机制

基址-界限 · Base and Bounds

Dynamic Relocation
每个进程一对寄存器（base, bound）。每次访存：物理地址 = 虚拟地址 + base；如果虚拟地址 > bound → 异常。进程看到 [0, bound)，实际存在 [base, base+bound)。

优点与致命缺陷

✅ 硬件极简（两个寄存器 + 一个加法器 + 一个比较器）。✅ 可重定位——加载时只需设 base = 分配的物理起始地址。

❌ 内部碎片：进程的堆和栈之间的大量未用空间也占物理内存。❌ 不灵活——不能共享代码段（两个进程跑同一程序 → 各复制一份）。❌ 不能增长——栈爆了怎么办？

基址-界限的直接升级是三个 base/bound 对——代码段、堆、栈各一对。每一对覆盖地址空间的一个区域。这就是分段。

3. 分段：基址-界限 × 3

$$\text{segment} = \text{vaddr 的高 2 bit} \quad \text{offset} = \text{vaddr 的低位}$$ $$\text{phys} = \text{base}_{\text{segment}} + \text{offset}$$ $$\text{if offset} > \text{bound}_{\text{segment}} \rightarrow \text{segmentation fault}$$

分段解决了"堆和栈之间的空间浪费"——每段独立分配物理内存。而且可以共享代码段（两个进程的代码段 base 指向同一物理区域）。

但分段引入了一个更严重的问题：外部碎片。物理内存变成一堆不同大小的段，空闲总空间够但没一块连续的能装下一个新段——就像停车场里到处都是空位但没有连续 3 个。这就是"内存碎片化"——和磁盘碎片同一原理。

停下来想一想：为什么说"分段 = 每个段是一个基址-界限"？代码段的 bound = 代码段大小，堆段的 bound = 堆大小（可能增长）。栈段是反向增长的——所以栈段需要额外一个方向位（grows positive 或 grows negative）。

4. 分页：切碎内存，映射任意

核心机制

分页 · Paging

Page · Frame · Page Table
把物理内存切成固定大小的帧（frame），把虚拟地址空间切成同样大小的页（page）。页可以映射到任意帧——不需要连续。物理内存的一堆碎片帧可以被拼成一个进程看到的"连续"虚拟空间。

为什么分页胜过分段

  • 消除外部碎片：所有帧一样大——永远能找到空的帧。
  • 灵活共享：两个进程可以把各自的虚拟页映射到同一物理帧——共享库、共享内存的物理基础。
  • 惰性分配：可以"虚拟页存在但没映射到物理帧"——访问时才分配（demand paging，0004 §2）。

4.1 地址翻译：从虚拟地址到物理地址

虚拟地址分为两部分：虚拟页号（VPN）和页内偏移（offset）。偏移直接复制到物理地址的低位——映射只关心页号。

$$\underbrace{|\quad\quad\text{VPN}\quad\quad|}_{\text{查页表}}\;\underbrace{|\;\text{offset}\;|}_{\text{直接复制}} \quad\xrightarrow{\text{页表}}\quad \underbrace{|\quad\quad\text{PFN}\quad\quad|}_{\text{物理帧号}}\;\underbrace{|\;\text{offset}\;|}_{\text{不变}}$$

32 位地址空间，4KB 页（offset 12 bit），VPN 20 bit → 页表有 $2^{20} = 1,048,576$ 个条目。每个 PTE（page table entry）4 字节 → 一个进程的页表 = 4MB。100 个进程 = 400MB 光页表——这是分页的空间代价。

5. 页表的结构与 PTE 的每个 bit

数据结构

PTE · Page Table Entry

页表项
一个 PTE 不只是"物理帧号"——它的每个 bit 都在控制硬件行为。理解每个 bit 的语义 = 理解 MMU 的全部功能。

x86-64 PTE 的关键 bit（64 bit 中低 52 bit 可用）

Bit名称含义
0P (Present)页在物理内存中吗？0 → 缺页异常。其余 51 bit 可被 OS 随意用（如存 swap 位置）
1R/W0 = 只读，1 = 可写。写只读页 → 异常。COW 靠这个 bit + 缺页处理实现（0004 §5）
2U/S0 = 内核页（CPL=0 才能访问），1 = 用户页。内核内存对用户态不可见
5A (Accessed)该页被访问过（硬件自动置 1）。页替换算法用它判断"热度"（0004）
6D (Dirty)该页被写过（硬件自动置 1）。换出时如果 D=1，必须写回磁盘；D=0 直接丢弃
8G (Global)全局页——CR3 写时不刷其 TLB 项（内核页用）
63XD (NX)禁止执行——防止在数据页上执行代码（栈溢出防护的基础）
→ 0004: P=0 触发缺页 → demand paging/swap/COW → 0004: A/D bit = 页替换算法的数据来源 → 0009: NX bit = W^X = DEP 的硬件基础

一个非常巧妙的设计：Present bit = 0 时，其余 63 bit 由 OS 随意定义。Linux 把换出到 swap 的页的 swap 位置编码在这 63 bit 里——缺页处理程序可以直接从 PTE 里取出"去哪找回这页"。这让 swap 几乎零额外元数据开销。

6. TLB：页表的缓存

每次访存都要查页表 → 太慢。4 级页表一次翻译要 4 次内存访问（每级一次）→ 访存延迟 × 4。

TLB（Translation Lookaside Buffer）是 MMU 里的一个小型硬件缓存：VPN → PFN 的直接映射。典型大小：L1 TLB 32–64 条目（数据 + 指令分开）、L2 TLB 512–2048 条目。

TLB 命中 vs 未命中的完整路径

TLB 命中：虚拟地址 → MMU 查 TLB（VPN 匹配）→ 得到 PFN → 拼接 offset → 物理地址。延迟：~0.5–1 cycle（TLB 和 L1 cache 并行访问）。
TLB 未命中：MMU 走页表——四级页表需要 4 次内存访问（每级读一个 PTE）。延迟：~40–100 cycles。如果页的 Present bit = 0 → 缺页异常 → OS 处理（可能涉及磁盘 I/O，~10ms）。
TLB 命中率通常 > 99.9%，因为空间局部性——程序访问的地址在短时间内聚集在少数几个页内。

6.1 TLB 的关键问题：上下文切换时怎么办？

切换进程 = 切换页表。旧进程的 TLB 条目指向旧进程的物理页——新进程不能看。解法：

  1. 全刷：写 CR3 时硬件自动刷全部 TLB（除了 G=1 的全局页）——简单但贵
  2. ASID（Address Space ID）：每个 TLB 条目带一个 ASID 标签——只匹配当前进程的 ASID。不用刷 TLB——切换 ASID 即可。ARM 和较新的 x86（PCID）支持

范式 #2 · 缓存（TLB 版）

为什么 TLB 可以很小但命中率极高：空间局部性——程序在短时间内访问的虚拟地址集中在一个很小的页集合里（代码在几个页内循环、数据在几个页内读写）。TLB 只存"最近用过的"几十到上千个 VPN→PFN 映射就够了。这是缓存能工作的根本原因——访问模式不是均匀分布的。

还在哪里出现：buffer cache（0007）、dentry cache（0007）、CPU cache（0008）

7. 多级页表：时间换空间

回到 §4.1 的问题：32-bit 地址 + 4KB 页 = 4MB 的页表。64-bit 呢？4KB 页 + 48-bit 虚拟地址 = VPN 36 bit → $2^{36} = 68\text{B}$ PTE → 全映射需要 $68\text{B} \times 8\text{B} = 512\text{GB}$ 光页表。不可能。

但实际进程不会用完整个 48-bit 地址空间——大部分 VPN 没映射。多级页表的思路：不为"没在用"的区域分配页表——只分配有映射的子树。

核心

四级页表 · 4-Level Page Table

48 位虚拟地址切成 5 段：PGD(9) | PUD(9) | PMD(9) | PTE(9) | offset(12)。PGD 是根（每个进程一个 4KB 页），只有 512 个 8B 条目——每个条目指向一个 PUD 页或为空（表示这 512GB 区域未映射）。空条目 = 不占内存。

地址分解

$$\underbrace{|\text{PGD}|}_{9\text{ bit}}\;\underbrace{|\text{PUD}|}_{9}\;\underbrace{|\text{PMD}|}_{9}\;\underbrace{|\text{PTE}|}_{9}\;\underbrace{|\text{offset}|}_{12}$$

每级索引 512 个条目（9 bit）。512 × 8B = 4KB — 每级页表刚好一页。

四级页表翻译的完整 walk

① 读 CR3 → PGD 物理地址。以 VA 的 PGD 索引（bit 47:39）查 PGD 表的第 i 项。如果该项 P=0 → 缺页（这 512GB 区域还没映射）。
② PGD[i] → PUD 物理地址。以 VA 的 PUD 索引（bit 38:30）查 PUD 表的第 j 项。P=0 → 缺页。
③ PUD[j] → PMD 物理地址。以 VA 的 PMD 索引（bit 29:21）查 PMD 表。P=0 → 缺页。
④ PMD[k] → PTE 物理地址。以 VA 的 PTE 索引（bit 20:12）查最终 PTE。P=0 → 缺页。P=1 → 取出 PFN。
⑤ 物理地址 = PFN × 4096 + offset（bit 11:0）。TLB 缓存这整条链的结果。

为什么是四级？48 bit 虚拟地址，minus 12 bit offset = 36 bit VPN。36/9 = 4 级。如果 57-bit（5-level paging，Intel 新增）：minus 12 = 45，45/9 = 5 级。Linux 的 `CONFIG_5LEVEL_PAGING` 支持这个。

8. 大页：TLB 不够用了

4KB 页 × 64-entry TLB → 覆盖 256KB 地址空间。数据库、JVM、ML 训练的内存 footprint 是 GB 级——TLB miss 会非常多。

大页（Huge Page）：2MB 或 1GB 的页。2MB 页 → offset 21 bit，页表少一级（PMD 直接指向 2MB 帧）。1GB 页 → offset 30 bit，页表少两级。TLB 覆盖面积暴涨 512×。

代价：内部碎片——一个 2MB 页即使只用了 4KB 也占整个 2MB。而且大页分配需要物理内存有连续的 2MB/1GB 区域——内存碎片化时做不到。

停下来想一想：为什么 Linux 用 THP（Transparent Huge Page）而非让应用显式申请？因为应用不知道自己会访问多少内存。THP 在后台尝试把连续的 512 个 4KB 页合并为一个 2MB 大页——对应用透明。但合并可能失败（内存碎片化），而且合并过程本身消耗 CPU（khugepaged 线程）。

10. 推导与自测

P1 · 页表大小计算 L1 基础

32-bit VA，4KB 页，每 PTE 4 字节。(a) VPN 多少 bit？页表有多少 PTE？(b) 页表占多大内存？(c) 如果进程只用前 64MB 和后 64MB（共 128MB 有效映射），在单级页表 vs 两级页表（每级 10 bit VPN）下，页表的总内存占用各多少？

▸ 解答
(a) offset = 12 bit → VPN = 32-12 = 20 bit。PTE 总数 = $2^{20} = 1,048,576$。
(b) 1,048,576 × 4B = 4MB。
(c) 单级：即使只用 128MB，全表仍需要 4MB（所有 VPN 的 PTE 必须存在——即使大部分 Present=0）。
两级（10+10）：第一级（页目录）有 $2^{10}=1024$ 个 PDE（4KB）。前 64MB = VA 0x0000_0000 到 0x03FF_FFFF → 第一级索引 [0..63]。后 64MB 在 VA 高区。用户只需 64 + 64 = 128 个 PDE（指向 128 个第二级页表）→ 第一级 4KB + 128 × 4KB ≈ 516KB。相比 4MB 节省 ~8×。
P2 · TLB 命中率与覆盖面积 L2 理解

L1 TLB 64 条目，L2 TLB 1536 条目，页大小 4KB。(a) 各能覆盖多大虚拟地址空间？(b) 一个程序的工作集是 8MB（代码+数据），TLB 能覆盖吗？如果用 2MB 大页呢？(c) 为什么 TLB 不做得和大页一样大（如 10,000 条目）？

▸ 解答
(a) L1 TLB: 64 × 4KB = 256KB。L2 TLB: 1536 × 4KB = 6MB。
(b) 8MB > 6MB → 即使 L2 TLB 全用上也不够覆盖 → 会发生 TLB miss。如果用 2MB 大页：L1 TLB 64 × 2MB = 128MB——绰绰有余。
(c) TLB 是全相联（fully-associative）或高组相联的硬件结构。每个条目都有一个比较器同时比较 VPN——64 条目 = 64 个比较器并行工作。10000 条目 = 10000 个比较器 → 面积和功耗爆炸。而且 TLB 在 L1 cache 的关键路径上——慢了会拖慢所有访存。所以用"小 L1 + 大 L2"两层结构，再加大页来提升覆盖。
P3 · 追踪一次 TLB miss + 页表 walk L2 理解

虚拟地址 0x00007F4A3B1C2000（48-bit），4KB 页，四级页表。(a) 分解为 PGD/PUD/PMD/PTE 索引 + offset。(b) 写出硬件从 CR3 到物理地址的完整查找序列。如果 PUD 项 Present=0，在哪个索引处发生缺页？

▸ 解答
0x00007F4A3B1C2000 二进制：0000 0000 0000 0000 0111 1111 0100 1010 0011 1011 0001 1100 0010 0000 0000 0000
PGD(47:39) = 000000000 = 0 · PUD(38:30) = 000 0111 111 = 63 · PMD(29:21) = 1 0100 1010 = 330 · PTE(20:12) = 0011 1011 00 = 236 · offset(11:0) = 01 1100 0010 0000 0000 0000 → 不用管具体值
① CR3 → PGD 物理地址。读 PGD[0] → PUD 物理地址。② 读 PUD[63]。如果 Present=0 → 在此缺页。③ 如果 Present=1 → 读 PMD[330]。④ 读 PTE[236] → 得到 PFN。⑤ 物理地址 = PFN × 4096 + offset。
P4 · Meltdown 与页表隔离 L3 进阶

2018 年的 Meltdown 漏洞利用了"内核内存映射在用户页表中（只是 U/S=0 标记为不可访问）"这一事实。攻击者可以训练 CPU 的推测执行在权限检查前就读取内核内存。(a) 为什么内核内存一开始会映射在用户页表中？(b) KPTI（Kernel Page Table Isolation）怎么修复它——代价是什么？(c) 这和本课学的哪个机制（上下文切换时的高开销操作）直接相关？

▸ 提示
(a) 映射内核内存到每个进程的页表避免了上下文切换时刷 TLB——内核的 TLB 项标了 G（Global）bit，切换进程时不刷。(b) KPTI 把内核页表从用户页表中移除——用户态页表只映射极少量"进入内核所必须"的代码。(c) 代价：每次系统调用都要切换页表（用户页表 → 内核页表），付出 CR3 写 + TLB 刷新的代价。
P5 · 逆向设计——如果物理地址和虚拟地址一样大 L3 进阶

假设你设计一种新型 CPU，物理地址和虚拟地址都是 64 bit 全宽（而非 x86-64 的 48 bit 虚拟+52 bit 物理），页大小 4KB。需要多少级页表？每级 VPN 建议多少 bit？每级页表多大？如果物理内存只有 16GB，页表浪费多少？

▸ 提示
VPN = 64-12 = 52 bit。每级 9 bit → 52/9 ≈ 5.78 → 需要 6 级。但最后一级不全（52-5×9=7 bit）。每级 512 条目 × 8B = 4KB 刚好一页。
